## 📄 파일 전체 지도

```python
import numpy as np, cv2
from Common.utils import contain_pts                    # 점이 사각형 안에 있나?

def draw_rect(img):                                     # ① 선택 창 그리기 (핸들 4개 + 초록 사각형) → 10-3
    rois = [(p-small, small * 2) for p in pts1]
    for (x,y), (w,h) in np.int32(rois):
        roi = img[y:y + h, x:x + w]
        val = np.full(roi.shape, 80, np.uint8)
        cv2.add(roi, val, roi)                          #    핸들 부분 밝게
        cv2.rectangle(img, (x,y, w, h), (0, 255, 0), 1)
    cv2.polylines(img, [pts1.astype(int)], True, (0, 255, 0), 1)
    cv2.imshow("select rect", img)

def warp(img):                                          # ② 결과 창 그리기 (Part 9 그대로) → 10-5
    perspect_mat = cv2.getPerspectiveTransform(pts1, pts2)
    dst = cv2.warpPerspective(img, perspect_mat, (400, 350), cv2.INTER_CUBIC)
    cv2.imshow("perspective transform", dst)

def onMouse(event, x, y, flags, param):                 # ③ 마우스 상태 기계 → 10-4
    global check
    if event == cv2.EVENT_LBUTTONDOWN:
        for i, p in enumerate(pts1):
            p1, p2 = p - small, p + small
            if contain_pts((x,y), p1, p2): check = i
    if event == cv2.EVENT_LBUTTONUP: check = -1
    if check >= 0 :
        pts1[check] = (x, y)
        draw_rect(np.copy(image))
        warp(np.copy(image))

image = cv2.imread('images/perspective2.jpg')           # (400, 470, 3)
small = np.array((12, 12))                              # 핸들 반지름 12 → 24×24 핸들
check = -1                                              # 잡고 있는 점 번호 (-1 = 없음)
pts1 = np.float32([(100, 100), (300, 100), (300, 300), (100, 300)])   # 좌상, 우상, 우하, 좌하
pts2 = np.float32([(0, 0), (400, 0), (400, 350), (0, 350)])           # 결과 캔버스 네 모서리

draw_rect(np.copy(image))
cv2.namedWindow("perspective transform")
cv2.setMouseCallback("select rect", onMouse, 0)
cv2.waitKey(0)
```

## 10-2. 전역 데이터 네 개

| 이름 | 값 | 역할 |
|---|---|---|
| `small` | `array([12, 12])` | 핸들 **반지름**. 핸들은 `p ± 12`, 즉 24×24 |
| `check` | `-1` | 지금 잡고 있는 점 번호. `-1`이면 아무것도 안 잡음 |
| `pts1` | float32 (4, 2) | **움직이는** 원본 네 점: 좌상 → 우상 → 우하 → 좌하 (시계 방향) |
| `pts2` | float32 (4, 2) | **고정된** 결과 네 점: 같은 순서 |

### 10-2-a. 왜 꼭 `np.float32`일까

`getPerspectiveTransform`은 **float32 점 4개만** 받아요. int32를 넣어 보면:
```
cv2.error: (-215:Assertion failed) src.checkVector(2, CV_32F) == 4 && ...
                                                       ↑ "float32 2차원 점 4개여야 함"
```
나중에 `pts1[check] = (x, y)`로 **정수**를 넣어도, 배열이 이미 float32라서 자동으로 `105.0`처럼 저장돼요. 그래서 처음 만들 때만 float32로 만들어 두면 돼요.

### 10-2-b. 순서 규칙: `10`과 `11`은 순서가 다르다

| 파일 | 네 점 순서 | 모양 |
|---|---|---|
| `10.perspective_transform.py` | 좌상, 우상, **좌하, 우하** | Z자 |
| `11.perspective_event.py` | 좌상, 우상, **우하, 좌하** | 시계 방향 한 바퀴 |

**둘 다 정상 동작해요.** 행렬을 구할 때 중요한 건 "`pts1[i]`가 `pts2[i]`로 간다"는 **짝**뿐이라서, pts1과 pts2가 **같은 규칙**만 따르면 돼요. 그런데 `11`이 시계 방향을 고른 데는 이유가 있어요. `cv2.polylines`는 점을 **순서대로** 잇는데, Z자 순서로 이으면 사각형이 아니라 **X자(나비넥타이)**가 그려져요. 화면에 사각형을 그려야 하는 `11`은 한 바퀴 도는 순서가 필요해요.

## 10-3. `draw_rect` 해부: 핸들 그리기

### 10-3-a. ROI 목록 만들기

```python
rois = [(p-small, small * 2) for p in pts1]
```
점마다 `(왼쪽 위 = p − 12, 크기 = 24)` 묶음을 만들어요.

| i | p | `p − small` | `small * 2` | 의미 (x, y, w, h) |
|---|---|---|---|---|
| 0 | (100, 100) | (88, 88) | (24, 24) | (88, 88, 24, 24) |
| 1 | (300, 100) | (288, 88) | (24, 24) | (288, 88, 24, 24) |
| 2 | (300, 300) | (288, 288) | (24, 24) | (288, 288, 24, 24) |
| 3 | (100, 300) | (88, 288) | (24, 24) | (88, 288, 24, 24) |

`np.int32(rois)`는 shape **(4, 2, 2)** 배열이 돼요(점 4개 × [위치, 크기] × [x, y]). 그래서 `for (x,y), (w,h) in ...`로 한 번에 풀 수 있어요. 마우스 좌표는 소수가 아니지만 `pts1`이 float32라서, 슬라이싱 인덱스로 쓰려고 int32로 바꾸는 거예요.

### 10-3-b. ROI는 "뷰", `cv2.add`는 "포화"

```python
roi = img[y:y + h, x:x + w]                   # ① 슬라이싱 = 복사가 아니라 "창문(뷰)"
val = np.full(roi.shape, 80, np.uint8)        # ② (24, 24, 3) 전부 80
cv2.add(roi, val, roi)                        # ③ roi + 80 → 결과를 roi 자리에 다시 씀
```
`np.shares_memory(roi, img)`가 `True`예요. roi는 img의 일부를 들여다보는 **창문**이라서, 창문에 쓰면 **img가 바뀌어요.** 그래서 반환값을 따로 받지 않아도 핸들이 밝아져요.

**실제 화소 값**

| 위치 | 전 (B, G, R) | `cv2.add` 후 |
|---|---|---|
| (100, 100) 핸들 중심 | (132, 105, 78) | (212, 185, 158) ← 전부 +80 |
| (88, 88) 핸들 모서리 | (210, 189, 167) | **(255, 255, 247)** ← 255에서 멈춤 |

> 📚 **복습: 포화 연산 (chap06 밝기 조절)**
> uint8은 0~255만 담을 수 있어요. 255에 80을 더할 때 두 방식이 달라요.
> ```
> cv2.add :  255 + 80 → 255   (포화: 끝에서 멈춤)
> numpy + :  255 + 80 →  79   (랩어라운드: 335 − 256 = 79, 밝은 곳이 갑자기 어두워짐)
> ```
> 핸들을 밝게 칠하는 데 numpy `+`를 쓰면, 하늘처럼 하얀 부분의 핸들이 **시커멓게** 보여요.

### 10-3-c. 왜 매번 `np.copy(image)`를 넘길까

`draw_rect(np.copy(image))`에서 `np.copy`를 빼고 원본 `image`를 넘기면, 이벤트가 올 때마다 **같은 원본에 80씩 계속 더해져요.** 화소 (100, 100)을 따라가 보면:
```
이벤트 0 (원래):  (132, 105,  78)
이벤트 1:         (212, 185, 158)
이벤트 2:         (255, 255, 238)
이벤트 3:         (255, 255, 255)   ← 세 번 만에 하얗게 탐
```
게다가 점을 옮기면 **예전 위치의 핸들과 초록 선이 지워지지 않고** 잔상으로 남아요. 그래서 매번 **깨끗한 원본의 복사본**에 처음부터 다시 그려요. `warp(np.copy(image))`의 복사는 사실 필요 없어요(`warpPerspective`는 입력을 바꾸지 않아요). 그래도 대칭을 맞추려고 쓴 거예요.

### 10-3-d. 사각형과 다각형 그리기

```python
cv2.rectangle(img, (x,y, w, h), (0, 255, 0), 1)                  # (x, y, w, h) 한 묶음 형식
cv2.polylines(img, [pts1.astype(int)], True, (0, 255, 0), 1)     # True = 닫힌 도형 (3→0도 이음)
```
- `rectangle`은 `(pt1, pt2)` 두 점 형식 말고 **`(x, y, w, h)` 묶음 하나**로도 받아요.
- `polylines`는 **점 리스트의 리스트**를 받아요(도형 여러 개를 한 번에 그릴 수 있어서). 그래서 `[ ]`로 한 번 더 감쌌어요. 이 초록 선이 **순서를 눈으로 검사하는 도구**가 돼요(10-6).

## 10-4. `onMouse` 해부: 상태 기계

### 10-4-a. 핸들 판정: `contain_pts`

```python
def contain_pts(p, p1, p2):                            # Common/utils.py
    return p1[0] <= p[0] < p2[0] and p1[1] <= p[1] < p2[1]
```
**반열린 구간** `[p1, p2)`예요. 0번 점 `(100, 100)`의 핸들은 `p1 = (88, 88)`, `p2 = (112, 112)`예요.

| 클릭 위치 | 결과 | 이유 |
|---|---|---|
| (88, 88) | ✅ True | 시작은 포함 |
| (111, 111) | ✅ True | |
| (112, 100) | ❌ False | 끝은 미포함 |
| (87, 100) | ❌ False | |

그래서 핸들은 정확히 x = 88~111, **24칸**이에요(Part 1의 `range`, 슬라이싱과 같은 규칙).

### 10-4-b. 이벤트 한 번의 드래그를 표로 따라가기

0번 핸들(좌상)을 `(105, 97)`에서 잡아서 `(70, 60)`까지 끄는 상황이에요.

| # | 이벤트 | (x, y) | 들어올 때 check | 일어나는 일 | 나갈 때 check | pts1[0] |
|---|---|---|---|---|---|---|
| 1 | MOUSEMOVE | (150, 150) | −1 | `if check >= 0` 거짓 → 아무것도 안 함 | −1 | (100, 100) |
| 2 | **LBUTTONDOWN** | (105, 97) | −1 | 반복문: i=0 → 핸들 안 ✅ → `check = 0`. i=1~3 → 밖 | **0** | **(105, 97)** ← 바로 이동 + 다시 그림 |
| 3 | MOUSEMOVE | (90, 80) | 0 | `pts1[0] = (90, 80)` → 두 창 다시 그림 | 0 | (90, 80) |
| 4 | MOUSEMOVE | (70, 60) | 0 | `pts1[0] = (70, 60)` → 두 창 다시 그림 | 0 | (70, 60) |
| 5 | **LBUTTONUP** | (70, 60) | 0 | `check = -1` → 아래 `if` 거짓 | **−1** | (70, 60) |
| 6 | MOUSEMOVE | (200, 200) | −1 | 아무것도 안 함 | −1 | (70, 60) |

**관찰 포인트 세 가지**

1. **2번 줄**: 누르는 순간 반복문이 끝나고 **같은 함수 안에서** 아래 `if check >= 0`까지 내려가요. 그래서 핸들 중심이 클릭한 곳으로 **최대 12화소 순간이동**해요(`(100,100) → (105,97)`).
2. **핸들이 겹치면**: 두 점이 24화소 안으로 가까워지면 클릭이 두 핸들 모두에 들어가요. 반복문이 끝까지 돌면서 `check`를 덮어쓰니까 **번호가 큰 점이 이겨요.** 작은 번호 점은 큰 번호 점을 치워야 잡을 수 있어요.
3. **5번 줄의 순서**: UP 처리(`check = -1`)가 아래 `if`보다 **먼저** 와서, 손을 뗀 이벤트에서는 다시 그리지 않아요.

### 10-4-c. `global check`는 필요하고 `global pts1`은 필요 없는 이유

Part 8 Q2와 이어지는 얘기예요.

| 코드 | 하는 일 | `global` 필요? |
|---|---|---|
| `check = i` | 이름 `check`에 **새 값을 붙임** (재바인딩) | ✅ 필요. 없으면 지역 변수가 됨 |
| `pts1[check] = (x, y)` | 이미 있는 배열의 **칸 하나를 고침** (변경) | ❌ 불필요. `pts1`이라는 이름은 그대로 |

🧠 **비유**: `check = 3`은 "사물함 이름표를 새로 붙이기"라서 어느 사물함(전역/지역)인지 정해야 해요. `pts1[0] = …`는 "이미 있는 사물함을 열고 안의 물건 하나 바꾸기"라서, 사물함을 **찾기만** 하면 돼요. 찾을 때는 파이썬이 알아서 전역까지 찾아봐요.

### 10-4-d. 이벤트 한 번에 걸리는 시간

마우스를 끌면 MOUSEMOVE가 초당 수십 번 와요. 매번 다시 계산해도 괜찮을까요? 470×400 이미지로 재 봤어요(`imshow` 제외).

| 작업 | 시간 |
|---|---|
| `getPerspectiveTransform` (8×8 풀기) | **0.0035 ms** (3.5 μs) |
| `draw_rect` (복사 + 핸들 4개 + 선) | 0.05 ms |
| `warpPerspective` LINEAR (지금 실제로 쓰이는 것) | 0.53 ms |
| `warpPerspective` CUBIC (10-5에서 고치면) | 1.45 ms |

합쳐도 **2 ms 이하**라서 초당 500번도 가능해요. 행렬 구하기는 거의 공짜고, 시간은 대부분 **화소마다 하는 일**(워핑)에 들어가요.

## 10-5. `warp` 해부

```python
perspect_mat = cv2.getPerspectiveTransform(pts1, pts2)      # 이벤트마다 새 행렬
dst = cv2.warpPerspective(img, perspect_mat, (400, 350), cv2.INTER_CUBIC)
```

### 10-5-a. ⚠️ 다섯 번째 등장: 위치 인자 버그

```
위치 인자 INTER_CUBIC 결과 == flags=INTER_LINEAR 결과?  →  True
위치 인자 INTER_CUBIC 결과 == flags=INTER_CUBIC 결과?   →  False
```
네 번째 자리는 `dst`라서 이번에도 **양선형**이 쓰이고 있어요. Part 3, 6, 8, 9에 이어 다섯 번째예요. 이 정도면 이 교재 코드 전체의 **습관적 실수**라고 봐야 해요. **OpenCV 함수의 보간 옵션은 항상 `flags=`로** 쓰는 습관을 들이세요.

### 10-5-b. 결과 크기가 `(400, 350)`으로 고정

`pts2`가 캔버스 네 모서리라서 **사진에서 어떤 모양을 골랐든** 결과는 항상 400×350이에요. 이게 왜 문제인지는 10-7에서 볼게요.

> 💡 **세부 사항**: 너비 400 캔버스의 x 좌표는 0~399예요. 그래서 `pts2`의 `(400, 0)`은 엄밀히 말하면 캔버스 **1칸 밖**이에요. Part 2에서 본 "화소 중심이냐 모서리냐" 관점 차이라서 결과에 1화소 미만의 영향밖에 없어요. 정확히 맞추고 싶으면 `(399, 349)`를 쓰면 돼요.

## 10-6. ⚠️ 이 Part의 핵심: 점 순서를 잘못 맞추면

사람이 핸들을 끌다 보면 점을 **엉뚱한 꼭짓점**에 갖다 놓을 수 있어요. `pts2`는 그대로 두고 `pts1`의 순서만 바꿔서 네 가지를 실험했어요(위치는 모두 같은 정사각형 `(100,100)~(300,300)`).

### 10-6-a. 실험 결과

| 이름 | pts1 순서 | 초록 선 모양 | M의 왼쪽 2×2 | det(A) | 네 꼭짓점의 w | 결과 그림 |
|---|---|---|---|---|---|---|
| **ok** | 좌상, 우상, 우하, 좌하 | □ | `[[2, 0], [0, 1.75]]` | **+3.5** | 1, 1, 1, 1 | 정상 |
| **ccw** | 좌상, **좌하**, 우하, **우상** (반시계) | □ | `[[0, 2], [1.75, 0]]` | **−3.5** | 1, 1, 1, 1 | **대각선 기준 거울상** (전치) |
| **shift** | **우상**, 우하, 좌하, **좌상** (한 칸 밀림) | □ | `[[0, 2], [−1.75, 0]]` | **+3.5** | 1, 1, 1, 1 | **반시계 90° 회전** |
| **bowtie** | 좌상, **우하**, **우상**, 좌하 | ⋈ (X자) | `[[−1, 0], [−0.875, 0.875]]` | −0.875 | **0.5, −0.5, −0.5, 0.5** | **두 조각으로 쪼개짐**, 55.7%만 채워짐 |

```
  ok                ccw                shift              bowtie
┌──────────┐      ┌──────────┐      ┌──────────┐      ┌───┐        ┌───┐
│ PILATUS  │      │S         │      │      L   │      │왼쪽│ (검정)  │오른│
│          │      │U  거울+   │      │      U   │      │건물│        │쪽 │
│          │      │T  전치    │      │  90° Z   │      │    │        │현수│
│          │      │A         │      │  회전 E   │      │    │        │막 │
└──────────┘      └──────────┘      └──────────┘      └───┘        └───┘
                  글자가 뒤집혀        글자가 아래→위로     가운데가 무한대로
                  보임               읽힘               날아가서 비어 있음
```

### 10-6-b. 왜 이렇게 될까: 수학으로 읽기

**ccw (반시계 순서)**: 사각형을 반대 방향으로 한 바퀴 돌았어요. `M`을 보면 `x' = 2y − 200`, `y' = 1.75x − 175`예요. 원본의 **x와 y가 서로 자리를 바꿨어요.** 이건 대각선을 거울로 한 반사라서 **det < 0**이에요(Part 8 Q3의 "det 음수 = 거울상"과 같아요).

**shift (한 칸 밀림)**: 원본의 우상 점이 결과의 좌상에 가요. 방향(시계)은 그대로라서 det > 0, 즉 **회전**이에요. 거울상은 아니에요. `x' = 2y − 200`, `y' = −1.75x + 525`라서 원본 오른쪽(x 큼) → 결과 위쪽(y' 작음)이에요.

**bowtie (X자)**: 이게 제일 위험해요.
```
M의 마지막 행 = [−0.005, 0, 1]   →   w = −0.005·x + 1

w = 0 이 되는 곳:  x = 200   ← 정사각형의 정가운데 세로선!

원본 (150, 120): w = +0.25  → (−200, −105)       캔버스 밖 왼쪽 위
원본 (200, 200): w =  0     → (−∞, +∞)           무한대 🔥
원본 (290, 110): w = −0.45  → (422.2, 350.0)     캔버스 밖 오른쪽 아래
```
Part 9-7-a에서 본 **"w = 0 직선 = 지평선"**이 선택 영역 **한가운데**를 지나가요. 선의 왼쪽(w > 0)과 오른쪽(w < 0)이 무한대를 사이에 두고 갈라져서, 결과 그림이 **두 조각**으로 쪼개지고 가운데는 비어 버려요.

### 10-6-c. 교훈: 두 가지 안전 검사

| 검사 | 방법 | 잡아내는 것 |
|---|---|---|
| ① 순서가 한 바퀴인가 | 초록 `polylines`가 X자인지 **눈으로** / `cv2.isContourConvex`로 **볼록한지** | bowtie |
| ② 방향이 맞는가 | 네 꼭짓점의 **w 부호가 모두 같은지**, det(A)의 부호 | bowtie(w 부호 섞임), 반시계(거울) |

`11`은 사람이 보면서 맞추니까 ①을 눈으로 할 수 있어요. 그런데 **자동으로** 꼭짓점을 찾는 프로그램은 검출된 네 점이 **아무 순서**로 나와요. 그래서 "좌상 → 우상 → 우하 → 좌하"로 **정렬하는 함수**가 꼭 필요해요. 이게 저장소의 `projects/p1_doc_scanner`에서 직접 구현할 `order_corners`예요([scanner/corners.py](../../projects/p1_doc_scanner/scanner/corners.py)). 정렬 방법과 흔한 방법이 깨지는 경우는 [GUIDE.md](../../projects/p1_doc_scanner/GUIDE.md) Step 3에 정리돼 있으니, 여기서는 **왜 필요한지**까지만 가져가세요.

## 10-7. 출력 크기 고정의 함정: 비율이 찌그러진다

### 10-7-a. 현수막으로 실험

사진 속 "FUN & ACTION" 현수막의 꼭짓점을 대략 찍었어요: `(266,143) (414,117) (420,241) (270,247)`.

```
네 변의 길이 (사진 속, 화소)
  위쪽:   150.3      아래쪽: 150.1
  왼쪽:   104.1      오른쪽: 124.1     ← 오른쪽이 더 김 = 오른쪽이 카메라에 더 가까움

펼칠 크기 = (가로: 위·아래 중 큰 값, 세로: 왼·오른 중 큰 값)
         = (150, 124)  → 비율 1.21

11의 고정 크기 = (400, 350) → 비율 1.14     ← 약 6% 세로로 늘어남
```
현수막은 거의 정사각형에 가까워서 6% 차이가 눈에 잘 안 띄어요. 그런데 **A4 세로 문서**(210×297, 비율 0.707)를 400×350(비율 1.143)에 펴면:
```
1.143 / 0.707 = 1.62배   ← 가로로 62% 뚱뚱해진 문서
```
글자가 옆으로 퍼져서 바로 티가 나요.

### 10-7-b. 해결: 사각형에서 크기를 계산

```python
W = round(max(위쪽 길이, 아래쪽 길이))
H = round(max(왼쪽 길이, 오른쪽 길이))
pts2 = np.float32([(0, 0), (W, 0), (W, H), (0, H)])
dst = cv2.warpPerspective(img, M, (W, H), flags=cv2.INTER_LINEAR)
```
**"짧게 찍힌 변이 아니라 긴 변에 맞춘다"**예요. 멀리 있어서 짧게 찍힌 쪽에 맞추면 해상도를 버리게 되니까요. 이것도 p1 프로젝트의 `quad_size`로 직접 구현해요(docstring에 규칙이 그대로 적혀 있어요).

> ⚠️ **한계**: 이건 **근사**예요. 원근 때문에 변 길이가 줄어든 정도는 거리마다 달라서, 진짜 종이 비율을 정확히 알려면 카메라 정보(초점거리)가 필요해요. 문서처럼 비율을 아는 경우(A4 = 1 : 1.414)에는 **비율을 직접 지정**하는 게 가장 정확해요.

## 10-9. 🚗 AVM 연결: 수동 캘리브레이션 도구와 LUT

> **① 이 화면 = 탑뷰 캘리브레이션 도구의 원형**
> 차 주변 바닥에 격자 매트를 깔고, 각 카메라 영상에서 매트의 기준점을 **사람이 찍거나 자동으로 검출해서** 호모그래피를 구해요. `11`의 핸들 드래그가 바로 그 "사람이 찍는" 버전이에요. 실무에서는 어안 왜곡을 먼저 편 영상 위에서 찍고, 점을 4개보다 많이 써서 `findHomography`로 푸는 게 보통이에요(Part 9-9).
>
> **② 행렬이 고정되면 → LUT(룩업 테이블)**
> `11`은 점이 계속 바뀌니까 매번 `warpPerspective`를 해요. 그런데 차에 고정된 카메라는 캘리브레이션이 끝나면 **M이 바뀌지 않아요.** 그러면 "결과 화소 (j, i)는 원본 어디서 가져오나"(Part 9-8의 M⁻¹ + 나눗셈)를 **한 번만 계산해서 표로 저장**하고, 매 프레임은 표만 보고 `cv2.remap`으로 가져오면 돼요.
>
> 1280×720 영상 → 800×800 탑뷰로 실제로 재 봤어요.
>
> | 방법 | 프레임당 시간 | 결과 차이 |
> |---|---|---|
> | `warpPerspective` (매번 M⁻¹·나눗셈) | 1.14 ms | 기준 |
> | `remap` + float32 LUT | 0.73 ms | 최대 2 밝기, 평균 0.00005 |
> | `remap` + 고정소수점 LUT (`convertMaps`) | 0.69 ms | 최대 2 밝기 |
>
> LUT 크기는 float32일 때 5.12 MB(800×800 × x, y × 4바이트), 고정소수점이면 3.84 MB예요. 이 PC(12스레드)에서는 1.6배 차이지만, **LUT의 진짜 장점은 속도가 아니라 합치기**예요. **어안 왜곡 펴기 + 호모그래피 + 4대 카메라 이어 붙이기**를 각각 하면 보간을 세 번 해서 흐려지는데(Part 7의 "보간은 한 번만" 교훈), 셋을 합친 **좌표 표 하나**로 만들면 영상에서 **보간을 딱 한 번만** 해요. 그래서 AVM 실무 탑뷰는 거의 전부 LUT 방식이에요.

| `global` | `check = …`(재바인딩)은 필요, `pts1[i] = …`(변경)은 불필요 |
| 속도 | 행렬 3.5 μs, 워핑 0.5~1.5 ms → 실시간 OK |
| 버그 | `INTER_CUBIC` 위치 인자 → 실제로는 LINEAR (5번째) |
| **점 순서** | 반시계 = 거울(det < 0), 한 칸 밀림 = 90° 회전, X자 = w 부호 섞임 → 두 조각 |
| 출력 크기 | 고정하면 비율 찌그러짐 → 변 길이로 `(W, H)` 계산 |
| AVM | 고정 M → LUT + `remap`. 왜곡 펴기·호모그래피·스티칭을 표 하나로 합쳐서 보간 1번 |

**다음 Part로 넘어가는 다리**: 이제 chap08의 파일 11개를 전부 봤어요. Part 11에서는 **크기 조절 → 이동 → 회전 → 어파인 → 합성 → 원근**을 **하나의 큰 그림**(변환 계층도, 자유도, 필요한 점 수, OpenCV 함수 대응표)으로 정리하고, 다섯 번 나온 위치 인자 버그를 포함한 **버그 목록**과 **AVM으로 가는 학습 로드맵**까지 묶을게요.
