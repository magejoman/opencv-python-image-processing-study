## 7-1. 행렬 곱 = 변환을 이어 붙이기

### 7-1-a. 📚 행렬 곱 복습

> **결과의 (행 r, 열 c) 칸 = 왼쪽 행렬의 r행 · 오른쪽 행렬의 c열** (같은 자리끼리 곱해서 더하기)
> ```
> ┌ 1  0  50 ┐   ┌ 0  1  0 ┐        (1행)·(1열) = 1·0 + 0·(−1) + 50·0 = 0
> │ 0  1   0 │ · │−1  0  0 │   →    (1행)·(2열) = 1·1 + 0·0    + 50·0 = 1
> └ 0  0   1 ┘   └ 0  0  1 ┘        (1행)·(3열) = 1·0 + 0·0    + 50·1 = 50  …
> ```
> numpy에서는 `A @ B` 또는 `A.dot(B)`예요. `A * B`는 **같은 자리끼리 곱하기**라 완전히 다른 연산이에요.

### 7-1-b. 오른쪽부터 적용된다

점 p에 변환 A, B, C를 차례로 적용하면:
```
① A 적용:   A·p
② B 적용:   B·(A·p)
③ C 적용:   C·(B·(A·p))  =  (C·B·A)·p          ← 행렬 곱은 괄호를 옮겨도 됨(결합법칙)
                              └─ M ─┘
```
**M = C·B·A** 하나만 미리 계산해 두면, 화소마다 `M·p` **한 번**만 곱하면 돼요.

🧠 **비유: 양말과 신발**
```
신는 순서:   양말(A) → 신발(B)
식으로 쓰면: 신발 · 양말 · 발 = B · A · p        ← 먼저 하는 게 오른쪽(발에 가까운 쪽)

벗는 순서:   신발 먼저 → 양말 나중
식으로 쓰면: (B · A)⁻¹ = A⁻¹ · B⁻¹               ← 역행렬은 순서가 뒤집힘
```

`getAffineMat`의 코드를 다시 보면:
```python
cen_trans.dot(rot_mat.dot(trans_mat.dot(scale_mat.dot(org_trans))))
#   ⑤          ④           ③            ②           ①      ← 적용 순서 (오른쪽부터)
```

### 7-1-c. 합치면 좋은 점 두 가지

**① 빠르다**: 화소 105,600개 × 행렬 5번 곱하기가 아니라, 행렬끼리 4번 곱해 두고 화소마다 **1번**만 곱해요.

**② 화질이 좋다**: 변환을 따로따로 하면 **보간이 여러 번** 일어나요. Part 4 🧪에서 0.5칸 이동을 10번 하니까 흐려졌죠. 실제로 같은 결과(45° 회전 + 0.7배)를 두 방식으로 만들어서 선명도(라플라시안 분산, 클수록 선명)를 쟀어요.

| 방식 | 보간 횟수 | 선명도 |
|---|---|---|
| 회전 `warpAffine` → 축소 `warpAffine` (두 번) | 2번 | 2,421 |
| 두 행렬을 곱해서 `warpAffine` 한 번 | **1번** | **3,531** (약 46% 더 선명) |

그리고 행렬을 곱한 결과는 OpenCV가 한 번에 만들어 주는 행렬과 **정확히 같아요.**
```
S(0.7) @ R(45°)                       getRotationMatrix2D((150,165), 45, 0.7)
[[ 0.495  0.495   -5.917 ]            [[ 0.495  0.495   -5.917 ]
 [-0.495  0.495  157.5754]]            [-0.495  0.495  157.5754]]     ✅
```

> 🚗 **AVM 연결**: 실무 탑뷰 파이프라인은 "렌즈 왜곡 보정 → 바닥 평면 투영 → 캔버스 배치(회전·이동)"처럼 여러 단계예요. 이걸 프레임마다 단계별로 하면 느리고 흐려져요. 그래서 **전체를 합친 좌표 대응을 한 번 계산해서 LUT(룩업 테이블)로 저장**하고, 실행 중에는 **보간 한 번**만 해요. 오늘 배우는 "합치기"의 실전 버전이에요.

## 7-2. 순서가 바뀌면 결과가 달라진다

### 7-2-a. 점 하나로 실험

- `T` = 오른쪽으로 50 이동
- `R` = 90° 회전 (`08`과 같은 OpenCV 방식, `(x, y) → (y, −x)`, 화면 반시계)
- 점 `p = (100, 0)`

**경우 ① `R·T`: 이동 먼저, 그다음 회전**
```
p = (100, 0)  ──T──▶  (150, 0)  ──R──▶  (0, −150)
```

**경우 ② `T·R`: 회전 먼저, 그다음 이동**
```
p = (100, 0)  ──R──▶  (0, −100)  ──T──▶  (50, −100)
```

**결과가 달라요:** `(0, −150)` vs `(50, −100)`

```
            y↑(화면에선 위)
              │
   (0,−150) ● │                    ← ① 이동이 회전에 "휩쓸려" 위쪽으로 감
              │
   (0,−100) ○ │   ● (50,−100)      ← ② 회전 후 순수하게 오른쪽 50
              │
──────────────┼──────────●──────── x
             원점      p(100,0)
```

### 7-2-b. 행렬로 보면

```
R·T = [[ 0  1   0]                T·R = [[ 0  1  50]
       [−1  0 −50]                       [−1  0   0]
       [ 0  0   1]]                      [ 0  0   1]]
            ↑                                  ↑
     이동 (50, 0)이 회전돼서               이동 (50, 0)이 그대로
     (0, −50)이 됨
```
**왼쪽 2×2(회전 부분)는 똑같고, 세 번째 열(이동)만 달라요.** 핵심은 이거예요.

> **이동을 먼저 하면, 그 이동 벡터도 뒤에 오는 회전·크기 변경을 같이 받는다.**
> **이동을 나중에 하면, 화면에서 보이는 그대로 순수하게 이동한다.**

### 7-2-c. 순서를 바꿔도 되는 경우

| 조합 | 바꿔도 같나? | 이유 |
|---|---|---|
| 이동 + 이동 | ✅ | 덧셈은 순서 무관 |
| 회전 + 회전 (같은 중심) | ✅ | 30° + 45° = 45° + 30° |
| **균일** 크기(sx = sy) + 원점 기준 회전 | ✅ | 원 모양을 유지하는 확대는 방향과 무관 |
| 비균일 크기(sx ≠ sy) + 회전 | ❌ | 가로로 늘인 뒤 돌리기 ≠ 돌린 뒤 가로로 늘이기 |
| **이동 + 회전·크기** | ❌ | 7-2-a |

일반적으로 **행렬 곱은 교환 법칙이 성립하지 않아요**(`A·B ≠ B·A`). 그래서 순서를 신경 써야 해요.

## 7-3. `getAffineMat` 해부

### 7-3-a. 코드

```python
def getAffineMat(center, degree, fx=1, fy=1, translate=(0,0)):
    cen_trans = np.eye(3, dtype=np.float32)          # ⓐ 단위행렬 5개로 시작
    org_trans = np.eye(3, dtype=np.float32)
    scale_mat = np.eye(3, dtype=np.float32)
    trans_mat = np.eye(3, dtype=np.float32)
    rot_mat   = np.eye(3, dtype=np.float32)

    radian = (degree/180.0) * np.pi
    rot_mat[0] = [ np.cos(radian), np.sin(radian), 0]    # ⓑ OpenCV 방식 회전
    rot_mat[1] = [-np.sin(radian), np.cos(radian), 0]

    cen_trans[:2, 2] = center                            # ⓒ +중심 (되돌리기)
    org_trans[:2, 2] = np.multiply(center[0], -1)        # ⓓ −중심 (원점으로) ← 🐛 7-5
    trans_mat[:2, 2] = translate                         # ⓔ 추가 이동
    scale_mat[0, 0], scale_mat[1, 1] = fx, fy            # ⓕ 크기

    ret_mat = cen_trans.dot(rot_mat.dot(trans_mat.dot(scale_mat.dot(org_trans))))   # ⓖ
    return np.delete(ret_mat, 2, axis=0)                 # ⓗ 3×3 → 2×3
```

| 줄 | 포인트 |
|---|---|
| ⓐ | `np.eye(3)` = 단위행렬 `[[1,0,0],[0,1,0],[0,0,1]]` = "아무것도 안 하는 변환". 필요한 칸만 바꿔 써요 |
| ⓑ | `[[c, s], [−s, c]]` → Part 5-4의 **OpenCV 방식, 화면 반시계** |
| ⓒⓓⓔ | `[:2, 2]` = 위 두 행의 세 번째 열 = **이동 칸** (6-2-b) |
| ⓕ | `[0,0]`, `[1,1]` = 대각선 = **크기 칸** |
| ⓖ | 오른쪽부터 적용: **org → scale → trans → rot → cen** |
| ⓗ | 마지막 행 `[0, 0, 1]`을 지워서 `warpAffine`용 2×3으로 만들어요 (`ret_mat[:2]`와 같아요) |

### 7-3-b. 5개 행렬의 실제 값 (aff_mat1: 45°, 크기 1, 이동 없음)

```
① org_trans              ② scale_mat           ③ trans_mat
[[1  0  −150]            [[1 0 0]               [[1 0 0]
 [0  1  −150]  ← ‼️       [0 1 0]                [0 1 0]
 [0  0     1]]            [0 0 1]]               [0 0 1]]

④ rot_mat (45°)                     ⑤ cen_trans
[[ 0.7071  0.7071  0]               [[1  0  150]
 [−0.7071  0.7071  0]                [0  1  165]
 [ 0       0       1]]               [0  0    1]]
```
①과 ⑤를 비교해 보세요. ⑤는 `+(150, 165)`인데 ①은 `−(150, 150)`이에요. **짝이 안 맞아요.** 7-5에서 다룰게요.

### 7-3-c. 점 하나를 파이프라인으로 흘려보내기 (버그를 고친 버전, aff_mat4)

aff_mat4 = 45°, 0.7배, 이동 (200, 0)이에요. 원리를 보려고 ①을 올바른 `−(150, 165)`로 고친 버전으로 따라갈게요.

**점 A: 이미지 중심 (150, 165)**
```
① org   (−150, −165)   →  (0, 0)
② scale (×0.7)         →  (0, 0)
③ trans (+200, 0)      →  (200, 0)
④ rot 45°              →  (0.7071·200 + 0.7071·0,  −0.7071·200 + 0.7071·0) = (141.42, −141.42)
⑤ cen   (+150, +165)   →  (291.42, 23.58)
```

**점 B: 왼쪽 위 모서리 (0, 0)**
```
① org                  →  (−150, −165)
② scale ×0.7           →  (−105, −115.5)
③ trans +200           →  (95, −115.5)
④ rot 45°              →  x = 0.7071·95 + 0.7071·(−115.5) = 0.7071·(−20.5)  = −14.50
                           y = −0.7071·95 + 0.7071·(−115.5) = 0.7071·(−210.5) = −148.85
⑤ cen                  →  (135.50, 16.15)

③에서 넣은 `(200, 0)`은 "오른쪽 200"이었는데, ④ 회전을 거치면서 **(141.42, −141.42) = 오른쪽 위 대각선**으로 바뀌었어요. 7-2의 "이동을 먼저 하면 회전에 휩쓸린다"가 실제로 일어난 거예요. 그래서 dst4는 그림이 **오른쪽 위**로 밀려나서 많이 잘려요.

```

```
잘못된 org:  p − (150, 150)  =  (p + (0, 15)) − (150, 165)
                                 └─ 먼저 아래로 15 이동 ─┘ 그다음 올바른 org
```
즉 버그 버전은 **"아래로 15 밀고 → 올바르게 중심 회전"**한 것과 같아요. 7-2의 교훈대로, 먼저 한 이동 `(0, 15)`는 뒤의 회전을 같이 받아요.
```
rot 45° · (0, 15) = (0.7071·0 + 0.7071·15,  −0.7071·0 + 0.7071·15) = (10.61, 10.61)   ✅
0.7배까지 받으면  = 0.7 × (10.61, 10.61)                          = (7.42, 7.42)     ✅
```
표의 숫자와 정확히 일치해요.

### 7-5-d. 왜 아무도 몰랐을까

1. **정사각형 이미지에서는 버그가 안 보여요.** `rotate.jpg`(360×360)라면 `center = (180, 180)`이라 `center[0] = center[1]`이에요. Part 0-3-d에서 "(150, 165)는 x와 y가 다르니 기억하라"고 한 이유가 이거예요.
2. **10화소 정도 밀리는 건 눈으로 알아채기 어려워요.** 회전된 그림이 "대충 가운데"에 있으면 맞는 것 같거든요. 하지만 화소 단위로 비교하면 평균 **45.8**이나 차이 나요.

> 💡 **실무 교훈: 불변점 테스트.** 변환 행렬을 만들면 **"움직이면 안 되는 점"**을 넣어서 확인하세요.
> ```python

> ```

## 7-6. 주석 처리된 다른 순서: scale과 trans를 바꾸면

```python
# 현재:  cen · rot · trans · scale · org        → org → scale → trans → rot → cen
# 주석:  cen · rot · scale · trans · org        → org → trans → scale → rot → cen
```
**이동이 크기 변경보다 먼저** 오면, 이동 벡터가 **크기 변경도 같이 받아요.**

aff_mat4 조건(45°, 0.7배, 이동 (200, 0), 버그 고친 버전)으로 중심점이 어디로 가는지 비교해 볼게요.

| 순서 | 이동 벡터가 겪는 일 | 최종 이동량 | 중심 → |
|---|---|---|---|
| 현재 (scale 다음 trans) | 회전만 받음 | (141.42, −141.42) | **(291.42, 23.58)** |
| 주석 (trans 다음 scale) | **0.7배** 된 뒤 회전 | (99.0, −99.0) | **(249.0, 66.0)** |
| (참고) 이동을 **맨 마지막**에 | 아무것도 안 받음 | (200, 0) | (350, 165) |

```
이동 (200, 0)이 어떤 변환을 "겪느냐"에 따라:
  맨 마지막에 이동:   ──────────▶  (200, 0)      화면 기준 순수하게 오른쪽
  회전 전에 이동:     ↗ (141, −141)              45° 돌아서 오른쪽 위
  크기·회전 전에:     ↗ (99, −99)                0.7배로 줄고 돌아감
```

**어느 게 "맞는" 순서일까요?** 정답은 없어요. **원하는 효과**에 따라 골라요.
- "화면에서 오른쪽으로 200 옮겨 줘" → 이동을 **맨 왼쪽**(마지막 적용)에 둬요.
- "회전된 그림 기준으로 그림의 '오른쪽' 방향으로 옮겨 줘" → 회전보다 **오른쪽**(먼저 적용)에 둬요.

🧠 비유하면 **"차를 앞으로 10m"**가 지도 기준 북쪽 10m인지, **차가 향한 방향**으로 10m인지의 차이예요. 후자처럼 이동을 회전보다 먼저 쓰면 "자기 기준(local) 좌표계"에서의 이동이 돼요.

|---|---|
| 합성 | `M = C·B·A` → **A 먼저, C 마지막** (오른쪽부터) |
| 역행렬 | `(B·A)⁻¹ = A⁻¹·B⁻¹` (양말·신발 순서 뒤집기) |
| 합치는 이유 | 화소마다 곱셈 1번 + **보간 1번** → 빠르고 선명 (실측 선명도 2,421 → 3,531) |
| 순서 | 일반적으로 `A·B ≠ B·A`. **먼저 한 이동은 뒤의 회전·크기를 같이 받음** |
| 2×3 읽기 | 왼쪽 2×2 = 모양, 세 번째 열 = 위치 |
| `getAffineMat` | org → scale → trans → rot → cen (3×3 5개 곱한 뒤 마지막 행 삭제) |
| 🐛 버그 | `np.multiply(center[0], -1)` → `(−150, −150)`. 정답은 `np.multiply(center, -1)` |
| 버그 효과 | 회전 중심이 `rot·(0, 15)` = (10.61, 10.61)만큼 어긋남. 정사각형에선 안 보임 |
| 실무 습관 | **불변점 테스트** `M @ (cx, cy, 1) == (cx, cy)` |
