## 9-2. 3×3 행렬과 원근 나눗셈

### 9-2-a. 마지막 행을 풀어 준다

Part 6-2-d에서 3×3 어파인 행렬의 마지막 행은 항상 `[0, 0, 1]`이었어요. 원근 변환은 **이 행에도 숫자를 넣어요.**

```
어파인 (3×3)                       원근 (3×3)
┌ a  b  c ┐                        ┌ a  b  c ┐
│ d  e  f │                        │ d  e  f │
└ 0  0  1 ┘  ← 고정                 └ g  h  1 ┘  ← g, h가 새로 생김
```

### 9-2-b. 두 단계 계산

```
① 행렬 곱:
┌ x̃ ┐   ┌ a  b  c ┐ ┌ x ┐        x̃ = a·x + b·y + c
│ ỹ │ = │ d  e  f │ │ y │   →    ỹ = d·x + e·y + f
└ w ┘   └ g  h  1 ┘ └ 1 ┘        w = g·x + h·y + 1      ← 이제 1이 아님!

② 원근 나눗셈 (w로 나누기):
x' = x̃ / w = (a·x + b·y + c) / (g·x + h·y + 1)
y' = ỹ / w = (d·x + e·y + f) / (g·x + h·y + 1)
```

**① 행렬 곱 → ② w로 나눠서 (x', y', 1) 모양으로 되돌리기.** 이게 전부예요.

> 💡 **어파인은 원근의 특수한 경우**예요. `g = h = 0`이면 `w = 1`이 돼서 나눗셈이 아무 일도 안 해요. 그래서 어파인 ⊂ 원근이에요.

### 9-2-c. w의 의미: "이 점은 얼마나 늘릴까"

w는 **점마다 다른 값**이에요. `10`의 실제 행렬에서 네 꼭짓점의 w를 계산하면:

| 원본 점 | 위치 | w | `1/w` (늘리는 배율) |
|---|---|---|---|
| (80, 40) | 왼쪽 위 | 0.895 | 1.12 |
| (75, 300) | 왼쪽 아래 | 1.040 | 0.96 |
| (315, 133) | **오른쪽 위** | **0.575** | **1.74** |
| (335, 300) | **오른쪽 아래** | **0.631** | **1.58** |

**w가 작은 쪽(오른쪽)은 많이 늘어나요.** 원본에서 짧게(멀리) 찍힌 오른쪽 변이 168 → 260으로 늘어나야 했죠(9-1-b). w가 바로 그 **"위치마다 다른 확대율"**을 만들어요. 어파인은 확대율이 **모든 곳에서 같아서**(A 하나) 이걸 못 했어요.

🧠 **비유: 핀홀 카메라.** 사진에서 물체 크기는 **거리에 반비례**해요(`사진 속 크기 = 초점거리 × 실제 크기 / 거리`). 멀리 있는 걸 작게 만드는 연산이 **"거리로 나누기"**예요. 원근 변환의 w는 각 점의 **"상대적인 거리"** 같은 역할을 해요. 그걸로 나눠서 원근감을 만들거나(평면 → 사진), 반대로 원근감을 없애요(사진 → 평면).

### 9-2-d. 📐 왜 하필 "1차식 ÷ 1차식"일까? (평면을 사진으로 찍기)

바닥 같은 **평면** 위의 점을 평면 좌표 `(u, v)`로 나타낼게요. 이 점의 3차원 카메라 좌표 `(X, Y, Z)`는 회전과 이동으로 구해요. 그래서 X, Y, Z가 **각각 u, v의 1차식**이에요.
```
X = r₁·u + r₂·v + t₁
Y = r₄·u + r₅·v + t₂
Z = r₇·u + r₈·v + t₃
```
핀홀 카메라는 사진 좌표를 **Z로 나눠서** 만들어요.
```
x = f·X/Z + cx = (1차식) / (1차식)
y = f·Y/Z + cy = (1차식) / (1차식)
```
정리하면 정확히 **`(a·u + b·v + c) / (g·u + h·v + i)`** 모양이에요. 그래서 **"평면을 어떤 각도에서 찍든, 평면 ↔ 사진의 대응은 항상 3×3 원근 행렬 하나"**예요. 이 행렬을 **호모그래피(homography)**라고 불러요.

> 🚗 **AVM 연결**: 서라운드뷰 탑뷰의 수학적 근거가 바로 이거예요. **바닥(평면)**을 비스듬히 찍은 카메라 영상을 호모그래피의 **역변환**으로 펴면, 위에서 내려다본 탑뷰가 돼요. 단, 어안(fisheye) 렌즈는 직선을 휘게 만들어서 핀홀 모델이 아니에요. 그래서 실무에서는 **렌즈 왜곡을 먼저 펴고 → 호모그래피**를 적용해요. 그리고 이 가정은 **바닥 평면 위의 점에만** 맞아요. 바닥에서 솟은 물체(차, 기둥)는 탑뷰에서 길게 늘어져 보이는데, 그게 이 가정이 깨지는 모습이에요.

### 9-2-e. "동차"의 진짜 의미: 크기 배수는 같은 점

Part 6-2-e에서 예고한 이야기예요. `(x̃, ỹ, w)`와 `(2x̃, 2ỹ, 2w)`는 w로 나누면 **같은 점**이에요.
```
(44.77, 53.72, 0.895)  → (50, 60)
(89.54, 107.44, 1.791) → (50, 60)      ← 전부 2배여도 같은 점
```
그래서 **행렬 M 전체에 2를 곱해도 결과가 똑같아요**(실제 확인: `2M`으로 해도 `(50, 60)`). 행렬 원소는 9개지만 "전체 크기"는 의미가 없으니까, **마지막 원소를 1로 고정**해서 진짜 미지수는 **8개**예요.

## 9-4. `cv2.getPerspectiveTransform` 속 열어 보기

### 9-4-a. 나눗셈이 있는데 어떻게 연립방정식으로 풀까?

```
x' = (a·x + b·y + c) / (g·x + h·y + 1)
```
**양변에 분모를 곱하면** 나눗셈이 사라져요.
```
x'·(g·x + h·y + 1) = a·x + b·y + c
a·x + b·y + c − g·x·x' − h·y·x' = x'          ← 미지수(a~h)에 대해 1차식!
```
y'도 똑같이:
```
d·x + e·y + f − g·x·y' − h·y·y' = y'
```
x, y, x', y'은 **알고 있는 숫자**라서, 미지수 a~h에 대한 **평범한 1차 연립방정식**이 돼요.

### 9-4-b. `10`의 숫자로 8×8 행렬 만들기

점 한 쌍 `(x, y) → (x', y')`마다 두 줄씩:
```
[ x  y  1  0  0  0  −x·x'  −y·x' ]  · [a b c d e f g h]ᵀ  =  x'
[ 0  0  0  x  y  1  −x·y'  −y·y' ]  · [a b c d e f g h]ᵀ  =  y'
```

**첫 번째 쌍 `(80, 40) → (50, 60)`**
```
−x·x' = −80·50 = −4000,   −y·x' = −40·50 = −2000
−x·y' = −80·60 = −4800,   −y·y' = −40·60 = −2400

[ 80  40  1   0   0  0  −4000  −2000 ] = 50
[  0   0  0  80  40  1  −4800  −2400 ] = 60
```

**4쌍 전부 (실제 출력)**
```
       a     b    c    d     e    f       g        h          = 우변
[[    80    40    1    0     0    0    −4000    −2000 ]          50
 [     0     0    0   80    40    1    −4800    −2400 ]          60
 [   315   133    1    0     0    0  −107100   −45220 ]         340
 [     0     0    0  315   133    1   −18900    −7980 ]          60
 [    75   300    1    0     0    0    −3750   −15000 ]          50
 [     0     0    0   75   300    1   −24000   −96000 ]         320
 [   335   300    1    0     0    0  −113900  −102000 ]         340
 [     0     0    0  335   300    1  −107200   −96000 ]]        320
```

### 9-4-c. 풀기

```python
h = np.linalg.solve(A, b)            # 8개 미지수
H = np.append(h, 1).reshape(3, 3)    # 마지막에 1을 붙여 3×3으로
```

**② 행렬 곱 (세 줄)**

**3번 줄을 보세요.** 나누기 전 `(214.7, 202.1)`은 목표 `(340, 320)`과 전혀 달라요. **w = 0.631로 나눠야** 비로소 맞아요. 나눗셈이 빠지면 원근 변환이 아니에요.

## 9-6. `10` 코드의 좌표 계산 해부

```python
ones = np.ones((4,1), np.float64)                     # ① [[1],[1],[1],[1]]
pts3 = np.append(pts1, ones, axis=1)                  # ② 오른쪽에 1 열 붙이기
pts4 = cv2.gemm(pts3, perspect_mat.T, 1, None, 1)     # ③ 행렬 곱
for i in range(len(pts4)):
    pts4[i] /= pts4[i][2]                             # ④ w로 나누기
```

| 줄 | 결과 | 포인트 |
|---|---|---|
| ① | (4, 1) 배열 | |
| ② | `[[80,40,1], [315,133,1], [75,300,1], [335,300,1]]` (4, 3) | float32 + float64 → **float64**로 올라감. `gemm`은 두 행렬의 타입이 같아야 해서 M(float64)과 맞춰져요 |
| ③ | 9-5 표의 `(x̃, ỹ, w)` 4줄 | 아래 설명 |
| ④ | `(x', y', 1)` 4줄 | `pts4[i]` 전체(w 포함)를 w로 나눠서 마지막이 1이 돼요 |

### ③ 왜 `M.T`(전치)를 곱할까?

수식에서는 점을 **세로(열) 벡터**로 써서 `M · p`예요. 그런데 `pts3`는 점 4개를 **가로(행)로** 쌓아 놓은 (4, 3) 배열이에요. 행 벡터로 같은 계산을 하려면 전치를 이용해요.
```
(M · p)ᵀ = pᵀ · Mᵀ           ← 전치의 성질: 곱의 전치는 순서를 뒤집어 각각 전치

pts3 (4×3)  ·  M.T (3×3)  =  결과 (4×3)      ← 행 하나하나가 pᵀ·Mᵀ
```
`cv2.gemm(A, B, alpha, C, beta)`는 `alpha·A·B + beta·C`를 계산하는 함수예요. C가 None이니까 그냥 `pts3 @ M.T`예요. 실제로 두 결과가 똑같아요.

> 💡 **더 간단한 방법**: `cv2.perspectiveTransform(pts1.reshape(-1, 1, 2), M)`을 쓰면 동차 좌표 만들기, 곱하기, **w로 나누기까지 한 번에** 해 줘요. 실제로 `(50,60) (340,60) (50,320) (340,320)`이 바로 나와요. 코드의 주석 처리된 `cv2.transform` 방식은 곱하기만 해 주고 나눗셈은 안 해요.

**중점 실험**: 원본 위쪽 변 `(80,40)–(315,133)`의 중점 `(197.5, 86.5)`를 변환하면:
```
변환된 중점:          (163.42, 60.0)
목적 위쪽 변의 중점:   (195.00, 60.0)        ← 31.6화소 왼쪽으로 치우침
```
같은 직선(y = 60) 위에 있긴 한데 **가운데가 아니에요.** 원본 위쪽 변의 오른쪽 절반은 "멀리" 있어서 짧게 찍혔으니까, 펴면 오른쪽 절반이 더 길게 늘어나요. 그래서 원래의 중점이 왼쪽으로 밀려나요. 사진에서 **멀리 있는 바닥 타일이 촘촘해 보이는 것**과 같은 현상이에요.

### 9-7-a. ⚠️ w = 0이 되는 곳: 무한대로 날아감

w = 0이면 0으로 나누게 돼요. 이번 행렬에서는:
```
w = −0.0015709·x + 0.0005257·y + 1 = 0
→ y = 0일 때 x ≈ 637,   y = 349일 때 x ≈ 753
```
이 직선은 원본 이미지(너비 400) **밖**이라 다행이에요. 그래도 원본 오른쪽 위 모서리 `(399, 0)`은 w = 0.373까지 작아져서 `(650.5, −399.7)`로 **캔버스 밖 멀리** 날아가요. w가 0에 가까울수록 무한히 멀어지는데, 이 **w = 0인 직선이 바로 사진 속의 지평선(소실선)**이에요.

> 🚗 **AVM 연결**: 탑뷰를 만들 때 카메라 영상의 **지평선 근처와 그 위(하늘)는 바닥 평면으로 펼 수 없어요.** w가 0에 가까워져서 무한히 늘어나거든요. 그래서 실무 탑뷰는 차 주변 **몇 미터 이내의 바닥만** 사용하고, 멀리 갈수록 화소가 길게 늘어져 흐려지는(해상도가 떨어지는) 것도 이 1/w 확대 때문이에요.

## 9-8. `cv2.warpPerspective`: 역방향 사상 + 화소마다 나눗셈

### 9-8-a. 내부 동작

Part 6의 `warpAffine`과 같아요. **순방향 행렬을 받아서 내부에서 역행렬을 구하고**, 목적의 모든 화소를 돌면서 원본 위치를 찾아요. 다른 점은 **화소마다 w로 나눈다**는 것 하나예요.

```
M⁻¹ = [[ 1.58064  −0.06626   14.2932 ]
       [ 0.64342   0.93775  −43.76121]
       [ 0.00214  −0.0006     1.04546]]     ← 역행렬도 마지막 행이 [0 0 1]이 아님 → 역방향에도 나눗셈 필요
```

**목적 화소 세 개 따라가기**

| 목적 (x, y) | M⁻¹ · (x, y, 1) = (x̃, ỹ, w) | ÷ w → 원본 위치 | 결과 |
|---|---|---|---|
| (50, 60) | (89.35, 44.67, 1.117) | **(80.00, 40.00)** | pts1[0]과 정확히 일치 ✅ |
| (195, 190) | (309.93, 259.88, 1.350) | **(229.54, 192.47)** | 소수 → 양선형 보간으로 값 계산 |
| (10, 10) | (29.44, −27.95, 1.061) | (27.75, **−26.34**) | 원본 밖 → 검정 (상황 ⓒ) |

결과 크기는 `image.shape[1::-1] = (400, 350)`이에요(Part 0의 컬러 이미지 규칙 그대로).

### 9-8-b. ⚠️ 또 그 버그: `INTER_CUBIC`이 적용되지 않는다

```python
dst = cv2.warpPerspective(image, perspect_mat, image.shape[1::-1], cv2.INTER_CUBIC)
```
`warpPerspective`의 인자 순서도 `(src, M, dsize, dst, flags, ...)`예요. 네 번째 자리는 **`dst`**예요. 실제로 확인하면:
```
위치 인자 INTER_CUBIC 결과 == flags=INTER_LINEAR 결과?  →  True   ← 큐빅이 아니라 양선형!
위치 인자 INTER_CUBIC 결과 == flags=INTER_CUBIC 결과?   →  False
```
**Part 3(`resize`), Part 6(`warpAffine`), Part 8에 이어 네 번째 등장**이에요. 이번에는 큐빅을 의도했는데 실제로는 **양선형**이 쓰였어요. 고치려면 `flags=cv2.INTER_CUBIC`이에요.

### 9-8-c. `INTER_CUBIC`은 무엇인가 (고쳤을 때 적용되는 것)

양선형은 주변 **2×2 = 4화소**를 **직선**으로 이어요. 큐빅은 주변 **4×4 = 16화소**를 **3차 곡선**으로 이어요. 곡선이라 경계가 더 **선명**하게 유지돼요.

대신 **넘침(overshoot)**이 생길 수 있어요. `[0 0 0 255 255 255]`를 2배로 키워 볼게요.
```
float로 계산한 큐빅:  [0  0  0  −8.96  −26.89  57.77  197.23  281.89  263.96  255 255 255]
                                  ↑ 0보다 작음              ↑ 255보다 큼
uint8 큐빅 (잘림):    [0  0  0   0      0      58     197     255     255     255 255 255]
양선형:               [0  0  0   0      0      64     191     255     255     255 255 255]
```
큐빅은 경계 근처에서 **살짝 넘쳤다가 돌아오는** 모양이에요. uint8에서는 0~255로 잘려서 안 보이지만, 회색 배경에서는 경계 주변에 **밝거나 어두운 테두리(링잉)**로 보일 수 있어요. 그래서 Part 3-5에서 본 `clip`이 큐빅에서는 더 중요해요.

## 9-9. 📚 Chapter06 가상광고판 다시 보기

> 그때 이런 코드를 썼어요.
> ```python
> pts_src = np.array([[0, 0], [853, 0], [863, 479], [0, 479]])           # 광고 이미지 네 모서리
> pts_dst = np.array([[232, 100], [606, 92], [602, 352], [236, 316]])    # 사진 속 광고판 네 꼭짓점
> h, status = cv2.findHomography(pts_src, pts_dst)
> im_warp = cv2.warpPerspective(im_src, h, (im_dst.shape[1], im_dst.shape[0]))
> cv2.fillConvexPoly(im_dst, pts_dst.astype(int), (0, 0, 0), cv2.LINE_AA)
> return im_warp + im_dst
> ```

이제 한 줄 한 줄이 무슨 뜻인지 알 수 있어요.

| 줄 | 이제 아는 의미 |
|---|---|
| `findHomography(pts_src, pts_dst)` | **9-4의 8×8 연립방정식 풀기.** 점이 4쌍이면 `getPerspectiveTransform`과 **똑같은 행렬**이에요(9-4-c에서 확인) |
| `h`의 shape (3, 3) | `[[a b c] [d e f] [g h 1]]` |
| `warpPerspective(im_src, h, …)` | 반듯한 광고 이미지를 **사진 속 기울어진 광고판 모양으로 찌그러뜨림** (오늘과 반대 방향: 직사각형 → 사다리꼴) |
| `fillConvexPoly(…, 0)` | 사진에서 광고판 자리를 검정(0)으로 비움 |
| `im_warp + im_dst` | 광고판 밖은 im_warp가 0(검정, 상황 ⓒ)이고 광고판 안은 im_dst가 0이라, **더하면 딱 끼워 맞춰져요** |

**`findHomography`와 `getPerspectiveTransform`의 차이**

| | `getPerspectiveTransform` | `findHomography` |
|---|---|---|
| 점 개수 | **정확히 4쌍** | **4쌍 이상** (수십~수백 쌍) |
| 푸는 방법 | 8×8을 정확히 풀기 | 점이 많으면 **최소제곱**으로 가장 잘 맞는 행렬 |
| 잘못된 점 섞임 | 그대로 망가짐 | `cv2.RANSAC` 옵션으로 **이상한 점을 걸러냄** |
| 두 번째 반환값 | 없음 | `status`: 어느 점이 쓰였는지(1) 버려졌는지(0) |

> 🚗 **AVM 연결**: 실무 캘리브레이션에서는 바닥 체커보드에서 **코너 수십 개**를 자동으로 검출해서 `findHomography`(또는 더 정교한 카메라 모델 최적화)로 풀어요. 검출 오차와 잘못 잡힌 코너가 섞이니까 4점짜리 `getPerspectiveTransform`보다 **많은 점 + RANSAC**이 훨씬 안정적이에요.

|---|---|
| 필요성 | 사진 속 평면은 사다리꼴. 어파인은 평행을 유지해서 못 폄 |
