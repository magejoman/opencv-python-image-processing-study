## 8-12. 🆕 이미지 피라미드: 크기가 다른 얼굴을 찾는 법

### (가) 문제

검출기는 **20×20 얼굴만** 알아봅니다. 그런데 34.jpg의 얼굴은 약 158×158입니다. 사진마다 얼굴 크기도 제각각입니다.

### (나) 해결: 창을 키우는 대신 사진을 줄인다

🧠 **비유: 도장 찍기.** 20×20 크기의 "얼굴 모양 도장"이 하나 있습니다. 큰 얼굴에 도장을 맞추려면 도장을 키울 수도 있지만, OpenCV는 반대로 **사진을 복사기로 점점 축소**하면서 같은 도장을 찍어 봅니다. 사진을 1/7.4로 줄이면 158픽셀 얼굴이 약 21픽셀이 되어 도장에 딱 맞습니다.

```
 단계 k:   0           …           17            …         21           …      30
 배율 f:   1.000                   5.054                   7.400                17.449
          ┌──────────┐            ┌─────┐                 ┌───┐                 ┌┐
          │ 500×349  │            │99×69│                 │68×│                 └┘ 29×20
```

k=31이면 줄인 사진이 26×18이 되어 세로가 20보다 작으므로 **멈춥니다.** 그래서 총 31단계입니다.

### (라) 🔢 한 줄을 손으로 검산: k=21

```
 f       = 1.1^21                      = 7.400
 창 크기 = round(20 × 7.400)           = 148     ← 원본에서 148×148 영역을 보는 셈
 줄인 사진 = round(500/7.4) × round(349/7.4) = 68 × 47
 이동 간격 = f > 2 이므로 1픽셀
 창 수   = (68 − 20 + 1) × (47 − 20 + 1) = 49 × 28 = 1,372
```

**8-B의 무대가 바로 이 단계입니다.** 8-B에서 47×68 이미지를 1픽셀 간격으로 훑었을 때 창이 1,372개였는데, 그 숫자가 이 표의 k=21 줄과 정확히 같습니다.

### (마) 이동 간격(step) 규칙

OpenCV는 **f ≤ 2면 2픽셀, f > 2면 1픽셀** 간격으로 창을 옮깁니다. 작은 배율(사진이 클 때)은 창 수가 너무 많아서 듬성듬성 보는 겁니다. 그래서 k=7(9,520개)에서 k=8(30,816개)로 갈 때 창 수가 오히려 **늘어납니다**.

⚠️ 줄인 사진에서 1픽셀 움직이면 원본에서는 **f픽셀** 움직인 것입니다. k=21이면 약 **7픽셀씩** 건너뛰며 봅니다. 그래서 검출 박스의 위치 정밀도는 대략 ±f/2 픽셀입니다. 아래 8-14의 후보 박스 좌표가 7~8 간격으로 나오는 이유입니다.

## 8-13. minSize의 효과: 계산량 20분의 1

| 설정 | 검사하는 단계 | 검사 창 수 | 실측 시간 (20회 평균) | 결과 |
|---|---|---|---|---|
| minSize (20, 20) | 31단계 전부 | 325,170 | 21.6 ms | `[174, 71, 158, 158]` |
| **minSize (100, 100)** | k=17~30 (14단계) | **15,827** | **8.5 ms** | `[174, 71, 158, 158]` |

결과는 같은데 창 수는 **약 20분의 1**입니다. 작은 단계(k=0~16)일수록 사진이 커서 창이 많기 때문에, 그 부분을 통째로 건너뛰는 효과가 큽니다. 시간이 20배가 아니라 약 2.5배만 줄어든 건 사진 축소, 적분 영상 만들기 같은 고정 비용이 있어서입니다.

**"찾을 얼굴이 대략 어느 크기인지 알면 minSize/maxSize로 범위를 좁혀라."** 이 데이터셋은 얼굴 사진이라 얼굴이 크다는 걸 알고 100으로 잡은 겁니다.

> 🚗 **AVM/ADAS 연결:** 차량 카메라에서 보행자를 찾을 때도 같은 논리를 씁니다. "카메라에서 2~15m 거리의 사람"이라면 화면상 키가 몇 픽셀에서 몇 픽셀까지인지 미리 계산할 수 있고, 그 밖의 크기는 검사하지 않습니다. 고전적인 보행자 검출(HOG+SVM)도 이 **피라미드 + 슬라이딩 윈도우** 구조를 그대로 씁니다.

## 8-15. minNeighbors: 무리를 이룬 후보만 인정

### (가) 1단계: 비슷한 박스끼리 묶기

OpenCV는 두 박스가 "비슷하다"를 이렇게 정의합니다(eps = 0.2).

```
 δ = 0.2 × ( min(w1, w2) + min(h1, h2) ) / 2

 네 변이 모두 δ 이내로 가까우면 비슷함:
   |x1 − x2| ≤ δ,  |y1 − y2| ≤ δ,
   |오른쪽변1 − 오른쪽변2| ≤ δ,  |아랫변1 − 아랫변2| ≤ δ
```

🔢 `[195, 95, 111, 111]`과 `[190, 86, 122, 122]` 비교:
```
 δ = 0.2 × (111 + 111) / 2 = 22.2
 |195 − 190| = 5     ≤ 22.2 ✅
 |95 − 86|   = 9     ≤ 22.2 ✅
 오른쪽변: 306 vs 312 → 6  ✅
 아랫변:   206 vs 208 → 2  ✅   → 비슷함, 같은 무리
```

"A와 B가 비슷하고 B와 C가 비슷하면 A, B, C는 한 무리"로 연결해 나갑니다. 34.jpg의 41개는 서로 사슬처럼 이어져서 **무리 하나(41개)**가 됩니다.

### (나) 2단계: 무리 크기로 거르기

**무리에 속한 박스 수가 minNeighbors보다 많아야**(즉 minNeighbors + 1개 이상) 살아남습니다.

### (다) 3단계: 무리의 평균이 최종 박스

```
 41개의 평균 = (173.80, 70.51, 158.37, 158.37)
 반올림       = [174, 71, 158, 158]   ← detectMultiScale 최종 결과 ✅
```

실측: `cv2.groupRectangles(raw, 2, 0.2)` → `[[174, 71, 158, 158]]`, 무리 크기 `[41]`

**158이라는 크기는 피라미드 어느 단계에도 없는 값**입니다(148과 163 사이). 여러 단계의 후보를 평균 내서 나온 값이라서 그렇습니다.

### (라) 🔢 minSize를 빼면 가짜가 섞여 나옵니다

minSize (20, 20)으로 원시 후보를 보면 **46개**입니다. 얼굴 무리 41개에 더해 **외톨이 5개**가 있습니다.

| 가짜 후보 | 크기 | 무리 크기 |
|---|---|---|
| (321, 18) | 22 | 1 |
| (35, 67) | 29 | 1 |
| (68, 290) | 32 | 1 |
| (14, 251) | 57 | 1 |
| (96, 246) | 84 | 1 |

| minNeighbors | 결과 |
|---|---|
| 0 | 46개 전부 (가짜 5개 포함) |
| **1** | `[[174, 71, 158, 158]]` (외톨이 5개 제거 ✅) |
| 2, 3 | `[[174, 71, 158, 158]]` |

minSize 100일 때는 가짜가 원래 없어서 minNeighbors를 1~10 어떤 값으로 해도 결과가 같았습니다(무리 크기 41이라 40까지 버팀). minNeighbors는 **"가짜를 버리는 안전장치"**이고, 값을 키울수록 엄격해집니다. 너무 크게 잡으면 작거나 흐린 진짜 얼굴(후보가 몇 개 안 모이는 얼굴)까지 버리게 됩니다.

## 8-16. scaleFactor의 트레이드오프

| scaleFactor | 결과 박스 | 실측 시간 |
|---|---|---|
| 1.05 | [176, 73, 154, 154] | 6.1 ms |
| **1.1** | **[174, 71, 158, 158]** | 3.2 ms |
| 1.2 | [174, 73, 156, 156] | 1.7 ms |
| 1.5 | [178, 72, 152, 152] | 1.0 ms |
| 2.0 | [172, 68, 160, 160] | 0.5 ms |

- **작게(1.05)**: 단계가 촘촘해 놓치는 크기가 적지만 단계 수가 약 2배라 느립니다.
- **크게(2.0)**: 단계가 성겨서 빠르지만, 얼굴 크기가 두 단계 사이(예: 도장이 20이나 40에만 맞는데 얼굴이 30)에 걸리면 **놓칠 수 있습니다.** 34.jpg는 얼굴이 크고 선명해서 2.0에서도 찾았지만, 일반적으로는 위험합니다.
- 1.1은 속도와 촘촘함의 **흔한 타협값**입니다.

(위 시간들은 같은 프로세스에서 연달아 잰 값이라 8-13의 측정보다 작게 나왔습니다. 비교는 이 표 안에서만 해 주세요.)

## 8-17. 📚 비교: MediaPipe(Chapter06)와 Haar Cascade

| 고개 돌림·기울기 | 약함 (정면용, 측면은 별도 XML) | 비교적 강함 |

## 🧪 직접 해 볼 실험

```python
import cv2
g = cv2.equalizeHist(cv2.cvtColor(cv2.imread('images/face/34.jpg'), cv2.COLOR_BGR2GRAY))
fc = cv2.CascadeClassifier('haarcascade_frontalface_alt2.xml')
raw = fc.detectMultiScale(g, 1.1, 0, 0, (20, 20))       # 묶기 전 후보 전부
img = cv2.cvtColor(g, cv2.COLOR_GRAY2BGR)
for x, y, w, h in raw:
    cv2.rectangle(img, (x, y, w, h), (0, 255, 0), 1)
for x, y, w, h in fc.detectMultiScale(g, 1.1, 2, 0, (20, 20)):
    cv2.rectangle(img, (x, y, w, h), (0, 0, 255), 3)    # 최종 결과는 굵은 빨강
cv2.imshow('candidates', img); cv2.waitKey(0)
```

## 📝 확인 퀴즈

1. 34.jpg에서 minSize를 (150, 150)으로 하면 검사하는 첫 단계는 k 몇이고, 그때 창 크기는?
2. k=22 단계(f=8.140)에서 줄인 사진의 (10, 5) 위치 창은 원본에서 어느 박스인가요?
3. 후보 박스 무리의 크기가 3이면 minNeighbors가 몇 이하일 때 살아남나요?
4. scaleFactor를 1.0으로 주면 어떻게 될까요?
5. 사진 속 얼굴이 30×30픽셀 정도로 작은데 코드는 minSize (100, 100)입니다. 어떤 일이 일어나나요?

<br>

**정답**
1. 창 크기 = round(20 × f) ≥ 150 → f ≥ 7.5 → **k=22** (f=8.140, 창 **163**). k=21은 148이라 건너뜁니다.
2. 원본 좌표 = 창 위치 × f, 크기 = 163 → (10 × 8.14, 5 × 8.14) ≈ **(81, 41, 163, 163)**
3. 3 > minNeighbors 이어야 하므로 **2 이하**
4. 배율이 영원히 1에 머물러서 피라미드가 끝나지 않습니다. OpenCV는 scaleFactor가 1보다 커야 한다고 검사해서 **에러**를 냅니다.
5. 30픽셀 얼굴에 맞는 단계(k ≈ 4)를 아예 검사하지 않으므로 **"얼굴 미검출"**이 됩니다. minSize는 속도를 주지만 범위 밖의 얼굴은 확실히 놓칩니다.
