## 5-1. 🆕 `canvas = image[:, w*2:image.shape[1]]`: numpy view

### (가) 숫자부터

```python
x, y, w, h = icons[-1]          # 98행: icons[-1]은 이 시점에 무지개 바가 아니라 color 아이콘
                                #       → w = 60
canvas = image[:, w*2:image.shape[1]]
       = image[:, 120:800]
```

실측:
```
w*2           = 120
canvas.shape  = (500, 680, 3)      ← 세로 전체, 가로는 120~799 (680칸)
```

> ⚠️ 이 `w`는 98행에서 `icons[-1]`을 풀었을 때 값입니다. 그 뒤 `icons.append`로 팔레트와 무지개 바가 추가됐지만 `w`는 다시 대입되지 않았으므로 60 그대로입니다. "메뉴 폭 = 아이콘 2개 = w×2"라는 계산입니다.

### (나) 복사본이 아니라 같은 메모리입니다

실측:
```
np.shares_memory(canvas, image)  → True
canvas.base is image             → True     ← canvas의 '주인'이 image
canvas[0,0]의 메모리 주소 == image[0,120]의 메모리 주소 → True
```

🧠 **비유: 같은 땅, 두 개의 주소.** 서울시 지도(image)에 "강남구"라는 이름(canvas)을 붙인 것과 같습니다. 강남구에 건물을 지으면 서울시 지도에도 그 건물이 생깁니다. 땅은 하나이고 부르는 이름만 둘입니다.

```
 image (500 × 800)
 ┌────────┬──────────────────────────────────────────────┐
 │ 메뉴   │                                              │
 │ x 0~119│          canvas = 이 부분을 가리키는 '창문'   │
 │        │          (500 × 680)                         │
 │ (canvas│          canvas[r, c]  ≡  image[r, c + 120]  │
 │  밖)   │                                              │
 └────────┴──────────────────────────────────────────────┘
```

### (다) 메모리 안에서는 어떻게 생겼나: stride

이미지는 메모리에 **한 줄로 쭉** 저장됩니다. stride는 "다음 칸으로 가려면 몇 바이트 건너뛰나"입니다.

실측:
```
image.strides  = (2400, 3, 1)       ← 다음 행: 800×3 = 2400바이트, 다음 열: 3바이트, 다음 채널: 1바이트
canvas.strides = (2400, 3, 1)       ← 똑같음!
canvas.flags['C_CONTIGUOUS'] = False
```

```
 메모리 (한 줄로 펼친 모습)
 행0: [메뉴 360바이트][캔버스 2040바이트] 행1: [메뉴 360][캔버스 2040] 행2: …
       └ 건너뜀 ┘     └── canvas 0행 ──┘       └ 건너뜀┘ └ canvas 1행 ┘
```

canvas의 한 행은 2040바이트(680×3)인데, 다음 행으로 가려면 2400바이트를 건너뛰어야 합니다. 중간의 메뉴 360바이트를 **건너뛰기만** 하고 복사하지 않습니다. 그래서 `C_CONTIGUOUS`(메모리가 빈틈없이 이어짐)가 False입니다. 그래도 OpenCV 함수는 이런 배열을 잘 처리합니다(아래 실측들).

### (라) 왜 굳이 canvas를 만드나

**메뉴는 그대로 두고 그림 영역에만 명령을 적용하려고**입니다. "밝게"를 `image` 전체에 하면 아이콘과 팔레트까지 밝아집니다. `canvas`에 하면 그림만 밝아집니다. 실측: 사진을 연 뒤 메뉴 픽셀 (30,30)은 `[255,255,255]` 그대로였습니다.

## 5-2. 🔢 OPEN: 사진 불러오기

```python
tmp = cv2.imread("images/my_picture.jpg", cv2.IMREAD_COLOR)
cv2.resize(tmp, canvas.shape[1::-1], canvas)
```

### (가) `canvas.shape[1::-1]` 해부

`[시작:끝:간격]` 슬라이싱입니다. `[1::-1]`은 "인덱스 1부터, 끝은 지정 없음(=맨 앞까지), 간격 −1(=거꾸로)"입니다.

```
 canvas.shape     = (500, 680, 3)
 인덱스              0    1    2
 [1::-1] → 인덱스 1부터 거꾸로: 1 → 0
         = (680, 500)                 ← (w, h) = resize가 원하는 dsize 순서!
```

`(높이, 너비, 채널)`에서 채널은 버리고 앞 둘의 순서를 뒤집는 **한 줄짜리 관용구**입니다. Step 1-1의 "numpy는 (h,w), OpenCV 크기는 (w,h)" 문제를 해결합니다. chap11 Part B([haar_utils.py:19](../../chap11/header/haar_utils.py#L19))에도 `image.shape[1::-1]`로 또 나옵니다.

### (나) 세 번째 인자 = `dst` (결과를 담을 그릇)

`cv2.resize(src, dsize, dst)`의 세 번째 위치 인자는 **결과를 써 넣을 배열**입니다. 여기에 view인 `canvas`를 넣었으니 결과가 canvas에 써지고, 따라서 **image에 써집니다.**

🔢 실측:

| 단계 | 값 |
|---|---|
| `tmp.shape` | (480, 640, 3), 640×480 사진 |
| dsize | (680, 500) |
| 실행 후 `image[250, 400]` | `[255,255,255]` → **`[64, 70, 79]`** (사진 픽셀로 바뀜) |
| 실행 후 메뉴 `image[30, 30]` | `[255,255,255]` 그대로 |

### (다) ⚠️ 비슷해 보이지만 동작하지 않는 코드

```python
canvas = cv2.resize(tmp, canvas.shape[1::-1])    # ❌
```

실측: 이렇게 하면 `image[250,400]`은 `[255,255,255]` 그대로입니다. 화면이 안 바뀝니다.

```
 dst로 넘김 (원래 코드)                   = 로 대입 (잘못된 코드)
 ┌─────────┐                             ┌─────────┐
 │ image   │◀── canvas (view)            │ image   │◀── (아무도 안 가리킴, 흰색 그대로)
 │ 사진이  │     resize 결과를             └─────────┘
 │ 써짐 ✅ │     여기에 써 넣음             ┌─────────┐
 └─────────┘                             │새 배열  │◀── canvas (이름표만 옮겨감)
                                         └─────────┘
```

`=`는 **이름표를 새 물건에 옮겨 붙이는** 동작입니다. 원래 땅(image)에는 아무 일도 일어나지 않습니다. Step 3-7의 "대입 vs 내용 수정" 구분과 같은 원리입니다. (이 함수 안에서 `canvas = …`를 하려면 `global canvas`도 필요하지만, 그래도 image는 안 바뀝니다.)

### (라) 덤: 비율이 살짝 늘어납니다

원본은 640/480 = 1.333, 캔버스는 680/500 = 1.360입니다. 가로로 약 2% 늘어나지만 눈으로는 거의 티가 안 납니다.

## 5-4. 🔢 PLUS / MINUS: 밝게·어둡게와 포화 연산

```python
val = np.full(canvas.shape, 10, np.uint8)     # (500, 680, 3) 크기, 전부 10
cv2.add(canvas, val, canvas)                  # canvas = canvas + val  (결과를 canvas에 다시 씀)
cv2.subtract(canvas, val, canvas)             # MINUS
```

세 번째 인자 `canvas`는 5-2와 같은 **dst**입니다. 결과를 제자리에 덮어씁니다.

> ### 📚 복습: uint8 오버플로
> uint8에는 0~255만 들어갑니다. 넘치면 numpy는 **256으로 나눈 나머지**(한 바퀴 돌기)를 쓰고, OpenCV는 **끝에서 멈춥니다**(포화, saturate).

🔢 **실측 비교표:**

| 원래 값 | `cv2.add` +10 | numpy `+` 10 | `cv2.subtract` −10 | numpy `−` 10 |
|---|---|---|---|---|
| 0 | 10 | 10 | **0** | **246** 😱 |
| 5 | 15 | 15 | **0** | **251** 😱 |
| 100 | 110 | 110 | 90 | 90 |
| 245 | 255 | 255 | 235 | 235 |
| 250 | **255** | **4** 😱 | 240 | 240 |
| 255 | **255** | **9** 😱 | 245 | 245 |

numpy로 "밝게"를 하면 하얀 부분(250)이 **새까맣게(4)** 변하고, "어둡게"를 하면 검은 부분(0)이 **새하얗게(246)** 변합니다. 그래서 반드시 `cv2.add` / `cv2.subtract`를 씁니다.

🔢 **실제 사진에 PLUS 한 번 (실측):**

| 위치 (y, x) | 전 BGR | 후 BGR |
|---|---|---|
| (250, 400) | (64, 70, 79) | (74, 80, 89) |
| (100, 300) | (226, 188, 153) | (236, 198, 163) |
| (400, 700) | (26, 37, 29) | (36, 47, 39) |

680×500×3 = 1,020,000개 값 중 **4,193개**는 10보다 덜 올라갔습니다. 이미 246 이상이라 255에서 멈춘 값들입니다.

### ⚠️ 포화는 정보를 지웁니다 (되돌릴 수 없음)

🔢 실측: 값 `[100, 200, 250]`에 PLUS 3번, MINUS 3번

```
 시작       : [100, 200, 250]
 +10 ×3     : [130, 230, 255]     ← 250은 255에서 멈춤 (260, 270, 280이 되어야 했음)
 −10 ×3     : [100, 200, 225]     ← 원래 250이었는데 225로 돌아옴 ❌
```

255에서 멈춘 순간 "원래 얼마였는지"가 사라집니다. 밝게를 많이 누르면 사진의 밝은 부분이 하얗게 날아가고, 어둡게를 눌러도 복구되지 않습니다. 사진 보정에서 말하는 **"하이라이트가 날아갔다"**가 바로 이 현상입니다.

> 💡 **왜 굳이 `val` 행렬을 만드나?** 예전 OpenCV 버전에서는 `cv2.add(img, 10)`처럼 숫자 하나를 넣으면 `(10, 0, 0, 0)`으로 해석돼 **B 채널만** 밝아지는 함정이 있던 것으로 알려져 있습니다. 교재는 이를 피하려고 같은 크기의 행렬을 만든 것으로 보입니다. 지금 설치된 4.12에서 실측하면 `cv2.add(img, 10)`도 세 채널 모두 `100→110`으로 올라갑니다. 버전에 기대지 않으려면 `val` 방식이 가장 확실합니다.

## 5-5. CLEAR: `canvas[:] = …`와 Step 4-7 정정

```python
elif mode == CREAR:
    canvas[:] = (255, 255, 255)
    mouse_mode = 0
```

### (가) `canvas[:] =` vs `canvas =`

| 코드 | 동작 | image가 바뀌나? |
|---|---|---|
| `canvas[:] = (255,255,255)` | canvas가 가리키는 **모든 칸의 내용**을 흰색으로 | ✅ |
| `canvas = (255,255,255)` | 이름표 canvas를 튜플에 옮겨 붙임 | ❌ |

`[:]`는 "전체 칸"이라는 뜻입니다. 5-2 (다)와 같은 원리입니다. `(500, 680, 3)` 배열에 `(3,)`짜리 색을 넣으면 브로드캐스팅으로 모든 픽셀이 흰색이 됩니다.

### (나) 🔧 정정: CLEAR의 `mouse_mode = 0`은 사실 없어도 됩니다

Step 4-7에서 "CLEAR로 지워도 마지막 도형이 되살아나므로 `mouse_mode = 0`이 필요하다"고 설명했습니다. **이번에 시뮬레이션으로 확인해 보니 그 설명은 틀렸습니다.**

🔢 실측 (사각형을 그려 mode=1인 상태에서 CL 아이콘 클릭):

| 단계 | mouse_mode | 캔버스의 도형 픽셀 |
|---|---|---|
| 사각형 확정 직후 | 1 | 1988 |
| CL 아이콘 **DOWN** (30, 330) | **0** ← 여기서 이미 0 | 1988 |
| CL 아이콘 UP → `command(CREAR)` | 0 | **0** (지워짐) |

이유: 메뉴 버튼을 누르는(DOWN) 순간 [C] 블록의 `mouse_mode = 0 if x < 125 else 3`이 먼저 실행됩니다. 메뉴는 x<125이므로 **이미 0**이 됩니다. 마우스로 메뉴를 클릭하는 모든 명령(OPEN, PLUS 등)이 마찬가지입니다. CLEAR 안의 `mouse_mode = 0`은 **결과에 영향 없는 안전장치**입니다.

Step 4-7의 설명 중 **트랙바 쪽은 맞습니다.** 바로 다음에 실측으로 보입니다.

## 5-6. 🔢 트랙바: 선 두께 조절

```python
cv2.createTrackbar("Thickness", "PaintCV", thickness, 255, onTrackbar)

def onTrackbar(value):
    global mouse_mode, thickness
    mouse_mode = 0
    thickness = value
```

> ### 📚 복습: `createTrackbar`
> `cv2.createTrackbar(트랙바 이름, 붙일 창 이름, 초기값, 최대값, 콜백)`
> 슬라이더를 움직일 때마다 OpenCV가 `콜백(현재값)`을 불러줍니다. 최소값은 항상 0입니다.

| 인자 | 값 | 의미 |
|---|---|---|
| 이름 | `"Thickness"` | 슬라이더 옆에 표시되는 글자 |
| 창 | `"PaintCV"` | 메인 창 위쪽에 붙음 |
| 초기값 | `thickness` = 3 | [paint_init.py:22](../../chap11/header/paint_init.py#L22)의 값 |
| 최대값 | 255 | 0~255 |
| 콜백 | `onTrackbar` | 슬라이더가 움직이면 `onTrackbar(새 값)` 호출 |

### (가) 여기의 `mouse_mode = 0`은 꼭 필요합니다

트랙바는 이미지 바깥의 별도 컨트롤이라 **조작해도 `onMouse`가 불리지 않습니다.** CLEAR와 달리 DOWN에서 0으로 초기화되는 일이 없습니다. 그래서 mode 1이 남아 있으면 루프가 마지막 도형을 **새 두께로** 다시 그립니다.

🔢 실측 (사각형 그린 직후 mode=1에서 두께를 3 → 20으로 바꿈):

| 상황 | 캔버스 도형 픽셀 |
|---|---|
| 두께 3으로 확정 | 1988 |
| `mouse_mode = 0` **없이** 두께 20 + 다음 프레임 | **8276** ← 같은 사각형이 굵게 덧그려짐 |
| 실제 `onTrackbar(20)` 호출 후 mode | **0** → 덧그리기 없음 ✅ |

```
 mouse_mode=0 없으면                 실제 코드 (mouse_mode=0)
 ┏━━━━━━━━━━━━━━┓  ← 두께 20으로       ┌──────────────┐  ← 두께 3 그대로
 ┃              ┃     굵어짐          │              │
 ┗━━━━━━━━━━━━━━┛                    └──────────────┘
                                     (다음에 그리는 도형부터 두께 20)
```

### (나) ⚠️ 두께를 0으로 내리면 직선·브러시·지우개가 프로그램을 죽입니다

트랙바 최소값은 0입니다. 두께 0으로 각 함수를 실측해 보면:

| 함수 | 두께 0 결과 |
|---|---|
| `cv2.rectangle` | OK (1픽셀 선) |
| `cv2.circle` | OK |
| `cv2.ellipse` | OK |
| **`cv2.line`** | ❌ **에러**: `0 < thickness && thickness <= MAX_THICKNESS` |

직선, 브러시(0×3=0), 지우개(0×5=0)는 모두 `cv2.line`을 씁니다. 두께 0에서 이 도구로 그리면 메인 루프에서 예외가 나고 **프로그램이 종료됩니다.**

고치는 방법: `thickness = max(1, value)`. 반대로 최대값 쪽은 255×5 = 1275까지 실측해 봤는데 에러가 나지 않았습니다.

## 5-7. 전체 조립 순서: 왜 `canvas`가 함수보다 아래에서 만들어져도 되나

```
  4행  def onMouse(...)            ┐
 29행  def draw(...)               │ 정의만 함 (아직 실행 안 됨)
 58행  def command(...)  ← canvas 사용
 91행  def onTrackbar(...)         ┘
 96행  image = …                   ┐
 97행  icons = place_icons(…)      │
102행  create_colorPlatte / HueIndex│ 위에서 아래로 실행
105행  imshow, setMouseCallback    │
107행  createTrackbar              │
109행  canvas = image[:, 120:800]  │ ← 여기서 비로소 canvas 생성
111행  while True: …               ┘ ← 이후에야 클릭 → command 실행
```

파이썬은 함수 안의 전역 이름을 **함수가 정의될 때가 아니라 실행될 때** 찾습니다. `command`가 처음 실행되는 건 메인 루프에서 사용자가 클릭한 뒤이고, 그때는 109행이 이미 끝나서 `canvas`가 존재합니다. 만약 109행보다 먼저 `command(PLUS)`를 직접 호출하면 `NameError: name 'canvas' is not defined`가 납니다.

## 📝 확인 퀴즈

1. `canvas[10, 20]`은 `image`의 몇 행 몇 열인가요?
2. `image.shape[1::-1]`의 값은?
3. 픽셀 값 3에 `cv2.subtract`로 10을 빼면? numpy로 빼면?
4. `command` 안에서 `canvas = np.full(canvas.shape, 255, np.uint8)`로 지우면 화면이 지워질까요?
5. CLEAR의 `mouse_mode = 0`은 없어도 되는데, 트랙바의 `mouse_mode = 0`은 왜 꼭 필요한가요?

<br>

**정답**
1. `image[10, 140]` (열 +120)
2. `(800, 500)`
3. cv2: **0**, numpy: 3 − 10 = −7 → 256 − 7 = **249**
4. 지워지지 않습니다. 새 배열에 이름만 옮겨 붙이는 것이라 image는 그대로입니다(게다가 `global canvas`가 있으므로 이후로는 canvas가 image와 끊어져서 다른 명령들도 화면에 반영되지 않게 됩니다).
5. 메뉴 클릭은 DOWN 때 [C] 블록이 이미 mode를 0으로 만듭니다. 트랙바는 `onMouse`를 거치지 않으므로 직접 0으로 만들어야 합니다.
