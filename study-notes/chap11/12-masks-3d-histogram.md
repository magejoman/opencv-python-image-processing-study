## 12-1. 박스만으로는 부족한 이유

Step 11-7 그림에서 봤듯이 hair1, hair2 박스 안의 대부분은 **얼굴 피부**입니다. 박스 전체로 히스토그램을 만들면 "피부 vs 피부" 비교가 되어 머리카락 길이와 상관없이 비슷하게 나옵니다.

그래서 **마스크**를 씁니다. 마스크는 영상과 같은 크기의 흑백 영상이고, **0이 아닌 픽셀만** 히스토그램에 셉니다.

> 📚 **복습: Chapter06의 `calcHist`.** `cv2.calcHist([img], [0], None, [256], [0, 256])`에서 세 번째 인자 `None`이 마스크 자리였습니다. 지금까지는 "전체 픽셀을 센다"는 뜻으로 None을 넣었고, 이번에는 여기에 실제 마스크를 넣습니다.

🧠 **비유: 스텐실(구멍 뚫린 판).** 박스는 "이 종이 위에서 작업한다"는 범위이고, 마스크는 그 위에 얹는 **스텐실**입니다. 구멍(255)으로 보이는 픽셀만 셉니다.

## 12-2. `make_masks` 한 줄씩

```python
def draw_ellipse(image, roi, ratio, color, thickness=cv2.FILLED):
    x, y, w, h = roi
    center = (x + w // 2, y + h // 2)
    size = (int(w * ratio), int(h * ratio))
    cv2.ellipse(image, center, size, 0, 0, 360, color, thickness)
    return image

def make_masks(rois, correct_shape):
    base_mask = np.full(correct_shape, 255, np.uint8)                   # ①
    hair_mask = draw_ellipse(base_mask, rois[3], 0.45, 0,  -1)          # ②
    lip_mask = draw_ellipse(np.copy(base_mask), rois[2], 0.45, 255)     # ③
    masks = [hair_mask, hair_mask, lip_mask, ~lip_mask]                 # ④
    masks = [mask[y:y+h,x:x+w] for mask,(x,y, w,h) in zip(masks, rois)] # ⑤
    return masks
```

### ① 전부 흰 판

`np.full((349, 500), 255)` → 174,500픽셀 전부 255.

### ② 얼굴 타원을 검게 칠하기

| 항목 | 계산 | 값 |
|---|---|---|
| 기준 박스 | `rois[3]` = hair | [181, 47, 142, 205] |
| 타원 중심 | (181 + 142//2, 47 + 205//2) | **(252, 149)** |
| 타원 반지름 | (int(142×0.45), int(205×0.45)) | **(63, 92)** |
| 칠하는 색 | 0, 두께 −1 (채우기) | |
| 0이 된 픽셀 | | **18,419개** |

Step 4에서 배운 대로 `cv2.ellipse`의 크기 인자는 **반지름**(반축)입니다. 타원 전체 폭은 126으로 박스 폭 142의 약 90%입니다. 이 타원이 **얼굴 피부 영역**이라는 가정입니다.

⚠️ 여기서 중요한 점: `cv2.ellipse`는 받은 배열에 **직접** 그리고, `draw_ellipse`는 그 배열을 그대로 돌려줍니다. 그래서 실측으로
```
 hair_mask is base_mask  →  True       ← 같은 배열 하나에 이름이 두 개
```
`base_mask`라는 이름과 달리 이제 base_mask에도 타원 구멍이 뚫려 있습니다. 12-3에서 자세히 봅니다.

### ③ 복사본에 입술 타원을 희게 칠하기

| 항목 | 계산 | 값 |
|---|---|---|
| 기준 박스 | `rois[2]` = lip | [221, 181, 63, 31] |
| 타원 중심 | (221 + 31, 181 + 15) | **(252, 196)** |
| 타원 반지름 | (int(63×0.45), int(31×0.45)) | **(28, 13)** |
| 칠하는 색 | 255 (두께 기본값 = 채우기) | |

`np.copy(base_mask)`는 **이미 얼굴 타원이 검게 칠해진** 판의 복사본입니다. 그 위에 입술 타원을 다시 희게 칠하면:
```
 lip_mask:  얼굴 타원 밖 = 255,  얼굴 타원 안 = 0,  그중 입술 타원 = 255
 0인 픽셀 = 18,419 − 1,205 = 17,214개   (얼굴 타원 − 입술 타원)
```

### ④ `~lip_mask`: 뒤집기

`~`는 uint8의 **비트 반전**입니다. 실측: `~[0, 255, 1]` = `[255, 0, 254]`. 0과 255만 있는 마스크에서는 흑백이 정확히 뒤집힙니다. 255가 되는 곳은 **얼굴 타원 안이면서 입술이 아닌 곳 = 피부**이고, 17,214개입니다.

(`~1 = 254`처럼 0/255가 아닌 값은 이상하게 뒤집히므로, `~`는 0/255 마스크에만 쓰세요.)

### ⑤ 박스 크기로 잘라내기, 그리고 최종 결과

| 인덱스 | 마스크 출처 | 자르는 박스 | 255인 픽셀 | 개수 / 박스 넓이 |

## 12-3. ⚠️ "원본 직접 수정"에 기대는 코드

12-2 ②에서 `base_mask`가 몰래 바뀌는 걸 봤습니다. 이걸 보고 "부작용이 있으니 고치자"며 이렇게 바꾸는 사람이 있을 겁니다.

```diff
- hair_mask = draw_ellipse(base_mask, rois[3], 0.45, 0,  -1)
+ hair_mask = draw_ellipse(np.copy(base_mask), rois[3], 0.45, 0,  -1)   # 원본 보호?
```

실측 결과:

| | 원래 코드 | "고친" 코드 |
|---|---|---|
| 마스크별 255 개수 | [5020, 5012, **1205**, **17214**] | [5020, 5012, **1953**, **0**] |
| sim1 (입술-얼굴) | 0.2116 | **1.0** 😱 |
| sim2 (윗-귀밑머리) | 0.4448 | 0.4448 |

무슨 일이 일어났나:
```
 고친 코드:  base_mask = 전부 255 (구멍 없음)
   lip_mask = 복사본(전부 255) + 입술 타원 255  = 전부 255
   ~lip_mask = 전부 0                           ← 피부 마스크가 텅 빔!
   → 피부 히스토그램 전부 0 → 0/0 = NaN → compareHist = 1.0   (Step 11-8과 같은 경로)
```

즉 이 코드는 **②의 부작용 덕분에** ③이 "얼굴 타원 구멍이 뚫린 판"을 복사하게 되고, 그래서 ④의 `~lip_mask`가 피부가 됩니다. 의도했든 아니든 **숨은 부작용에 기대는 코드**이고, 선의의 수정 한 줄이 경고 하나와 함께 조용한 오답을 만듭니다.

### 고치려면 의도를 드러내게

```python
def make_masks(rois, shape):
    face_oval = draw_ellipse(np.zeros(shape, np.uint8), rois[3], 0.45, 255)  # 얼굴 타원 = 255
    lip_oval  = draw_ellipse(np.zeros(shape, np.uint8), rois[2], 0.45, 255)  # 입술 타원 = 255
    hair_mask = cv2.bitwise_not(face_oval)                                  # 얼굴 밖
    skin_mask = cv2.bitwise_and(face_oval, cv2.bitwise_not(lip_oval))       # 얼굴 안 − 입술
    masks = [hair_mask, hair_mask, lip_oval, skin_mask]
    return [m[y:y+h, x:x+w] for m, (x, y, w, h) in zip(masks, rois)]
```
마스크마다 "무엇과 무엇의 조합인지"가 한 줄에 보입니다. Step 5의 view와 복사 이야기와 같은 교훈입니다. **함수가 인자를 직접 바꾸는지 반드시 확인하세요.** OpenCV 그리기 함수(`line`, `circle`, `ellipse`, `rectangle`, `putText`)는 전부 직접 바꿉니다.

## 12-4. 🆕 3차원 색 히스토그램

```python
bsize = (64, 64, 64)
ranges = (0,256, 0,256, 0,256)
hists = [cv2.calcHist([sub], [0,1,2], mask, bsize, ranges) for sub, mask in zip(subs, masks)]
```

### (가) 1차원에서 3차원으로

| | Chapter06 흑백 히스토그램 | 이번 색 히스토그램 |
|---|---|---|
| 채널 | `[0]` 하나 | `[0, 1, 2]` = B, G, R **동시에** |
| 칸 수 | 256 | 64 × 64 × 64 = **262,144** |
| 한 칸의 폭 | 밝기 1 | 각 채널 256 / 64 = **4** |
| 결과 shape | (256, 1) | **(64, 64, 64)** float32 |
| 칸 번호 | 밝기 값 | **(B//4, G//4, R//4)** |

🧠 **비유: 색깔 서랍장.** 가로 64칸(B) × 세로 64칸(G) × 깊이 64칸(R)인 정육면체 서랍장입니다. 픽셀 하나를 꺼내서 색에 맞는 서랍 하나에 구슬을 넣습니다. 다 넣고 나면 "어느 색 조합이 몇 개"인지가 서랍마다 쌓입니다.

### (나) 🔢 픽셀 하나를 직접 넣어 보기 (34.jpg 실측)

| 영역 | 픽셀 (B, G, R) | ÷4 → 서랍 번호 | 그 서랍의 구슬 수 |
|---|---|---|---|
| hair1 | (50, 73, 99) | **(12, 18, 24)** | 13 |
| hair2 | (60, 86, 117) | (15, 21, 29) | 8 |
| 입술 | (178, 160, 203) | (44, 40, 50) | 4 |
| 피부 | (151, 156, 185) | (37, 39, 46) | 20 |

### (다) 각 영역에서 구슬이 가장 많은 서랍

| 영역 | 1등 서랍 | 그 서랍의 BGR 범위 | 구슬 수 | 영역 평균 BGR |
|---|---|---|---|---|
| hair1 | (17, 23, 29) | B 68~71, G 92~95, R 116~119 (갈색) | 38 | (72.9, 89.3, 108.6) |
| hair2 | (3, 5, 7) | B 12~15, G 20~23, R 28~31 (거의 검정) | 57 | (62.8, 80.3, 100.6) |
| 입술 | (31, 37, 48) | B 124~127, G 148~151, R 192~195 | 17 | (133.6, 140.3, **184.2**) |
| 피부 | (40, 43, 50) | B 160~163, G 172~175, R 200~203 | 131 | (128.4, 140.5, 169.2) |

평균으로 보면 입술은 피부보다 R이 15 높고(184.2 vs 169.2), R − G 차이가 43.9 vs 28.7로 더 붉습니다. hair1과 hair2는 둘 다 어두운 갈색 계열이라 평균이 가깝습니다.

### (라) 서랍장은 거의 비어 있다

| 영역 | 센 픽셀 수 (= 히스토그램 합) | 구슬이 든 서랍 | 전체 262,144 중 |
|---|---|---|---|
| hair1 | 5,020 | 952 | 0.36% |
| hair2 | 5,012 | 907 | 0.35% |
| 입술 | 1,205 | 654 | 0.25% |
| 피부 | 17,214 | 2,064 | 0.79% |

히스토그램 합이 정확히 12-2의 마스크 255 개수와 같습니다. 마스크 구멍으로 보이는 픽셀만 셌다는 뜻입니다. 그리고 **서랍의 99% 이상이 비어 있습니다.** 이 "듬성듬성함"이 12-8에서 칸 수에 따라 결과가 크게 흔들리는 원인이 됩니다.

### (마) 왜 B, G, R 히스토그램 3개가 아니라 3차원 하나인가

1차원 3개는 "B가 50인 픽셀이 몇 개, G가 73인 픽셀이 몇 개"를 **따로** 셉니다. 그러면 "B 높고 R 낮은 픽셀(파랑) 절반 + B 낮고 R 높은 픽셀(빨강) 절반"인 영역과 "B와 R이 둘 다 중간인 픽셀(보라)"로 이루어진 영역을 구분할 수 없습니다. 3차원은 **(B, G, R) 조합**을 세므로 실제 "색"을 셉니다.

## 12-5. 정규화: `h / np.sum(h)`

```python
hists = [h/np.sum(h) for h in hists]
```

구슬 수를 전체 구슬 수로 나눠서 **합이 1**이 되게 합니다(실측 합 0.99999988 ~ 1.0, float32 오차). 입술은 1,205픽셀, 피부는 17,214픽셀로 크기가 14배 다르므로 "개수"가 아니라 "비율"로 비교하자는 의도입니다.

그런데 실측해 보면:
```
 정규화한 히스토그램으로 sim1 = 0.211566653768
 정규화 안 한 원본으로  sim1 = 0.211566651471     ← 소수 8자리까지 같음
```

12-6에서 볼 CORREL은 **크기를 몇 배 해도 결과가 같은** 공식이라 이 정규화는 결과에 영향이 없습니다. INTERSECT(교집합) 같은 다른 비교 방법을 쓸 때는 정규화가 꼭 필요하므로, 습관으로 넣어 둔 것이라고 보면 됩니다. 다만 Step 11-8에서 본 것처럼 빈 영역에서는 이 줄이 **0/0 = NaN**을 만듭니다.

## 12-6. 🆕 `HISTCMP_CORREL`: 상관계수

```python
sim1 = cv2.compareHist(hists[2], hists[3], cv2.HISTCMP_CORREL)   # 입술 vs 피부
sim2 = cv2.compareHist(hists[0], hists[1], cv2.HISTCMP_CORREL)   # 윗머리 vs 귀밑머리
```

### (가) 공식: 피어슨 상관계수

```
              Σ (H1[i] − H̄1)(H2[i] − H̄2)
 r  =  ─────────────────────────────────────────        H̄ = 칸 값의 평균 = 합 / 칸 수 N
        √( Σ (H1[i] − H̄1)²  ×  Σ (H2[i] − H̄2)² )
```

- **+1**: 두 히스토그램이 같은 모양 (한쪽이 많은 칸에서 다른 쪽도 많음)
- **0**: 관계없음
- **−1**: 정반대 모양

🧠 **비유: 두 반의 시험 점수.** 과목별 점수를 나란히 놓고 "A반이 잘한 과목에서 B반도 잘했나?"를 보는 것입니다. 평균보다 위/아래인 방향이 같을수록 + 쪽으로 커집니다.

### (나) 🔢 칸 4개짜리 예제로 손 계산

A = [4, 3, 2, 1], B = [3, 4, 1, 2]

| 칸 | A | B | A − 2.5 | B − 2.5 | 곱 | (A−2.5)² | (B−2.5)² |
|---|---|---|---|---|---|---|---|
| 0 | 4 | 3 | 1.5 | 0.5 | 0.75 | 2.25 | 0.25 |
| 1 | 3 | 4 | 0.5 | 1.5 | 0.75 | 0.25 | 2.25 |
| 2 | 2 | 1 | −0.5 | −1.5 | 0.75 | 0.25 | 2.25 |
| 3 | 1 | 2 | −1.5 | −0.5 | 0.75 | 2.25 | 0.25 |
| **합** | | | | | **3.0** | **5.0** | **5.0** |

r = 3.0 / √(5 × 5) = **0.6**. OpenCV 실측도 0.6입니다. 같은 방법으로 A와 [1, 2, 3, 4](정반대)는 **−1.0**, A와 2A = [8, 6, 4, 2]는 **1.0**입니다. 마지막 결과가 12-5에서 "정규화해도 결과가 같다"의 이유입니다. 몇 배를 해도 모양이 같으면 1입니다.

### (다) 34.jpg에 적용하면

손 계산을 쉽게 하려고 공식을 합(Σ)으로 풀어 씁니다(N = 칸 수).
```
 r = (s12 − s1·s2/N) / √( (s11 − s1²/N) · (s22 − s2²/N) )
     s1 = ΣH1,  s2 = ΣH2,  s11 = ΣH1²,  s22 = ΣH2²,  s12 = ΣH1·H2
```

윗머리(H1) vs 귀밑머리(H2), 정규화된 값의 실측 합:
```
 s1 = s2 = 1,   s11 = 0.0024181,   s22 = 0.0025831,   s12 = 0.0012471
```

교과서대로 N = 262,144(전체 칸 수)를 넣으면:
```
 1/N = 0.0000038
 분자 = 0.0012471 − 0.0000038 = 0.0012433
 분모 = √(0.0024143 × 0.0025793) = √(6.227×10⁻⁶) = 0.0024954
 r   = 0.0012433 / 0.0024954 = 0.4982
```

그런데 OpenCV가 돌려준 값은 **0.4448**입니다. 계산이 틀린 게 아닙니다. 다음 12-7에서 원인을 봅니다.

## 12-7. 🔬 숨은 함정: 파이썬이 3차원 히스토그램을 "64채널 2차원"으로 넘긴다

### (가) 실측 비교

| 계산 방법 | sim1 (입술-피부) | sim2 (윗-귀밑머리) |
|---|---|---|
| 코드 그대로 `compareHist(h1, h2)` (64,64,64) | **0.2116** | **0.4448** |
| numpy로 피어슨 직접 계산 (N = 262,144) | 0.2927 | 0.4982 |
| `compareHist(h1.ravel(), h2.ravel())` 1차원으로 펴서 | 0.2927 | 0.4982 |
| 위 손 계산 공식에 **N = 4,096**을 넣으면 | **0.2116** | **0.4448** ✅ |

### (나) 원인

OpenCV-Python은 numpy 배열을 OpenCV 행렬로 바꿀 때 **마지막 축이 작으면(512 이하) 채널로** 해석합니다. 컬러 영상 (349, 500, **3**)이 "349×500, 3채널"이 되는 바로 그 규칙입니다(Step 10-7의 `cv2.transform`과 같은 규칙).

```
 (64, 64, 64) 히스토그램
   → OpenCV가 보는 모습: 64 × 64 행렬, 칸마다 64채널
   → compareHist가 평균을 낼 때 쓰는 N = 행 × 열 = 4,096   (채널은 안 셈)
   → 평균 H̄ = 1/4,096 로 64배 크게 잡힘
```

N = 4,096으로 다시 손 계산:
```
 1/N = 0.0002441
 분자 = 0.0012471 − 0.0002441 = 0.0010030
 분모 = √((0.0024181 − 0.0002441) × (0.0025831 − 0.0002441))
      = √(0.0021740 × 0.0023390) = √(5.085×10⁻⁶) = 0.0022550
 r   = 0.0010030 / 0.0022550 = 0.4448   ← OpenCV 값과 일치
```

### (다) 그럼 고쳐야 하나?

**함부로 고치면 안 됩니다.** Step 13의 판단 기준값 0.2, 0.25, 0.1은 **이 0.2116, 0.4448 같은 값**을 보면서 정한 것입니다. `.ravel()`로 "올바른" 피어슨 값을 쓰면 모든 유사도가 올라가서(0.2116 → 0.2927), 기준값을 그대로 두면 분류 결과가 바뀝니다.

교훈 두 가지:
1. 같은 함수라도 **파이썬에서 배열 모양에 따라** 다른 계산이 될 수 있습니다. 3차원 히스토그램을 비교할 때는 `.ravel()`로 펴서 넘기는 것이 의도대로 동작하는 방법입니다.
2. 기준값(threshold)은 **그 기준값을 정할 때 쓴 계산 방식과 한 몸**입니다. 계산을 바꾸면 기준값도 다시 맞춰야 합니다.

## 12-8. 칸 수(64)는 결과를 얼마나 흔드나

같은 34.jpg, 같은 마스크로 칸 수만 바꿨습니다.

| 채널당 칸 수 | 전체 칸 | sim1 (입술-피부) 코드 / 피어슨 | sim2 (윗-귀밑머리) 코드 / 피어슨 |
|---|---|---|---|
| **64** (코드) | 262,144 | **0.2116** / 0.2927 | **0.4448** / 0.4982 |
| 32 | 32,768 | 0.3234 / 0.3853 | 0.6224 / 0.6548 |
| 16 | 4,096 | 0.4784 / 0.5299 | 0.7721 / 0.7939 |
| 8 | 512 | 0.6754 / 0.7228 | 0.7557 / 0.7925 |
| 4 | 64 | **0.9043** / 0.9270 | 0.7246 / 0.7943 |

- **칸이 촘촘하면(64)** 서랍이 99% 비어 있습니다(12-4 라). 색이 밝기 4만큼만 달라도 다른 서랍에 들어가서 "겹치는 서랍"이 적고, 유사도가 낮게 나옵니다. 실측으로 hair1과 hair2는 구슬이 든 서랍 952개, 907개 중 **같이 든 서랍이 563개**뿐이고, 입술(654개)과 피부(2,064개)는 **241개**만 겹칩니다.
- **칸이 성기면(4)** 비슷한 색이 전부 같은 서랍에 들어가서 입술과 피부마저 0.90으로 "거의 같다"가 됩니다. 구분 능력이 사라집니다.

Chapter06에서 히스토그램 칸 수를 고를 때와 같은 트레이드오프입니다. 그리고 12-7과 같은 결론으로 이어집니다. **Step 13의 기준값은 64칸 전용**입니다.

> 🚗 **AVM 연결:** 서라운드 뷰는 카메라 4대의 영상을 이어 붙이는데, 카메라마다 노출이 달라서 이음새에 밝기 차이가 생깁니다. 그래서 **인접한 두 카메라가 같이 보는 겹침 영역**의 색 통계(평균, 히스토그램)를 비교해서 카메라별 밝기 보정값을 계산합니다. 여기서도 마스크로 "겹침 영역 중 바닥 픽셀만" 골라 비교하는 것이 핵심이고, 칸 수와 비교 방법에 따라 결과가 흔들리는 문제도 똑같이 생깁니다.
