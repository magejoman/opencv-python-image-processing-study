# 부록: YUV422와 RGBA 다루기 (업무용 보충)

chap06 Part 6의 YUV(공식)와 Part 3의 알파 합성(개념)을, **업무에서 쓰는 두 포맷 기준**으로 다시 정리한 문서예요.
Part 6은 변환 공식만 다뤘고 **메모리 배치, 레인지, 알파 처리**는 다루지 않아서 여기서 채워요.

> 모든 숫자와 코드는 NumPy 2.1.2, OpenCV 4.12.0에서 실제로 돌려서 확인했어요.
> 확인하지 못한 내용은 "(미확인)"이라고 표시했어요.

## 0. 먼저 알아 둘 것

| 항목 | 한 줄 요약 |
|---|---|
| YUV422 | 화소 **두 개가 색(U, V)을 하나씩 공유**. 화소당 2바이트. OpenCV에서는 **`(H, W, 2)`** uint8 배열 |
| 순서 | **YUYV / UYVY / YVYU**가 있고, 틀리면 색이 완전히 깨져요 |
| 레인지 | `cv2.COLOR_YUV2BGR_YUY2`는 **리미티드(Y 16~235)**로 해석. Part 6의 `BGR2YUV`는 **풀(0~255)** → **짝이 안 맞아요** |
| RGBA | 화소당 4바이트. `cv2`는 BGRA 순서. **straight**와 **premultiplied** 두 종류가 있고 합성 공식이 달라요 |
| `BGRA2BGR` | 알파를 **버릴 뿐** 배경과 합성하지 않아요 |

## 1. YUV422: 메모리 구조

### 1-1. 왜 422인가 (Part 6 Step G 복습)

> 📚 **복습**: 이미지 정보 대부분은 밝기(Y)에 있고, 사람 눈은 색 변화에 둔감해요. 그래서 색차(U, V)를 줄여서 저장해도 눈에 잘 안 띄어요.

| 포맷 | 의미 | 바이트/화소 | 1280×720 | 1920×1080 |
|---|---|---:|---:|---:|
| YUV444 / RGB | 화소마다 Y, U, V 전부 | 3.0 | 2.76 MB | 6.22 MB |
| **RGBA** | R, G, B, A | **4.0** | **3.69 MB** | **8.29 MB** |
| **YUV422** | 가로로 **2화소가 U, V 공유** | **2.0** | **1.84 MB** | **4.15 MB** |
| YUV420 | 가로·세로 2×2화소가 U, V 공유 | 1.5 | 1.38 MB | 3.11 MB |

**YUV422는 RGBA의 절반 크기**예요. 카메라에서 메모리로 옮기는 대역폭 때문에 422를 쓰는 경우가 많아요.

### 1-2. 바이트 배치: YUYV

화소 4개(P0~P3)를 저장할 때 이래요.

```
화소:        P0     P1     P2     P3
Y 값:        Y0     Y1     Y2     Y3          ← 화소마다 따로
U, V 값:     └─U01,V01─┘   └─U23,V23─┘          ← 두 화소가 하나를 공유

메모리 (YUYV, 8바이트):
  [ Y0 | U01 | Y1 | V01 | Y2 | U23 | Y3 | V23 ]
    └── P0, P1 ──┘      └── P2, P3 ──┘
     2화소 = 4바이트 = 화소당 2바이트
```

세 가지 순서는 이래요.

| 이름 | 바이트 순서 | OpenCV 변환 코드 |
|---|---|---|
| **YUYV** (= YUY2) | Y0 U Y1 V | `cv2.COLOR_YUV2BGR_YUY2` |
| **UYVY** | U Y0 V Y1 | `cv2.COLOR_YUV2BGR_UYVY` |
| **YVYU** | Y0 V Y1 U | `cv2.COLOR_YUV2BGR_YVYU` |

### 1-3. OpenCV에서의 모양: `(H, W, 2)`

```python
frame.shape   # (H, W, 2)   ← 마지막 축 2개 = [Y, (U 또는 V)]
frame[..., 0] # Y 평면, 화소마다 하나 (YUYV 기준. UYVY는 [U,Y0],[V,Y1]이라 Y가 frame[..., 1])
frame[..., 1] # U, V가 번갈아: 짝수 열은 U, 홀수 열은 V
```

```
frame[y, 0] = [Y0, U01]
frame[y, 1] = [Y1, V01]
frame[y, 2] = [Y2, U23]
frame[y, 3] = [Y3, V23]       ← 둘째 채널은 열마다 U, V가 번갈아 나옴
```

- **Y만 필요하면** 변환 없이 `frame[..., 0]`을 쓰면 돼요 (실측: `COLOR_YUV2GRAY_YUY2` 결과와 같아요).
- **주의**: `(H, 2W)`처럼 **1채널로 펴서** `cvtColor`에 넣으면 에러가 나요 (실측: `color.simd_helpers.hpp` 에러). 반드시 `(H, W, 2)`로 `reshape`해야 해요.

### 1-4. 버퍼를 읽어서 BGR로 바꾸기

```python
YUV422_CODES = {
    "YUYV": cv2.COLOR_YUV2BGR_YUY2,   # Y0 U  Y1 V
    "UYVY": cv2.COLOR_YUV2BGR_UYVY,   # U  Y0 V  Y1
    "YVYU": cv2.COLOR_YUV2BGR_YVYU,   # Y0 V  Y1 U
}

def decode_yuv422(raw, w, h, fmt="YUYV", stride=None):
    """raw: bytes 또는 1차원 uint8. stride: 한 줄의 바이트 수(패딩 포함). 없으면 w*2."""
    stride = stride or w * 2
    buf = np.frombuffer(raw, np.uint8)[: h * stride].reshape(h, stride)
    frame = buf[:, : w * 2].reshape(h, w, 2)          # 패딩 제거 → (h, w, 2)
    return cv2.cvtColor(frame, YUV422_CODES[fmt])
```

이 함수를 실제로 돌려서 확인했어요 (YUYV, UYVY 모두 순수 빨강 `[0, 1, 255]`로 복원).

### 1-5. ⚠️ 함정 ①: 순서를 틀리면 색이 깨져요

같은 바이트를 순서만 다르게 해석한 결과예요 (실측, 원래 색은 빨강/빨강/초록/연두).

| 해석 | 복원된 BGR (앞 두 화소) |
|---|---|
| 올바름 (YUYV) | 빨강 계열 정상 |
| UYVY로 잘못 읽음 | `[0, 151, 3]`, `[173, 255, 194]` ← 초록, 하늘색 등 **엉뚱한 색** |
| YVYU로 잘못 읽음 | `[255, 50, 11]` ← U와 V가 뒤바뀌어 **빨강이 파랑**으로 |

> 색이 이상하면 **먼저 순서(YUYV/UYVY/YVYU)**를 의심하세요. 파랑과 빨강이 뒤바뀌어 보이면 YVYU(U와 V 교환)나 BGR/RGB 혼동이에요.

### 1-6. ⚠️ 함정 ②: 스트라이드(줄 패딩)

카메라나 드라이버가 주는 버퍼는 **한 줄이 `W×2` 바이트보다 길 수** 있어요 (정렬 때문에 뒤에 패딩이 붙어요).

```
줄 0: [ W*2 바이트 데이터 ][ 패딩 ]   ← stride 바이트
줄 1: [ W*2 바이트 데이터 ][ 패딩 ]
```

패딩을 무시하고 `reshape(h, w, 2)`를 하면 **줄이 밀려서** 두 번째 줄부터 색이 깨져요. 실측으로 확인했어요 (`W=6`, `stride=16`).

| 방법 | 둘째 줄 복원 결과 |
|---|---|
| 패딩 무시하고 그냥 `reshape` ❌ | `[0, 132, 0]` ← 엉뚱한 초록 |
| `reshape(h, stride)` 후 `[:, :w*2]` ✅ | `[0, 1, 255]` ← 정상 |

`decode_yuv422`의 `stride` 인자가 이걸 처리해요. 실제 stride는 드라이버/카메라 API가 알려 주는 값을 쓰세요.

## 2. YUV의 레인지: 풀 vs 리미티드

### 2-1. 개념

| | 풀 레인지 (full) | 리미티드 레인지 (limited, studio) |
|---|---|---|
| Y 범위 | 0 ~ 255 | **16 ~ 235** |
| U, V 범위 | 0 ~ 255 | 16 ~ 240 |
| 검정 | Y = 0 | **Y = 16** |
| 흰색 | Y = 255 | **Y = 235** |
| 흔한 곳 | JPEG, 일부 카메라 | TV/영상 규격, 많은 카메라와 비디오 인코더 |

리미티드는 **위아래에 여유**(0~15, 236~255)를 남겨 둔 거예요. 신호가 살짝 튀어도 잘리지 않게 하려는 옛 방송 규격의 흔적이에요.

### 2-2. ⚠️ 함정 ③: OpenCV의 두 변환은 레인지가 달라요

실측 결과예요.

| 변환 | 흰색(255) → Y | 검정(0) → Y | 방식 |
|---|---:|---:|---|
| `cv2.COLOR_BGR2YUV` (Part 6에서 쓴 것) | **255** | **0** | **풀** |
| 리미티드 BT.601 공식으로 계산 | **235** | **16** | 리미티드 |
| `cv2.COLOR_YUV2BGR_YUY2`로 **복원** | Y=235 → **255** | Y=16 → **0** | **리미티드로 해석** |

Y에 같은 값을 넣고 복원한 결과예요 (U=V=128, 회색).

| Y | 0 | 16 | 128 | 235 | 255 |
|---|---:|---:|---:|---:|---:|
| 복원된 BGR | 0 | **0** | **130** | **255** | 255 |

- Y = 0과 Y = 16이 **둘 다 검정**이에요 (하위 16단계가 뭉개져요).
- Y = 235와 255가 **둘 다 흰색**이에요.
- Y = 128은 128이 아니라 **130**이에요. `(128 − 16) × 255/219 = 130.4`.

즉 **`BGR2YUV`(풀)로 만든 YUV를 `YUV2BGR_YUY2`(리미티드 해석)로 복원하면** 색이 틀어져요 (실측: 순수 초록이 `[7, 255, 0]`, 순수 파랑이 `[239, 0, 0]`).

> 회사 카메라가 만드는 YUV가 리미티드일 가능성이 높지만, **제 추측이에요**. 반드시 확인하세요.
>
> ```python
> y = frame[..., 0]            # YUYV 기준
> print(y.min(), y.max())      # 어둡고 밝은 장면을 같이 찍었을 때
> ```
> 리미티드면 **min이 16 근처, max가 235 근처**에서 멈춰요. 0과 255까지 가면 풀이에요.
> 풀 YUV를 OpenCV로 복원하면 대비가 약간 늘고 어둡고 밝은 끝이 뭉개져요.

### 2-3. 행렬은 BT.601이에요 (BT.709는 미확인)

리미티드 BT.601 공식으로 직접 인코딩 → 422로 줄이기 → `YUV2BGR_YUY2`로 복원했더니, **색 경계가 화소 쌍에 맞춰진 이미지(3-2의 첫 행)에서 오차가 최대 1**이었어요. 즉 이 변환은 **BT.601 + 리미티드**예요.

`cvtColor`에는 행렬을 고르는 인자가 없어요 (`cvtColor(src, code, dst, dstCn)`).
HD 카메라가 BT.709로 인코딩한다면 색이 조금 틀어질 수 있어요 (**이 세션에서 BT.709는 확인하지 않았어요**). 그 경우에는 소스의 규격을 확인하고, 직접 행렬을 곱해야 할 수 있어요.

## 3. 422의 색 해상도 한계

### 3-1. 색이 **가로로 절반**이에요

Y는 화소마다 있지만 U, V는 **두 화소에 하나**예요. 그래서 **두 화소 사이에서 색이 바뀌는 경계**는 정확히 표현할 수 없어요.

### 3-2. 실험: 빨강 | 파랑 경계

가로 16화소 이미지의 왼쪽 8칸은 빨강, 오른쪽 8칸은 파랑이에요. 리미티드 BT.601로 422로 줄였다가 복원했어요.

| 경계 위치 | 최대 오차 | 평균 오차 | 복원 결과 (x = 5 ~ 10) |
|---|---:|---:|---|
| **화소 쌍의 경계와 일치** (7 / 8 사이) | **1** | 0.50 | 빨강 3칸, 파랑 3칸 ✅ |
| **화소 쌍 안쪽** (x = 7이 파랑, 6이 빨강) | **151** | 19.25 | `[0,1,255]`, **`[151,24,152]`**, **`[104,0,104]`**, `[255,0,0]` ❌ |

```
경계가 쌍 안쪽에 있을 때:   P6(빨강) P7(파랑)  ← 둘이 U, V를 공유
                           색차가 평균돼서 → 자주색 두 화소 [151,24,152], [104,0,104]
```

- **색이 같은 영역이나 완만한 그라데이션**에서는 오차가 거의 없어요.
- **글자, 얇은 색 선, 색이 급변하는 경계**에서는 **자주색 번짐(색 번짐, fringing)**이 생겨요.
- 주차선(흰색/노랑 선)처럼 **얇은 색 선**은 422를 거치면 색이 흐려질 수 있어요 (추정. 주차선 이미지로 직접 확인하지는 않았어요).

### 3-3. OpenCV가 색을 늘리는 방법

두 화소가 한 쌍의 U, V를 **그대로 복사**해서 써요 (실측: 같은 쌍의 두 화소는 복원된 BGR이 **완전히 같아요**). 보간(부드럽게 섞기)은 하지 않아요.

## 4. RGBA: 알파 채널 다루기

### 4-1. 채널 순서와 메모리

```python
fg.shape          # (H, W, 4)
fg[y, x]          # OpenCV 기본은 [B, G, R, A]
```

| 변환 | 코드 |
|---|---|
| BGRA ↔ RGBA | `cv2.COLOR_BGRA2RGBA`, `cv2.COLOR_RGBA2BGRA` |
| BGRA → BGR (알파 **제거**) | `cv2.COLOR_BGRA2BGR` |
| BGR → BGRA (알파 255 추가) | `cv2.COLOR_BGR2BGRA` |

`BGRA → RGBA`로 바꾸면 화소가 `[255,128,0,128]` → `[0,128,255,128]`이 되고, 메모리에는 **R, G, B, A 순서의 바이트**로 놓여요 (실측으로 확인). 파랑과 빨강이 뒤바뀌어 보이면 BGRA/RGBA 혼동이에요.

### 4-2. ⭐ straight vs premultiplied

| | straight (비-premultiplied) | premultiplied |
|---|---|---|
| 저장된 색 | **원래 색 그대로** | **색 × 알파**가 이미 곱해짐 |
| 합성 공식 | `out = a·F + (1−a)·B` | `out = F' + (1−a)·B` |
| 투명(a=0) 화소의 색 | 아무 색이나 가능 | 항상 (0, 0, 0) |
| 단서 | | **모든 색 채널이 알파 이하** (`R,G,B ≤ A`) |

(a = A/255, F = 전경 색, F' = a·F, B = 배경 색)

실측 예: 전경 `F = (255,128,0)`, 알파 128, 배경 `B = (40,80,200)`.

| 데이터 | 사용한 공식 | 결과 BGR |
|---|---|---|
| straight | straight 공식 ✅ | **[148, 104, 100]** |
| premultiplied | premultiplied 공식 ✅ | **[148, 104, 100]** (같음) |
| premultiplied | **straight 공식** ❌ | **[84, 72, 100]** (너무 어두움) |

공식을 잘못 고르면 **반투명 가장자리가 어둡게 변해요** (알파가 두 번 곱해지기 때문이에요). 검정 테두리나 어두운 후광(halo)이 보이면 이걸 의심하세요.

### 4-3. 합성 코드

```python
def blend_straight(bg_bgr, fg_bgra):
    """straight(비-premultiplied) 알파 합성. 결과 uint8 BGR."""
    a = fg_bgra[..., 3:4].astype(np.float32) / 255
    out = fg_bgra[..., :3] * a + bg_bgr * (1 - a)
    return np.clip(np.round(out), 0, 255).astype(np.uint8)

def blend_premultiplied(bg_bgr, fg_bgra):
    """premultiplied 알파 합성: 전경 색에 이미 알파가 곱해져 있음."""
    a = fg_bgra[..., 3:4].astype(np.float32) / 255
    out = fg_bgra[..., :3] + bg_bgr * (1 - a)
    return np.clip(np.round(out), 0, 255).astype(np.uint8)
```

- `fg_bgra[..., 3:4]`처럼 **`3:4`로 잘라서 차원을 `(H, W, 1)`로 유지**해야 `(H, W, 3)` 색과 브로드캐스팅돼요. `fg_bgra[..., 3]`은 `(H, W)`라서 안 맞아요.
- 알파가 0, 128, 255인 화소 세 개로 실행해 확인했어요 → 배경 그대로 / 반반 섞임 / 전경 그대로.
- `addWeighted`는 **이미지 전체에 같은 알파 하나**만 쓸 수 있어서, 화소마다 알파가 다른 RGBA 합성에는 못 써요.

### 4-4. ⚠️ RGBA 함정 모음

| # | 함정 | 실측 |
|---|---|---|
| ① | **uint8로 곱하면 오버플로**. `fg * a`가 uint8끼리 곱해져 한 바퀴 돌아요 (Part 3) | uint8로 계산한 합성 결과가 `[0,0,0]` **전부 0** (완전히 깨짐) |
| ② | **`BGRA2BGR`은 합성이 아니라 알파 제거** | 알파 0인(완전 투명) 화소가 **원래 색 `[255,128,0]` 그대로** 남음 |
| ③ | **`cv2.imread` 기본값은 알파를 버려요** | 기본 → `(2,3,3)`, `cv2.IMREAD_UNCHANGED` → `(2,3,4)` |
| ④ | **JPG는 알파를 저장하지 못해요** | PNG는 알파 `[0,128,255]` 보존, JPG는 다시 읽으면 `(2,3,3)` |
| ⑤ | **반올림 차이** | `cv2.multiply(200, 128, scale=1/255)` = **100**, 실수 계산은 100.4 |

① 때문에 합성은 **float32로 올려서 계산한 뒤 `clip` → `astype(uint8)`**로 돌려놓는 게 안전해요 (Part 3의 "더 큰 상자" 규칙과 같아요).

## 6. 문제가 생겼을 때 확인 순서

### YUV422 색이 이상할 때

1. **순서**: YUYV / UYVY / YVYU를 바꿔 가며 보기 (파랑↔빨강이 뒤바뀌면 YVYU 의심)
2. **모양**: `(H, W, 2)`인가? 1채널로 펴서 넣지 않았나?
3. **스트라이드**: 한 줄이 `W×2` 바이트보다 길지 않나? (둘째 줄부터 색이 깨지면 의심)
4. **레인지**: `frame[..., 0]`의 min/max가 16~235인가, 0~255인가? (명암이 이상하면 의심)
5. **행렬**: 소스가 BT.601인가 709인가? (**미확인**, 색조가 살짝 틀어지면 의심)
6. **경계 번짐**: 얇은 색 선, 글자 주변의 자주색 번짐은 **422의 한계**이지 버그가 아니에요

### RGBA 합성이 이상할 때

1. **채널 순서**: BGRA인가 RGBA인가?
2. **straight vs premultiplied**: 모든 색 채널이 알파 이하인가? 가장자리가 어두우면 premultiplied 데이터에 straight 공식을 쓴 거예요
3. **오버플로**: uint8끼리 곱하지 않았나? (float32로 올리세요)
4. **알파 소실**: `imread`에 `IMREAD_UNCHANGED`를 줬나? JPG로 저장하지 않았나?
5. **합성 착각**: `BGRA2BGR`이 합성해 준다고 생각하지 않았나?

## 7. 업무와 이어지는 지점 (추정)

> 아래는 제가 기억하는 업무 맥락(AVM, 서라운드 뷰)을 바탕으로 한 **추정**이에요. 실제 파이프라인과 다를 수 있어요.

- **카메라 입력이 YUV422**라면, 보정과 탑뷰 변환 전에 `(H, W, 2)`에서 **Y만 뽑아** 밝기 분석(히스토그램, 노출 비교)을 하면 변환 비용을 아낄 수 있어요 (`frame[..., 0]`).
- **카메라 영상을 이어 붙이는 경계(겹치는 영역) 블렌딩**은 화소마다 가중치가 다른 알파 마스크 합성이에요. 4-3의 `blend_straight` 구조 그대로예요.
- **GUI 오버레이(주차선 가이드 등)가 RGBA**라면, 그래픽 쪽 파이프라인은 premultiplied를 쓰는 경우가 많아요 (일반 지식, **이 환경에서 확인하지 않았어요**). 오버레이가 어느 쪽인지 먼저 확인하세요.
