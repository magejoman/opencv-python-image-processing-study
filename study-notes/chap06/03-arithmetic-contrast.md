## 3-0. 📚 복습 두 가지

**① uint8은 8비트 상자예요**

```
비트 8개 = 2⁸ = 256가지 → 0 ~ 255
0000 0000 = 0
1111 1111 = 255
1 0000 0000 = 256 ← 9번째 자리가 필요하지만 상자에는 8칸뿐
```

**② 알파 블렌딩 (reference 02, 03번)**

reference에서 반투명 박스를 그릴 때 이 식을 썼었죠.

$$\text{결과} = \alpha \cdot A + (1-\alpha) \cdot B$$

α=0.3이면 A를 30%, B를 70% 섞어요. 그때는 `arr.astype(np.float64)`로 바꿔서 계산한 다음 `.clip(0, 255).astype(np.uint8)`로 되돌렸어요. **이번 Part에서 그렇게 해야 했던 이유**를 정확히 알게 될 거예요.

## 3-1. ⭐ 범위를 넘으면 어떻게 될까: 두 가지 규칙

`200 + 100 = 300`인데 상자에는 255까지만 들어가요. 처리하는 방법이 두 가지 있어요.

### 규칙 A: 포화(Saturation), 물컵 방식 (OpenCV)

```
     넘치면 가득 찬 채로 멈춤             모자라면 빈 채로 멈춤
   ┌─────┐                            ┌─────┐
   │~~~~~│ ← 255에서 끝 (넘친 건 버림)    │     │
   │█████│                            │     │ ← 0에서 끝
   │█████│                            │     │
   └─────┘                            └─────┘
   200+100 → 255                      50-100 → 0
```

$$y = \min(\max(x + k,\ 0),\ 255)$$

### 규칙 B: 모듈로(Modulo), 주행거리계 방식 (numpy)

```
 자동차 주행거리계가 999999 다음에 000000 이 되듯이

    ... 253 → 254 → 255 → 0 → 1 → 2 ...   (원형으로 이어짐)

          255  0
       254 ╭───╮ 1
          │     │
       ...│     │...           200+100 = 300 → 300 - 256 = 44
          ╰───╯              50-100 = -50 → -50 + 256 = 206
```

$$y = (x + k) \bmod 256$$

수학적으로 보면 9번째 비트가 그냥 **잘려 나가는** 거예요.

```
200 = 1100 1000
100 = 0110 0100
합  = 1 0010 1100  (= 300)
      ↑ 이 비트는 상자에 못 들어감 → 버림
결과 =   0010 1100  = 44
```

### 왜 둘이 다를까?

- **numpy**는 범용 수학 라이브러리예요. CPU의 정수 덧셈이 원래 이렇게 동작하니까 그대로 따라요 (빠르고 단순해요).
- **OpenCV**는 영상 전용 라이브러리예요. 밝게 했는데 갑자기 검게 되면 말이 안 되니까 일부러 `saturate_cast`라는 포화 처리를 넣었어요.

## 3-2. `04.bright_dark.py`: 밝게, 어둡게

### Step A. 코드

```python
dst1 = cv2.add(image, 200)        # OpenCV: +200, 포화
dst2 = cv2.subtract(image, 200)   # OpenCV: -200, 포화
dst3 = image + 100                # numpy:  +100, 모듈로
dst4 = image - 100                # numpy:  -100, 모듈로
```

⚠️ 눈여겨볼 점: **OpenCV 쪽은 200, numpy 쪽은 100**으로 더하는 양이 달라요. 공정한 비교는 아니지만, 각 규칙의 특징은 잘 보여줘요.

### Step B. 값 하나씩 추적 (실측)

| 원래 x | `cv2.add(x,200)` | `cv2.subtract(x,200)` | `x + 100` | `x - 100` |
|---:|---:|---:|---:|---:|
| 0 | 200 | 0 | 100 | **156** ⚠️ |
| 30 | 230 | 0 | 130 | **186** ⚠️ |
| 55 | **255** (딱 맞음) | 0 | 155 | 211 ⚠️ |
| 56 | 255 (256→멈춤) | 0 | 156 | 212 ⚠️ |
| 100 | 255 | 0 | 200 | 0 |
| 155 | 255 | 0 | **255** | 55 |
| 156 | 255 | 0 | **0** ⚠️ (256→0) | 56 |
| 200 | 255 | 0 | **44** ⚠️ | 100 |
| 255 | 255 | 55 | **99** ⚠️ | 155 |

⚠️ 표시가 한 바퀴 돈 값이에요. 예를 들어 `x - 100`에서 x=0은 −100 → −100 + 256 = **156**이 돼요. 가장 어두운 검정이 밝은 회색으로 바뀐 거예요.

### Step C. 변환 곡선으로 보면

```
cv2.add(x, 200)              x + 100 (numpy)
 y                            y
255┤  ───────────────        255┤          ╱│
   │ ╱                          │        ╱  │      ╱  ← 156부터 0으로 추락 후
200┤╱                           │      ╱    │    ╱      다시 올라감
   │                         100┤    ╱      │  ╱
  0┼────────────── x            │  ╱        │╱
   0  55          255          0┼──────────┴────── x
                                0         155 156  255
 x≥55 는 전부 255 로 하얗게      톱니 모양 → 밝던 곳이 갑자기 어두워짐
```

### Step D. 이미지 전체에서는 얼마나? (`bright.jpg`, 평균 밝기 144.0)

| 결과 | 실측 |
|---|---|
| `cv2.add(+200)`에서 255로 포화된 화소 | **85.0%** → 거의 새하얀 이미지 |
| `cv2.subtract(−200)`에서 0으로 포화된 화소 | **81.6%** → 거의 새까만 이미지 |
| `+100`에서 한 바퀴 돈 화소 (원래 값 > 155) | **55.0%** → 밝던 곳이 시커멓게 얼룩짐 |
| `−100`에서 한 바퀴 돈 화소 (원래 값 < 100) | **25.0%** → 어둡던 곳이 밝게 얼룩짐 |

창을 띄워 보면 `dst3`과 `dst4`는 **밝기가 뒤죽박죽된 이상한 이미지**가 나와요. 이게 모듈로 연산의 부작용이에요.

### Step E. numpy로 안전하게 하는 방법

reference에서 했던 바로 그 방법이에요.

```python
safe = np.clip(image.astype(np.int16) + 100, 0, 255).astype(np.uint8)
#              └──────────┬─────────┘          └─┬─┘ └──────┬──────┘
#           ① 더 큰 상자로 옮김               ② 범위 자르기   ③ 원래 상자로
#             (int16: -32768~32767)          (포화 처리)
```

1. **더 큰 상자로 옮겨서** 300이 300 그대로 남게 해요.
2. `clip`으로 0~255 밖을 잘라내요. 이게 포화 처리예요.
3. 다시 uint8로 바꿔요.

`cv2.add` 한 줄이 이 세 단계를 C++ 안에서 한 번에 해 주는 거예요.

## 3-3. `05.image_synthesis.py`: 두 이미지 섞기

### Step A. 재료

| `add1.jpg` (300×300, 평균 138.0) | `add2.jpg` (300×300, 평균 144.0) |
|---|---|
| 흐린 하늘을 배경으로 한 기마상 실루엣 | 석조 부조와 "APOSTO…" 글자가 새겨진 벽 |

두 이미지의 **크기가 같아야** 칸끼리 더할 수 있어요.

### Step B. 세 가지 방법

```python
alpha, beta = 0.6, 0.7
add_img1 = cv2.add(image1, image2)                        # ① 그냥 더하기
add_img2 = cv2.add(image1 * alpha, image2 * beta)         # ② 비율 곱해서 더하기
add_img2 = np.clip(add_img2, 0, 255).astype("uint8")      #    + 직접 포화 처리
add_img3 = cv2.addWeighted(image1, alpha, image2, beta, 0) # ③ OpenCV 한 방
```

### Step C. 화소 3개 추적 (실측)

| 위치 (y,x) | image1 | image2 | ① 단순 합 | 0.6·p + 0.7·q | ② clip+astype | ③ addWeighted |
|---|---:|---:|---:|---:|---:|---:|
| (50, 50) 하늘+벽 | 216 | 81 | 297 → **255** | 186.30 | 186 | 186 |
| (150, 200) 말 몸통+벽 | 26 | 140 | 166 | **113.60** | **113** | **114** ⚠️ |
| (100, 100) 말+벽 | 32 | 186 | 218 | 149.40 | 149 | 149 |

### Step D. ① 단순 합: 너무 밝아요

두 이미지의 평균이 138과 144라서, 더하면 평균이 282쯤 돼요. 255를 훌쩍 넘죠. 실측해 보니 **61.6%의 화소가 255로 포화**돼요. 결과 이미지는 대부분 하얗게 날아가요.

### Step E. ② 비율 곱하기: 숨은 타입 변화

```python
image1 * alpha     # uint8 × float → ?
```

실측: 결과 `dtype`이 **float64**예요. numpy는 소수를 곱하면 결과를 담을 수 있도록 **자동으로 큰 상자(실수형)로 바꿔요.**

```
image1 (uint8)  ×  0.6 (float)   →   결과 (float64)
   216          ×  0.6           =   129.6   (소수점이 살아 있음)
```

그런데 float64 두 개를 `cv2.add`로 더하면 **포화가 일어나지 않아요.** 실수에는 0~255 한계가 없으니까요. 실측 최댓값이 **283.2**예요. 그래서 다음 줄의 `np.clip(..., 0, 255).astype("uint8")`이 꼭 필요해요. reference에서 `.clip(0,255).astype(np.uint8)`을 습관처럼 붙였던 이유가 이거예요.

### Step F. ②와 ③이 1씩 다른 이유: 버림 vs 반올림

(150, 200) 화소를 보면 이래요.

```
0.6 × 26 + 0.7 × 140 = 15.6 + 98.0 = 113.6

② .astype("uint8") → 소수점 이하 버림(truncate) → 113
③ addWeighted      → 반올림(round)              → 114
```

실측해 보니 90,000 화소 중 **40,495개(45%)가 정확히 1 차이**이고, 나머지는 같았어요. 눈으로는 구분이 안 되지만, "직접 구현과 OpenCV 결과가 왜 미묘하게 다르지?"의 대표적인 원인이에요. Part 5의 평활화 비교에서도 똑같은 현상이 나와요.

### Step G. `cv2.addWeighted` 공식

$$\text{dst} = \text{saturate}(\text{src1} \times \alpha + \text{src2} \times \beta + \gamma)$$

```python
cv2.addWeighted(image1, 0.6,  image2, 0.7,  0)
#               src1    α     src2    β     γ (마지막에 더하는 상수)
```

### Step H. α + β의 의미

- **α + β = 1** (예: 0.4 + 0.6): 진짜 블렌딩이에요. 결과 밝기가 두 이미지 사이에 머물러요. reference의 `α·A + (1−α)·B`가 이 경우예요.
- **α + β = 1.3** (이 코드): 전체적으로 1.3배 **밝아지는** 합성이에요. 그래도 포화 비율이 3.0%라서 ①의 61.6%보다 훨씬 자연스러워요.
- **α + β < 1**: 전체가 어두워져요.

> 📚 **reference와의 차이**: reference의 반투명 박스는 α가 **화소마다 다른 값**(마스크 배열)이었어요. 여기 `addWeighted`는 **이미지 전체에 같은 α 하나**를 써요.

## 3-4. ⭐ 명암 대비의 수학: `y = a·x + b`

### Step A. 대비(contrast)란?

> **대비 = 어두운 곳과 밝은 곳의 차이가 얼마나 큰가**

- 대비가 높으면 검정은 더 검게, 흰색은 더 희게 보여요. 또렷하고 강렬해요.
- 대비가 낮으면 전부 비슷한 회색이에요. 뿌옇고 안개 낀 느낌이에요.

### Step B. 직선 하나로 밝기와 대비를 모두 표현해요

중학교 때 배운 일차함수예요.

$$y = a \cdot x + b$$

| 기호 | 그래프에서 | 이미지에서 |
|---|---|---|
| **a (기울기)** | 직선이 얼마나 가파른가 | **대비**. a > 1이면 증가, a < 1이면 감소 |
| **b (절편)** | 직선을 위아래로 이동 | **밝기**. b > 0이면 밝게, b < 0이면 어둡게 |

### Step C. 왜 기울기가 대비일까? 숫자로 확인

어두운 화소 100과 밝은 화소 150이 있다고 해 볼게요. 차이는 **50**이에요.

```
a = 2 :   100 → 200,  150 → 300(→255)    차이 55 이상 → 벌어짐 (대비 ↑)
a = 0.5:  100 → 50,   150 → 75           차이 25     → 좁아짐 (대비 ↓)
b = +30:  100 → 130,  150 → 180          차이 50     → 그대로! (밝기만 ↑)
```

**곱하기는 간격을 늘리거나 줄이고, 더하기는 위치만 옮겨요.** 비유하면 고무줄에 점 두 개를 찍고, 늘리면(곱하기) 점 사이가 멀어지고 그냥 옮기면(더하기) 간격이 그대로인 것과 같아요.

통계로는 **표준편차(std)**가 "값이 얼마나 퍼져 있나", 즉 대비를 숫자로 나타내요. 아래 실측에서 std가 어떻게 변하는지 보세요.

## 3-5. `06.contrast.py`: 대비 조절 네 가지

### Step A. 준비물

```python
image = cv2.imread("images/contrast.jpg", cv2.IMREAD_GRAYSCALE)  # 480×360, 공항의 비트루비우스 인간 조형물
noimage = np.zeros(image.shape[:2], image.dtype)   # 전부 0인 "더미" 이미지
avg = cv2.mean(image)[0] / 2.0
```

**`noimage`는 왜 필요할까요?** `scaleAdd`와 `addWeighted`는 원래 **이미지 두 장**을 받는 함수예요. 한 장만 쓰고 싶어서 **0으로 가득 찬 이미지를 두 번째 자리에 넣어 효과를 없앤 거예요.** (x + 0 = x)

**`cv2.mean(image)`의 실측 반환값**은 `(137.088, 0.0, 0.0, 0.0)`이에요.

- OpenCV는 채널을 최대 4개(B, G, R, A)까지 다룰 수 있어서 **항상 4칸짜리 튜플**을 돌려줘요. 흑백은 채널이 1개라 첫 칸만 의미가 있어요. 그래서 `[0]`을 붙여요.
- 평균 m = **137.088**, `avg` = m / 2 = **68.544**예요.

### Step B. 두 함수 해부

```python
cv2.scaleAdd(src1, alpha, src2)           # = src1 × alpha + src2        (포화, 반올림)
cv2.addWeighted(src1, a, src2, b, gamma)  # = src1 × a + src2 × b + gamma (포화, 반올림)
```

`noimage`(전부 0)를 넣으면 이렇게 줄어들어요.

```
cv2.scaleAdd(image, a, noimage)            = image × a + 0         = a·x
cv2.addWeighted(image, a, noimage, 0, g)   = image × a + 0 × 0 + g = a·x + g
```

결국 둘 다 **`y = a·x + b`**예요. `addWeighted`는 b(gamma)까지 한 번에 줄 수 있어요.

### Step C. 네 가지 결과를 수식으로 정리

| 이름 | 코드 | 수식 | 의도 |
|---|---|---|---|
| dst1 | `scaleAdd(image, 0.2, noimage) + 20` | y = 0.2x + 20 | 대비 크게 감소 |
| dst2 | `scaleAdd(image, 2.0, noimage)` | y = 2x | 대비 증가 |
| dst3 | `addWeighted(image, 0.5, noimage, 0, avg)` | y = 0.5x + 68.5 | 평균 기준 대비 감소 |
| dst4 | `addWeighted(image, 2.0, noimage, 0, -avg)` | y = 2x − 68.5 | 평균 기준 대비 증가 |

dst1의 `+ 20`은 **numpy 덧셈**(모듈로)이에요. 그런데 0.2x의 최댓값이 0.2 × 255 = 51이라 51 + 20 = 71 < 255가 돼서 한 바퀴 돌 일이 없어요. 안전해요.

### Step D. 값 하나씩 추적 (실측)

| x | dst1 (0.2x+20) | dst2 (2x) | dst3 (0.5x+68.5) | dst4 (2x−68.5) |
|---:|---:|---:|---:|---:|
| 0 | 20 | 0 | 69 | 0 (−68.5 → 포화) |
| 40 | 28 | 80 | 89 | 11 |
| 64 | 33 | 128 | 101 | 59 |
| 100 | 40 | 200 | 119 | 131 |
| 128 | 46 | **255** (256 → 포화) | 133 | 187 |
| 180 | 56 | 255 | 159 | 255 |
| 255 | 71 | 255 | 196 | 255 |

검산 한 줄: dst3에서 x=100이면 0.5 × 100 + 68.544 = 118.544 → 반올림 **119** ✔

### Step E. 변환 곡선 네 개를 한 그래프에

```
 y
255┤               dst2 ┌──────────────── (x≥128 포화)
   │              dst4 ╱┌─────────────── (x≥162 포화)
   │                 ╱ ╱
   │               ╱  ╱     ..... 원본 y=x
196┤             ╱  ╱  .....───── dst3 (0.5x+68.5)
   │           ╱  ╱.....──
137┤ ─ ─ ─ ─ ╱─ ─●─ ─ ─ ─ ─ ─ ─ ─   ← 평균 137
   │       ╱ .....
 69┤  ───╱.───                     
 71┤    ╱....          ──────────── dst1 (0.2x+20) : 20~71 사이에 갇힘
 20┤──.╱───────────
  0┼─╱─────────────────────────── x
   0     68   137              255
```

### Step F. 실측 통계: 숫자로 보는 대비

| 결과 | 최소 | 최대 | **평균** | **std (대비)** | 255 포화 | 0 포화 |
|---|---:|---:|---:|---:|---:|---:|
| 원본 | 0 | 255 | 137.1 | 89.8 | 7.0% | 0.6% |
| dst1 | 20 | 71 | **47.4** | **18.0** ↓↓ | 0% | 0% |
| dst2 | 0 | 255 | **183.7** | 90.2 | **50.3%** | 0.6% |
| dst3 | 69 | 196 | **137.3** ✅ | **44.9** ↓ | 0% | 0% |
| dst4 | 0 | 255 | 154.6 | **106.2** ↑ | 43.7% | 19.3% |

여기서 중요한 걸 읽어낼 수 있어요.

- **dst1**: 대비가 1/5로 줄었는데 **평균도 137에서 47로 확 떨어졌어요.** 대비만 낮추고 싶었는데 이미지까지 시커멓게 됐어요.
- **dst2**: std는 거의 그대로인데 평균이 184로 올라가고 **절반이 하얗게 날아갔어요.** 2배를 하니 128 이상이 모두 255가 되어서 늘어난 대비가 포화로 다시 잘려 나갔어요.
- **dst3**: 대비는 절반으로 줄었는데 **평균은 137.1 → 137.3으로 거의 그대로**예요. 이게 바로 "평균 기준"의 효과예요.

## 3-6. ⭐ 왜 평균(avg)을 더하거나 뺄까: 시소의 받침점

### Step A. 문제: `y = a·x`의 받침점은 0이에요

`y = 0.2x`는 **x = 0을 고정점**으로 두고 나머지를 0 쪽으로 끌어당겨요.

```
받침점이 0인 시소 (dst1, dst2 방식)

  a < 1:  모든 값이 0 쪽으로 쭈그러듦 → 대비 ↓ + 전체가 어두워짐
  a > 1:  모든 값이 0에서 멀어짐       → 대비 ↑ + 전체가 밝아짐(포화)

   0 ●━━━━━━━━━━━━━━━━━━━━━━━ 255
   ▲ 받침점
```

밝기와 대비가 **같이 움직여 버리는 게** 문제예요.

### Step B. 해결: 받침점을 평균 m으로 옮겨요

> "평균 화소는 그대로 두고, 나머지만 평균에서 멀어지게 하거나 가까워지게 하자."

$$y = m + a\,(x - m)$$

단계별로 읽으면 이래요.
1. `x − m`: 평균에서 **얼마나 떨어져 있나** (밝으면 +, 어두우면 −)
2. `a × (x − m)`: 그 거리를 a배로 늘리거나 줄이기
3. `m + ...`: 다시 평균 위치에 붙이기

```
받침점이 평균 m 인 시소

   0 ━━━━━━━━━━━━━●━━━━━━━━━━━━━ 255
                  ▲ m = 137 (여기는 안 움직임)
   어두운 쪽은 더 어둡게 ←      → 밝은 쪽은 더 밝게   (a > 1)
```

x = m을 넣으면 y = m + a × 0 = **m**이에요. 평균 화소는 **어떤 a를 써도 그대로**예요.

### Step C. 전개하면 코드의 `gamma`가 나와요

$$y = m + a(x - m) = a\,x + (1 - a)\,m$$

| a | 식 | gamma = (1−a)·m |
|---|---|---|
| 0.5 | 0.5x + 0.5m | **+0.5m = +avg** ✅ (코드의 dst3와 일치) |
| 2.0 | 2x − m | **−m = −2·avg** |

### Step D. 🔍 교재 코드의 dst4는 살짝 어긋나 있어요

코드는 dst4에 `-avg`(= **−m/2**)를 써요. 위 표대로라면 **−m(= −137)**이어야 해요.

받침점(y = x가 되는 점)을 직접 구해 볼게요.

```
dst3: x = 0.5x + m/2   →  0.5x = m/2  →  x = m      = 137  ✅ 평균이 받침점
dst4: x = 2x − m/2     →  x = m/2                  = 68.5 ❌ 받침점이 평균의 절반
```

그래서 dst4의 평균이 137에서 **154.6으로 올라갔어요.** 대비뿐 아니라 밝기도 같이 올라간 거예요. 정확한 식 `addWeighted(image, 2.0, noimage, 0, -m)`으로 직접 돌려 보면 이렇게 나와요.

| | 교재 dst4 (−m/2) | 수정판 (−m) |
|---|---:|---:|
| x=137 → | 205 | **137** (그대로 ✅) |
| 평균 | 154.6 | **129.9** |
| std | 106.2 | 111.9 |

수정판도 평균이 137에서 조금 내려가요. 양쪽 끝이 0과 255에서 잘리면서 생기는 오차예요. 어두운 쪽은 29.3%, 밝은 쪽은 35.4%가 잘려서 비대칭이 생겨요. 그래도 **받침점은 정확히 평균**에 있어요.

> 교재 의도는 "평균을 이용해 밝기 변화를 줄이자"였고, 대비 감소(dst3)에서는 정확히 맞아요. 대비 증가(dst4)는 엄밀히 계산하면 −m이어야 해요. 코드를 고치지는 않았어요. 직접 바꿔서 비교해 보세요.
