## 6-0. 📚 복습: BGR과 채널 다루기

reference 03번에서 `plt.imshow`로 보여줄 때 색이 이상하게 나와서 `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)`나 `img[:,:,::-1]`로 바꿨었죠.

```
컬러 이미지 shape (H, W, 3)           img[y, x] = [B, G, R]   ← OpenCV는 B가 0번 채널
                                     img[:, :, 0] = 파랑 채널 전체 (H, W) 흑백 이미지
                                     img[:, :, 2] = 빨강 채널 전체
```

| 함수 | 하는 일 |
|---|---|
| `cv2.split(img)` | (H, W, 3)을 (H, W)짜리 **채널 3장**으로 나눠요. 결과는 튜플 `(ch0, ch1, ch2)` |
| `cv2.merge([a, b, c])` | 반대로 3장을 합쳐서 (H, W, 3)으로 만들어요 |
| `cv2.cvtColor(img, cv2.COLOR_X2Y)` | 컬러 공간 X를 Y로 변환해요 |

**중요한 함정**: `cv2.imshow`는 3채널 이미지를 받으면 **무조건 BGR로 해석해서** 보여줘요. HSV나 Lab 이미지를 그대로 `imshow`하면 이상한 색이 나와요. 그래서 이번 Part의 코드들은 **`split`해서 채널 하나씩 흑백으로** 보여줘요.

Part 4에서 HSV를 미리 봤어요 (Hue = 색상 각도, 0~179). 이번에 그 **공식**을 다뤄요.

## 6-1. 컬러 공간이 왜 여러 개일까

### 비유: 같은 장소를 가리키는 여러 방법

"서울시청"이라는 같은 장소를 이렇게 표현할 수 있어요.
- 위도 37.566, 경도 126.978 → **GPS가 쓰기 좋음**
- 서울특별시 중구 세종대로 110 → **우편 배달부가 쓰기 좋음**
- "광화문에서 남쪽으로 500m" → **길 안내에 좋음**

장소는 하나인데, **목적에 따라 편한 표현이 달라요.** 색도 같아요.

| 컬러 공간 | 세 숫자의 의미 | 누가/어디서 쓰기 좋나 |
|---|---|---|
| **BGR/RGB** | 빨강, 초록, 파랑 빛의 세기 | 모니터, 카메라 센서 (하드웨어) |
| **CMY(K)** | 하늘색, 자홍, 노랑 잉크의 양 (+검정) | **프린터** |
| **HSI/HSV** | 색상, 선명도, 밝기 | **사람의 직관**, 색으로 물체 찾기 |
| **YCrCb/YUV** | 밝기 + 색차 2개 | **JPEG, 영상 압축, TV 방송** |
| **Lab** | 밝기 + 초록↔빨강 + 파랑↔노랑 | **색 차이 측정** (사람 눈과 비슷한 거리감) |

**변환은 정보를 바꾸지 않아요.** 같은 색을 다른 좌표계로 옮겨 적는 것뿐이에요. 다만 uint8로 저장하면서 반올림 오차가 조금 생겨요.

## 6-2. 가산혼합과 감산혼합: 빛과 잉크

### Step A. 빛을 더하면 밝아져요 (RGB, 가산혼합)

캄캄한 방에서 손전등 세 개(빨강, 초록, 파랑)를 벽에 비춘다고 생각해 보세요.

```
         빨강 R
          ╱╲
    노랑 ╱  ╲ 자홍
        ╱ 흰색╲
  초록 G──────── 파랑 B
         청록

  R + G = 노랑      빛을 더할수록 → 밝아짐
  G + B = 청록      R + G + B = 흰색
  R + B = 자홍      아무것도 없으면 = 검정
```

### Step B. 잉크를 더하면 어두워져요 (CMY, 감산혼합)

흰 종이에 잉크를 칠하면, 잉크는 **특정 빛을 흡수(빼기)**해요.

| 잉크 | 흡수하는 빛 | 반사되어 눈에 보이는 빛 |
|---|---|---|
| **C**yan (청록) | **빨강**을 흡수 | 초록 + 파랑 |
| **M**agenta (자홍) | **초록**을 흡수 | 빨강 + 파랑 |
| **Y**ellow (노랑) | **파랑**을 흡수 | 빨강 + 초록 |

그래서 짝이 정확히 맞아요.

$$C = 255 - R, \qquad M = 255 - G, \qquad Y = 255 - B$$

"빨강이 적을수록 청록 잉크가 많이 필요하다"는 뜻이에요. Part 1의 **반전 `255 − x`**를 채널마다 한 거예요.

### Step C. 순수한 색으로 확인 (실측)

| 색 | BGR | → CMY (계산) | 해석 |
|---|---|---|---|
| 빨강 | (0, 0, 255) | C = 0, M = 255, Y = 255 | 빨강 = **자홍 + 노랑** 잉크 |
| 초록 | (0, 255, 0) | C = 255, M = 0, Y = 255 | 초록 = **청록 + 노랑** |
| 파랑 | (255, 0, 0) | C = 255, M = 255, Y = 0 | 파랑 = **청록 + 자홍** |
| 노랑 | (0, 255, 255) | C = 0, M = 0, Y = 255 | 노랑 잉크만 |
| 흰색 | (255, 255, 255) | 0, 0, 0 | 잉크 없음 (종이색) |
| 검정 | (0, 0, 0) | 255, 255, 255 | 세 잉크 전부 최대 |

## 6-3. `13.convert_cmy.py` 코드 해부와 ⚠️ 채널 이름 버그

### Step A. 코드

```python
white = np.array([255, 255, 255], np.uint8)   # shape (3,)
CMY_img = white - BGR_img                     # (3,) - (270, 320, 3)
Cyan, Magenta, Yellow = cv2.split(CMY_img)    # ⚠️ 이 줄에 문제가 있어요
```

### Step B. 브로드캐스팅: (3,)과 (H, W, 3)

```
white   :                [255, 255, 255]         shape      (3,)
BGR_img : 각 칸마다      [  B,   G,   R]          shape (270, 320, 3)
                         ───────────────
결과    : 각 칸마다      [255-B, 255-G, 255-R]    shape (270, 320, 3)
```

numpy는 **뒤에서부터** 차원을 맞춰요. 마지막 차원이 둘 다 3이니까, `white`를 270 × 320칸 모두에 복사한 것처럼 계산해요. 결과는 uint8이고, 255에서 0~255를 빼니까 **음수가 될 일이 없어서** 안전해요 (Part 3).

### Step C. ⚠️ 채널 순서 버그

`CMY_img`의 채널 순서를 하나씩 따라가 볼게요.

```
BGR_img 채널:   0번 = B       1번 = G       2번 = R
CMY_img 채널:   0번 = 255-B   1번 = 255-G   2번 = 255-R
                    = Y           = M           = C
```

**0번 채널은 Cyan이 아니라 Yellow예요!** 그런데 코드는 `Cyan, Magenta, Yellow = ...`로 받아요.

빨강 화소로 검증해 볼게요. BGR (0, 0, 255) → CMY_img = **(255, 255, 0)**이에요 (실측).

| 변수 이름 (코드) | 실제 들어간 채널 | 빨강 화소의 값 | 맞나? |
|---|---|---|---|
| `Cyan` | 0번 = 255 − B = **Yellow** | 255 | ❌ 빨강에는 Cyan 잉크가 0이어야 해요 |
| `Magenta` | 1번 = 255 − G = Magenta | 255 | ✅ |
| `Yellow` | 2번 = 255 − R = **Cyan** | 0 | ❌ 빨강에는 Yellow가 255여야 해요 |

그래서 13번을 실행하면 **"Cyan" 창에 실제로는 Yellow 채널이, "Yellow" 창에 Cyan 채널이** 나와요. 고치려면 이렇게 써요.

```python
Yellow, Magenta, Cyan = cv2.split(CMY_img)    # ✅ BGR 순서를 따라감
```

다음 파일인 14번은 `Yellow, Magenta, Cyan = ...`으로 **올바르게** 받아요. 두 파일이 서로 다른 것도 이 버그의 증거예요. 이 파일을 고치지는 않았어요. 고칠지는 정해 주세요.

### Step D. 창에 보이는 것 해석하기

- **`CMY_img` 창**: 3채널이라 `imshow`가 **BGR로 착각해서** 보여줘요. 각 채널이 255 − 원래값이니까 결국 **색 반전(네거티브) 이미지**로 보여요.
- **채널별 창(흑백)**: **밝을수록 그 잉크가 많이 필요한 곳**이에요.
  - 실제 Cyan 채널(코드상 "Yellow" 창)에서 **성화의 금색 배경과 나무 문**은 어둡게 보여요. 빨강, 노랑 계열이라 Cyan 잉크가 거의 필요 없어요.
  - 실제 Yellow 채널(코드상 "Cyan" 창)에서는 반대로 금색 배경이 **밝게** 보여요.

## 6-4. CMYK: 왜 검정(K) 잉크를 따로 쓸까

### Step A. 이론과 현실의 차이

이론상 C + M + Y = 255씩이면 완벽한 검정이에요. 하지만 현실에서는 이래요.

1. **잉크가 불완전해서** 셋을 섞으면 칙칙한 **진갈색**이 나와요.
2. 검정 글씨 하나에 잉크 **3배**가 들어가서 **비싸요.**
3. 종이가 잉크에 흠뻑 젖어서 **마르는 데 오래 걸리고 번져요.**
4. 세 잉크 위치가 미세하게 어긋나면 글자 테두리에 **색 번짐**이 생겨요.

그래서 프린터는 **세 잉크의 공통 부분(회색 성분)을 검정 잉크 하나로 대체**해요.

### Step B. 공식

$$K = \min(C, M, Y), \qquad C' = C - K,\quad M' = M - K,\quad Y' = Y - K$$

비유하면, 세 친구가 각각 사과를 7개, 5개, 9개 가졌을 때 **공통으로 가진 5개**를 "공동 바구니(K)"에 넣고 남은 것만 각자 들고 있는 거예요.

```
처리 전:   C ███████          (7)
           M █████            (5)   ← 가장 작은 값 = 공통 부분
           Y █████████        (9)

K = 5      K █████            (공통 5개를 검정 잉크 하나로)
처리 후:   C ██               (2)
           M                  (0)   ← 가장 작은 채널은 항상 0이 됨
           Y ████             (4)
```

### Step C. 실측 화소로 추적

| 색 | BGR | CMY (Y, M, C 순) | K = min | 처리 후 (Y, M, C) |
|---|---|---|---:|---|
| 회색 | (128, 128, 128) | (127, 127, 127) | **127** | **(0, 0, 0)** → 검정 잉크만 |
| 검정 | (0, 0, 0) | (255, 255, 255) | **255** | (0, 0, 0) → 검정 잉크만 |
| 빨강 | (0, 0, 255) | (255, 255, 0) | 0 | (255, 255, 0) → 변화 없음 |
| 주황 | (0, 128, 255) | (255, 127, 0) | 0 | (255, 127, 0) |
| 어두운 빨강 (Part 2 테두리) | (3, 33, 120) | (252, 222, 135) | **135** | (117, 87, 0) |
| 나무 문 (150, 70) | (17, 27, 74) | (238, 228, 181) | **181** | (57, 47, 0) |
| 대리석 벽 (30, 30) | (155, 159, 154) | (100, 96, 101) | **96** | (4, 0, 5) |

- **무채색(회색, 검정)**은 C, M, Y가 전부 0이 되고 **검정 잉크만** 남아요.
- **순수한 원색**은 어느 채널이 이미 0이라 K = 0이에요. 변화가 없어요.
- **어두운 색**(나무 문)은 K가 커요. 잉크 대부분이 검정으로 대체돼요.
- **대리석 벽**은 거의 무채색이라 K가 96이고 나머지는 4, 0, 5만 남아요.

이미지 전체로 보면 K 채널 평균이 **101.9**예요. 이 사진에서 C, M, Y 잉크의 상당 부분이 검정으로 바뀐다는 뜻이에요.

## 6-5. `14.convert_cmyk.py`: 튜플 빼기 배열의 비밀

### Step A. 코드

```python
CMY = cv2.split(CMY_img)                               # 튜플 (ch0, ch1, ch2)
black = cv2.min(CMY[0], cv2.min(CMY[1], CMY[2]))       # 원소별 최솟값
Yellow, Magenta, Cyan = CMY - black                    # ← 이게 어떻게 동작할까?
```

### Step B. `cv2.min`: 원소별 최솟값

`cv2.min(a, b)`는 같은 위치끼리 작은 쪽을 골라요 (`np.minimum`과 같아요). 두 번 중첩하면 세 채널 중 가장 작은 값이 돼요.

```
CMY[1] = [[ 5, 90]]     cv2.min(CMY[1], CMY[2]) = [[ 5, 30]]
CMY[2] = [[ 9, 30]]
CMY[0] = [[ 7, 40]]     cv2.min(CMY[0], 위 결과)  = [[ 5, 30]]  = black
```

### Step C. 튜플 − 배열: 숨은 변환 과정 (실측)

`CMY`는 **파이썬 튜플**이에요 (실측: `<class 'tuple'>`, 길이 3). 튜플에는 원래 빼기가 없어요. 그런데도 동작하는 이유는 이래요.

```
① numpy가 튜플을 배열로 자동 변환
   (ch0, ch1, ch2)  →  np.array  →  shape (3, 270, 320)    ← 채널이 "맨 앞"으로!

② 브로드캐스팅
   (3, 270, 320)  -  (270, 320)  →  black 을 3장 복사한 것처럼 빼기

③ 결과: shape (3, 270, 320) uint8  (실측)

④ 언패킹: 첫 번째 차원(3)을 따라 세 개로 나눔
   Yellow  = 결과[0]   (270, 320)
   Magenta = 결과[1]
   Cyan    = 결과[2]
```

- `cv2.merge`로 만드는 (H, W, 3)과 달리 **(3, H, W)** 모양이 생긴다는 게 포인트예요.
- black은 셋 중 최솟값이라 **빼도 절대 음수가 안 돼요.** uint8 모듈로 걱정이 없어요.
- 이번에는 순서 `Yellow, Magenta, Cyan`이 **올바르게** 붙어 있어요 (6-3 Step C 참고).

## 6-6. HSI: 사람이 색을 말하는 방식

### Step A. 왜 필요할까

친구한테 색을 설명할 때 "R 200, G 150, B 50이야"라고 하지 않죠. 보통 이렇게 말해요.

> "**주황색**인데, **좀 바랜 느낌**이고, **밝은 편**이야"

이 세 가지가 정확히 H, S, I예요.

| 채널 | 뜻 | 물감 비유 | 질문 |
|---|---|---|---|
| **H**ue (색상) | 무슨 색인가 | **어떤 물감 튜브**를 짰나 | 빨강? 초록? 파랑? |
| **S**aturation (채도) | 얼마나 순수한가 | 거기에 **회색 물감을 얼마나** 섞었나 | 원색? 파스텔? 회색? |
| **I**ntensity (명도) | 얼마나 밝은가 | **조명**이 얼마나 센가 | 밝음? 어두움? |

### Step B. 공간 모양: 원기둥(또는 원뿔)

```
                I = 255 (흰색)
                    ●
                   ╱│╲
                  ╱ │ ╲
                 ╱  │  ╲
      H = 각도  ●───┼───●  ← 가장자리 = S 최대 (원색)
     (색상환)    ╲  │  ╱     중심축 = S = 0 (회색)
                 ╲ │ ╱
                  ╲│╱
                    ●
                I = 0 (검정)

  가운데 세로축 = 회색 계열 (검정 → 회색 → 흰색)
  축에서 멀어질수록 = 채도 ↑
  축을 중심으로 돌아가는 각도 = 색상
```

## 6-7. ⭐ HSI 공식의 수학 (`15.convert_hsv.py`)

### Step A. 코드 전체

```python
def calc_hsi(bgr):
    B, G, R = float(bgr[0]), float(bgr[1]), float(bgr[2])     # ① float 변환
    bgr_sum = (R + G + B)
    tmp1 = ((R - G) + (R - B)) * 0.5                           # ② 분자
    tmp2 = math.sqrt((R - G) * (R - G) + (R - B) * (G - B))    # ③ 분모
    angle = math.acos(tmp1 / tmp2) * (180 / np.pi) if tmp2 else 0   # ④ 각도
    H = angle if B <= G else 360 - angle                       # ⑤ 0~360°로
    S = 1.0 - 3 * min([R, G, B]) / bgr_sum if bgr_sum else 0   # ⑥ 채도
    I = bgr_sum / 3                                            # ⑦ 명도
    return (H/2, S*255, I)                                     # ⑧ uint8 범위로
```

### Step B. ① `float()` 변환이 꼭 필요한 이유

주석에는 "속도 면에 유리"라고만 적혀 있는데, 더 중요한 이유가 있어요. `bgr[0]`은 **numpy uint8**이에요. 변환하지 않으면 `R - G`에서 **Part 3의 모듈로**가 터져요.

```
R = 50, G = 200 (uint8)  →  R - G = 50 - 200 = -150  →  모듈로  →  106  ❌
R = 50.0, G = 200.0      →  R - G = -150.0                           ✅
```

### Step C. ⑦ 명도 I: 그냥 평균

$$I = \frac{R + G + B}{3}$$

가장 쉬워요. 세 빛의 **평균 에너지**예요.

### Step D. ⑥ 채도 S: 회색 성분이 얼마나 섞였나

$$S = 1 - \frac{3 \cdot \min(R,G,B)}{R+G+B} = 1 - \frac{\min(R,G,B)}{I}$$

6-4의 CMYK와 같은 아이디어예요. **min(R, G, B)는 세 채널 모두에 공통으로 들어 있는 "회색 성분"**이에요.

| 경우 | min | I | S | 해석 |
|---|---|---|---|---|
| 순수 빨강 (255, 0, 0) | 0 | 85 | 1 − 0/85 = **1** | 회색 성분 0 → 완전 순수 |
| 회색 (128, 128, 128) | 128 | 128 | 1 − 128/128 = **0** | 전부 회색 성분 |
| 분홍 BGR (203, 192, 255) | 192 | 216.7 | 1 − 192/216.7 = **0.114** | 대부분 흰빛, 붉은 기가 조금 |

`if bgr_sum else 0`: 검정(0, 0, 0)이면 0으로 나누게 되니까 S = 0으로 정해요.

### Step E. ②~④ 색상 H: 왜 arccos일까 (기하학적 의미)

공식은 이래요.

$$\theta = \arccos\!\left(\frac{\tfrac{1}{2}\big[(R-G)+(R-B)\big]}{\sqrt{(R-G)^2 + (R-B)(G-B)}}\right)$$

무서워 보이지만, 의미는 **"이 색이 빨강 방향에서 몇 도 돌아가 있나"**예요.

**① 색을 3D 화살표로 보기**

(R, G, B)를 3차원 공간의 점으로 생각해요. 회색들은 (0,0,0)에서 (255,255,255)로 가는 **대각선 위**에 있어요.

**② 회색 성분 빼기**

색에서 그 밝기의 회색 (I, I, I)를 빼면 **"순수한 색 부분" 화살표** c만 남아요.

$$\vec{c} = (R - I,\ G - I,\ B - I)$$

**③ 위에서 내려다보기**

대각선(회색축) 방향으로 위에서 내려다보면, 모든 c 화살표가 한 평면 위에 있어요. 빨강, 초록, 파랑 방향이 **120°씩** 떨어져 있어요.

```
          빨강 방향 (0°)
              ↑
              │    ↗ 이 색의 화살표 c
              │  ╱  θ = 빨강과의 각도
              │╱
              ● 회색축 (위에서 본 모습)
            ╱   ╲
          ╱       ╲
   파랑 (240°)    초록 (120°)
```

**④ 두 화살표 사이의 각도 = 내적 공식**

고등학교 벡터에서 배운 공식이에요.

$$\cos\theta = \frac{\vec{c} \cdot \vec{u}_{\text{빨강}}}{|\vec{c}|\,|\vec{u}_{\text{빨강}}|}$$

빨강 방향 $\vec{u} = (2, -1, -1)/\sqrt{6}$을 넣고 정리하면 이렇게 돼요.

- 분자: $\vec{c}\cdot\vec{u} = \dfrac{2R - G - B}{\sqrt 6} = \dfrac{2}{\sqrt 6}\cdot\underbrace{\tfrac12[(R-G)+(R-B)]}_{\texttt{tmp1}}$
- 분모: $|\vec{c}| = \sqrt{\tfrac{2}{3}}\cdot\underbrace{\sqrt{(R-G)^2+(R-B)(G-B)}}_{\texttt{tmp2}}$
- 상수끼리 정리하면 $\dfrac{2/\sqrt6}{\sqrt{2/3}} = \dfrac{2}{\sqrt 4} = 1$이라서 깔끔하게 **cos θ = tmp1 / tmp2**가 돼요.

즉 `tmp1`은 "빨강 방향으로 얼마나 가 있나", `tmp2`는 "순수한 색 화살표의 길이(에 비례)"예요.

**⑤ arccos의 한계와 `360 - angle`**

arccos는 **0~180°만** 돌려줘요. 각도의 크기만 알지 **시계 방향인지 반시계 방향인지는 몰라요.** 초록(120°)과 파랑(240°)은 둘 다 빨강에서 120° 떨어져 있어서 arccos 결과가 같아요.

```
B ≤ G (초록 쪽으로 돌아감)  → H = θ          (0~180°)
B > G (파랑 쪽으로 돌아감)  → H = 360° - θ    (180~360°)
```

### Step F. 순수한 색으로 전체 추적 (실측)

| 색 | BGR | tmp1 | tmp2 | θ = acos | B > G? | **H** | H/2 (저장) | S×255 | I |
|---|---|---:|---:|---:|---|---:|---:|---:|---:|
| 빨강 | (0, 0, 255) | 255.0 | 255.0 | 0° | 아니오 | **0°** | 0 | 255 | 85 |
| 노랑 | (0, 255, 255) | 127.5 | 255.0 | 60° | 아니오 | **60°** | 30 | 255 | 170 |
| 초록 | (0, 255, 0) | −127.5 | 255.0 | 120° | 아니오 | **120°** | 60 | 255 | 85 |
| 청록 | (255, 255, 0) | −255.0 | 255.0 | 180° | 아니오 | **180°** | 90 | 255 | 170 |
| 파랑 | (255, 0, 0) | −127.5 | 255.0 | **120°** | **예** | 360 − 120 = **240°** | 120 | 255 | 85 |

- **회색**은 tmp2 = 0이라 `if tmp2 else 0`으로 0으로 나누기를 피하고 H = 0이에요. Part 4에서 본 "회색은 H = 0" 함정이 바로 여기서 생겨요.

### Step G. ⑧ 왜 H/2이고 S×255일까

| 값 | 원래 범위 | uint8에 넣기 위해 | 저장 범위 |
|---|---|---|---|
| H | 0 ~ 360° | **÷ 2** | 0 ~ 180 |
| S | 0 ~ 1 | **× 255** | 0 ~ 255 |
| I | 0 ~ 255 | 그대로 | 0 ~ 255 |

H를 360 그대로 넣으면 256 이상에서 넘쳐요. 그래서 반으로 줄였고, 정밀도는 **2° 단위**로 떨어져요. OpenCV의 HSV도 같은 이유로 0~179를 써요.

### Step H. 이미지 전체 변환과 속도

```python
def bgr2hsi(image):
    hsv = [[calc_hsi(pixel) for pixel in row] for row in image]   # 화소마다 파이썬 함수 호출
    return (np.array(hsv)).astype('uint8')
```

`color_space.jpg`(코린토스 운하 사진, 300 × 264 = 79,200화소) 실측이에요.

| 방법 | 시간 |

| 직접 구현 `bgr2hsi` | **102 ms** |

Part 1의 교훈이 그대로예요. 화소마다 파이썬 함수를 부르고, 그 안에서 `sqrt`와 `acos`까지 하니까 느려요. 그리고 `.astype('uint8')`은 **버림**이에요 (Part 3).

## 6-8. 직접 만든 HSI와 OpenCV의 HSV는 뭐가 다를까

15번은 두 결과를 나란히 보여줘요. 이름이 비슷하지만 **S와 I/V의 정의가 달라요.**

| | HSI (직접 구현) | HSV (OpenCV) |
|---|---|---|
| 밝기 | I = **평균** (R+G+B)/3 | V = **최댓값** max(R,G,B) |
| 채도 | S = 1 − min / I | S = (max − min) / max |
| 색상 | arccos 공식 | 육각형 기반 구간별 공식 (sqrt, acos 없이 빠름) |

### 실측 비교

| 색 | BGR | HSI (H, S, I) | HSV (H, S, V) |
|---|---|---|---|
| 빨강 | (0, 0, 255) | (0, 255, **85**) | (0, 255, **255**) |
| 노랑 | (0, 255, 255) | (30, 255, **170**) | (30, 255, **255**) |
| 분홍 | (203, 192, 255) | (175, **29**, 216) | (175, **63**, 255) |
| 어두운 파랑 | (100, 0, 0) | (120, 255, **33**) | (120, 255, **100**) |
| 운하 물 (200, 165) | (119, 103, 80) | (102, 52, 100) | (102, 84, 119) |
| 바위 (100, 30) | (57, 101, 138) | (16, 107, 98) | (16, 150, 138) |

- **H(색상)**: 거의 같아요. 이미지 전체에서 H 차이의 중앙값이 **0**, 90%가 **1 이하**예요 (실측).
- **I vs V**: 순수 빨강의 I는 85밖에 안 되는데 V는 255예요. V는 "가장 센 채널이 얼마나 센가"라서 **원색은 전부 V = 255**예요. I는 "전체 빛 에너지"라서 빨강 하나만 켜진 빛은 흰색의 1/3이에요.
- **S**: HSV 쪽이 대체로 더 커요 (이미지 평균 S: HSI 61.6, HSV 90.8).

**OpenCV는 왜 HSV를 쓸까?** `max`, `min`, 나눗셈만으로 계산할 수 있어서 **빠르고 단순해요.** 색으로 물체를 찾는 용도(Part 7, reference 05번 배경 교체)에는 H가 거의 같으니 HSV로 충분해요.

> ⚠️ 15번 코드의 창 이름 `'OpenCV_Intensity'`에는 실제로 **V(최댓값)**가 나와요. 제목만 HSI 이름을 따라 붙인 거예요.

## 6-9. `16.convert_others.py`: 밝기와 색을 분리하는 공간들

### Step A. 공통 아이디어: 밝기 1개 + 색 정보 2개

```python
Gray_img = cv2.cvtColor(BGR_img, cv2.COLOR_BGR2GRAY)
YCC_img  = cv2.cvtColor(BGR_img, cv2.COLOR_BGR2YCrCb)
YUV_img  = cv2.cvtColor(BGR_img, cv2.COLOR_BGR2YUV)
LAB_img  = cv2.cvtColor(BGR_img, cv2.COLOR_BGR2LAB)
```

세 공간 모두 **0번 채널은 밝기**, 1, 2번 채널은 **색(색차)**이에요.

### Step B. Gray = YCrCb의 Y

> 📚 **복습**: reference 02번의 휘도 공식 Y = 0.299R + 0.587G + 0.114B예요.

실측으로 `Gray_img`와 YCrCb의 Y 채널을 비교했더니 **완전히 같아요** (`array_equal = True`). `COLOR_BGR2GRAY`는 사실 "YCrCb의 Y만 꺼내기"예요.

### Step C. YCrCb: JPEG의 컬러 공간

$$Y = 0.299R + 0.587G + 0.114B$$
$$Cr = (R - Y) \times 0.713 + 128, \qquad Cb = (B - Y) \times 0.564 + 128$$

- **Cr** = "빨강이 밝기보다 얼마나 더 있나" (Color difference, red)
- **Cb** = "파랑이 밝기보다 얼마나 더 있나" (Color difference, blue)
- **+128은 왜?** R − Y는 **음수**가 될 수 있어요. uint8은 음수를 못 담으니까 **128을 "색 없음(0)" 위치로** 정했어요. 128보다 크면 +, 작으면 −예요.

피부색 BGR (140, 170, 225)으로 손계산해 볼게요.

```
Y  = 0.299×225 + 0.587×170 + 0.114×140 = 67.28 + 99.79 + 15.96 = 183.03 → 183
Cr = (225 - 183.03) × 0.713 + 128 = 41.97 × 0.713 + 128 = 157.93 → 158
Cb = (140 - 183.03) × 0.564 + 128 = -43.03 × 0.564 + 128 = 103.73 → 104
```

OpenCV 실측도 **(183, 158, 104)**로 같아요. 피부는 빨강이 많으니 Cr > 128, 파랑이 적으니 Cb < 128이에요.

⚠️ **채널 순서**: 이름은 보통 "YCbCr"라고 부르는데 OpenCV는 **Y, Cr, Cb** 순서예요. 코드의 `sp1 = ['Y', 'Cr', 'Cb']`가 맞게 붙어 있어요.

### Step D. YUV: 같은 아이디어, 다른 비율

$$U = 0.492\,(B - Y) + 128, \qquad V = 0.877\,(R - Y) + 128$$

YCrCb와 같은 구조인데 **계수만 달라요.** (U ≈ Cb 쪽, V ≈ Cr 쪽, OpenCV 순서는 Y, U, V.) 아날로그 컬러 TV 방송에서 나온 공간이에요. 흑백 TV는 Y만 받아서 그대로 보여주고, 컬러 TV는 U, V를 추가로 받아 색을 입혔어요. **하위 호환**을 위한 설계였어요.

피부색 손계산: U = 0.492 × (−43.03) + 128 = **106.8**, V = 0.877 × 41.97 + 128 = **164.8** → 실측 (183, **107**, **165**) ✔

### Step E. Lab: 사람 눈의 거리감에 맞춘 공간

| 채널 | 뜻 | uint8 저장 |
|---|---|---|
| **L** | 사람이 **느끼는** 밝기 (0~100) | × 255/100 → 0~255 |
| **a** | **초록(−) ↔ 빨강(+)** | +128 |
| **b** | **파랑(−) ↔ 노랑(+)** | +128 |

설계 목표는 **"숫자 거리 = 눈으로 느끼는 색 차이"**예요. BGR에서는 같은 거리만큼 바뀌어도 사람이 느끼는 차이가 달라요. 실측으로 비교해 볼게요 (ΔE = Lab 공간에서의 거리).

| 변화 | BGR 거리 | Lab 거리 ΔE |
|---|---:|---:|
| 어두운 회색 (10) → (40) | 52.0 | **13.2** |
| 밝은 회색 (200) → (230) | 52.0 | **10.7** |
| 초록 200 → 230 | 30.0 | **14.6** |
| 빨강 200 → 230 | 30.0 | **11.5** |

BGR로는 똑같이 바뀌었어도 사람은 **어두운 쪽 변화를 더 크게** 느껴요. Lab은 그걸 반영해요. 그래서 회색 128을 Lab으로 바꾸면 L이 128이 아니라 **137**이 나와요 (실측). 사람 눈의 밝기 감각이 **비선형**이라서예요.

### Step F. 순수한 색의 네 공간 값 (실측)

| 색 | BGR | Gray | YCrCb (Y, Cr, Cb) | YUV (Y, U, V) | Lab (L, a, b) |
|---|---|---:|---|---|---|

| 흰색 | (255, 255, 255) | 255 | (255, **128, 128**) | (255, 128, 128) | (255, 128, 128) |

**무채색(흰색, 검정, 회색)은 색 채널이 전부 128**이에요. "색 없음"이라는 뜻이에요.

### Step G. 창을 띄우면 색 채널이 왜 밋밋한 회색일까

`color_space.jpg`의 채널별 범위를 실측했어요.

| 공간 | 0번 (밝기) | 1번 | 2번 |
|---|---|---|---|
| YCrCb | 1~255, **std 54.6** | 112~168, std 11.0 | 67~144, std 15.0 |
| YUV | 1~255, **std 54.6** | 75~142, std 13.0 | 109~177, std 13.5 |
| Lab | 0~255, **std 54.6** | 113~150, std 4.6 | 111~187, std 15.2 |

색 채널들은 128 근처에 좁게 몰려 있어요 (std 4~15). 그래서 창에 **거의 균일한 회색**으로 보여요. 정상이에요. 이 사진은 흙색 절벽과 물빛이라 색이 강하지 않아요.

여기서 중요한 사실을 알 수 있어요. **이미지 정보의 대부분은 밝기(Y)에 있어요.** 사람 눈도 밝기 변화에는 민감하고 색 변화에는 둔해요. 그래서 **JPEG은 Cr, Cb를 가로세로 절반 해상도로 줄여서 저장해요** (크로마 서브샘플링). 용량은 크게 줄고 눈으로는 차이를 거의 못 느껴요.

### Step H. 어디에 쓰나

| 공간 | 대표 활용 |
|---|---|
| YCrCb | JPEG 압축, **피부색 검출** (피부는 조명이 바뀌어도 Cr, Cb 범위가 비교적 일정. 흔히 쓰는 경험적 범위는 Cr 133~173, Cb 77~127) |
| YUV | 영상 코덱, 카메라 출력 포맷 |
| Lab | 색 차이 측정(ΔE), 색 보정, 밝기만 조절하기 (L에만 Part 5의 평활화를 하면 색이 틀어지지 않아요) |
| HSV | 색으로 물체 찾기 (Part 7), 크로마키 |

> 💡 마지막 줄이 실용 팁이에요. 컬러 사진에 평활화를 하고 싶을 때 B, G, R 각각에 하면 **색이 틀어져요.** 대신 YCrCb의 **Y**나 Lab의 **L** 채널에만 적용하고 다시 BGR로 돌려요.

```
│ 1. 컬러 공간 = 같은 색을 목적에 맞게 다시 적은 좌표계. imshow는 3채널을 BGR로만 해석  │
│ 2. CMY = 255 - BGR (채널별 반전). 순서는 BGR을 따라 (Y, M, C)                     │
│    ⚠️ 13번 Cyan/Yellow 변수명이 뒤바뀜. 14번은 올바름                             │
│ 3. CMYK: K = min(C,M,Y), 각 채널에서 K를 뺌 → 가장 작은 채널은 0, 무채색은 K만     │
│    튜플 - 배열 → (3,H,W) 로 자동 변환 + 브로드캐스팅 → 언패킹                       │
│ 4. HSI: I = 평균, S = 1 - min/I (회색 성분 비율),                                │
│    H = arccos(tmp1/tmp2) = 회색축에서 본 "빨강과의 각도",  B>G 이면 360-θ           │
│    저장: H/2 (0~180), S×255.  float 변환 필수 (uint8 뺄셈은 모듈로)                 │
│ 5. OpenCV HSV: V = max, S = (max-min)/max. H는 HSI와 거의 동일. 600배 빠름          │
│ 6. YCrCb/YUV/Lab: 밝기 1 + 색차 2. 색차는 128 = 색 없음                            │
│    Gray == YCrCb의 Y.  OpenCV 순서는 Y, Cr, Cb                                   │
│    Lab: 숫자 거리 ≈ 사람이 느끼는 차이.  정보 대부분은 밝기에 → JPEG 색 압축          │
└────────────────────────────────────────────────────────────────────────────┘
```
