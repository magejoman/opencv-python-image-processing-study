## 🔑 L10 확인 문제 정답

**Q1.** 세 조각에 42번째 줄 조건(`45 < x < 80`, 면적 > 60)을 적용하면 이렇습니다.

| 조각 | (x0,y0,x1,y1) | 폭 × 높이 | w/h | 면적 | 결과 |
|---|---|---|---|---|---|
| ㅎ 꼭지 | (52, 1, 58, 4) | 6 × 3 | 2.0 ✓ | **18** ✗ | **탈락** (면적 60 이하) |
| ㅎ 몸통 | (48, 5, 62, 20) | 14 × 15 | 0.93 ✓ | 210 ✓ | 통과 |
| ㅏ | (63, 2, 70, 27) | 7 × 25 | 0.28 ✓ | 175 ✓ | 통과 |

통과한 두 조각으로 정렬하면:
```
정렬 전                  np.sort(axis=0) 후
몸통 [48, 5, 62, 20]      [48, 2, 62, 20]   ← 48은 몸통, 2는 ㅏ에서 옴 (행이 섞임)
ㅏ   [63, 2, 70, 27]      [63, 5, 70, 27]
x0,y0 = (48, 2)   x1,y1 = (70, 27)   →  (x, y, w, h) = (48, 2, 22, 25)
```

반전 포인트가 하나 있어요. 꼭지는 상자 계산에서는 빠졌지만, 08번 28번째 줄은 그림을 **사각형으로** 잘라냅니다. 그래서 상자 안(y 2~26, x 48~70)에 걸친 꼭지의 **2~3행은 칸 안에 그대로 남고, 맨 윗줄(y=1)만 잘려요.**

**Q2.** 득표가 9 2표, 7 2표로 **동점**입니다. 거리는 보지 않고 **번호가 작은 7**이 이겨요. 가장 가까운 두 명(거리² 100, 120)이 9였는데도 그렇습니다.

고치는 방법은 두 가지예요.
- **① 홀수 K:** K = 3이면 [9, 9, 7]이라 9가 이기고, K = 1이면 바로 9예요.
- **② 거리 가중 투표:** `findNearest`가 돌려주는 `neighborResponses`와 `dist`로 1/거리만큼 표를 줘서 직접 다수결을 냅니다.

**Q3.**
```
resp1[idx] = [resp1[5], resp1[4], resp1[6], resp1[3], resp1[2], resp1[1], resp1[0]]
           = [4, 2, 5, 8, 3, 0, 1]
results[2] = texts[36] = '바'    →    분류 결과:  4 2 바 8 3 0 1
```
`resp2`가 33이어도 `texts[33] = '바'`라서 **출력은 똑같아요.** '바' 중복은 **출력 문자에는 영향이 없고, 투표 단계에서 표를 둘로 쪼개는 데만** 영향을 줍니다(L9 Q3).

## 1-3. 🧪 고칠 때마다 점수가 어떻게 변했나 (전체 파이프라인, 15대 × seed 5개 = 75번)

| 버전 | 바꾼 것 | 정답 / 75 |
|---|---|---|
| A | 원본 그대로 | **21** (SVM이 진짜 번호판을 거부한 게 34번!) |
| B | + 회전 버그 수정 (L6) | **44** ← 가장 큰 도약 |
| C | B + 한글만 K = 1 (L10) | **51** |
| D | B + 숫자와 한글 모두 K = 1 | 50 (숫자는 K = 1이 오히려 1건 손해) |
| E | B + 거리 가중 투표 (K = 10) | 43 (효과 없음) |
| **C + 합치기** | C + `merge_x` (L10) | **52** ← 최고 |

**E(거리 가중)는 왜 효과가 없었을까요?** 1,600차원에서 이웃 거리는 모두 2,000~4,500 사이에 몰려 있어요. 그래서 1/거리 가중치도 최대 2배밖에 차이가 안 나요. 결국 "동점일 때만 거리로 결정하는 보통 투표"와 비슷해지고, 남의 글꼴 9명이 끼는 문제(L10 20-2)는 그대로 남습니다.

⚠️ **이 표는 낙관적인 숫자예요.** K = 1이나 `merge_x`를 **이 15대를 보고** 골랐기 때문입니다. L8 Q3에서 배운 데이터 누수죠. 새 차 사진에서는 이보다 낮게 나올 수 있어요.

## 1-4. 최고 버전(52/75)에 남은 23건 해부

| 종류 | 건수 | 사례 |
|---|---|---|
| **한글만 틀림** | 13 | 12번 마→아·허 (5번 모두), 11번 저→서 (4번), 7번 서→저 (2번), 10번 라→주·러 (2번) |
| **숫자만 틀림** | 4 | 7번 9→7 (2번), 5번 1099→10**7**9 (2번) |
| 둘 다 틀림 | 2 | 2번 34머→**5**4**어**, 7번 서9→**가7** |
| **번호판 검출 실패** | 4 | SVM 거부 3번 (4번 차 ×2, 10번 차), 2차 후보 없음 1번 (10번 차) |

여기서 볼 점이 세 가지 있어요.
1. **K = 1도 공짜가 아니에요.** 12번 차는 K = 10일 때 동점 덕분에 '마'를 3/5번 맞혔는데, K = 1로 바꾸니 가장 가까운 쌍둥이가 '아'라서 **5번 모두 틀렸어요.** 한쪽을 고치면 다른 쪽이 깨지는 **트레이드오프**입니다.
2. **숫자 오답은 거의 다 9→7**이에요. 꼬리가 길고 비스듬한 9의 아랫부분이 7과 닮았기 때문이에요(L10 20-1).
3. 검출 실패 4건은 L8에서 **재학습한 SVM**(여백이 훨씬 넉넉함)이 도움이 될 만한 곳이에요. 다만 그 조합은 아직 측정하지 않았어요.

# PART 2. 이 방식의 한계: 숫자로 보기

## 2-1. 🧮 직렬 파이프라인은 확률을 곱한다

번호판 하나를 맞히려면 **모든 단계가 연속으로** 성공해야 합니다.
```
P(최종 정답) = P(후보 찾기) × P(SVM 통과) × P(글자 7개 분리) × P(글자₁) × P(글자₂) × … × P(글자₇)
```

**글자 7개가 각각 같은 정확도 p라면 p⁷이 돼요:**
| 글자 하나 정확도 p | p⁷ (7글자 전부 맞을 확률) |
|---|---|
| 99% | 93.2% |
| **95.6%** | **73.2%** ← 우리 최고 버전의 실제 값 |
| 95% | 69.8% |
| 90% | 47.8% |

**🔢 최고 버전 역산:** 검출 성공은 71/75 = 94.7%이고, 검출된 것 중 7글자 정답은 52/71 = 73.2%입니다. 73.2%의 7제곱근을 구하면 **글자 하나당 약 95.6%**예요.

글자 하나는 **95% 넘게 맞히는데도** 번호판 전체로는 4번에 1번꼴로 틀립니다.

> 🍕 비유: 시험 7과목을 **전부 통과해야 졸업**이라면, 과목마다 95%로 붙어도 졸업 확률은 70%예요. 과목 하나하나가 아주 강해야 합니다.

## 2-2. 마법 숫자가 너무 많다

이 챕터 코드에 박혀 있는 "이 카메라, 이 거리, 이 번호판 형식 전용" 숫자들입니다.
```
동전:   blur 7×7 σ=2,  OPEN 3×3,  반지름 표 26~70 (≈3.9 px/mm),  색 가중치 ws,  기준 1.2
번호판: blur 5×5,  Sobel 기준 120,  CLOSE 5×13 ×3,  면적 3000~12000,  비율 2~6.5,
        씨앗 ±15,  floodFill ±25,  144×28,  180×35,  여백 6·3,  한글 구역 45~80,
        면적 60·150,  w/h 2.5,  K = 10
```
**카메라 높이, 해상도, 번호판 형식 중 하나만 바뀌어도** 이 숫자들을 처음부터 다시 맞춰야 해요. 2019년부터 쓰는 앞 숫자 3자리 번호판(123가4567)은 "7개", "한글은 3번째", "45~80" 세 가정을 동시에 깹니다.

## 2-3. 특징을 사람이 정했다: "픽셀 그대로"

SVM은 4,032개 픽셀을, k-NN은 1,600개 픽셀을 **있는 그대로** 비교합니다. 그래서:
- 1~2픽셀만 어긋나도 거리가 확 늘어나요 (L9: 같은 '1'끼리도 거리 2,637).
- **모든 픽셀이 같은 무게**라서 "다"와 "나"를 가르는 획 하나가 공통 부분에 묻혀요 (L9: '저' 정확도 0%).

## 2-4. 학습 데이터가 작고 치우쳐 있다

번호판 140장(번호판 70 + 아닌 것 70), 글꼴 20개, 시험용 차 15대(그중 두 대는 같은 번호판)가 전부예요. 그리고 **낮, 정면, 옛날 2자리 번호판뿐**입니다. 밤, 비, 비스듬한 각도, 더러운 번호판은 한 장도 없어요.

## 2-5. "모르겠다"가 없다

k-NN은 '두'를 숫자 분류기에 넣어도 '7'이라고 **자신 있게** 답합니다(L10). SVM도 d가 −0.025처럼 0에 거의 붙어 있어도 "번호판"이라고 하고요. **확신이 없으면 답을 보류하는 장치**(reject option)가 없습니다.

# PART 3. 딥러닝은 무엇이 다른가

## 3-1. 단계별 비교

| 단계 | 이 챕터 (규칙 + 고전 ML) | 요즘 흔한 딥러닝 방식 |
|---|---|---|
| 번호판 찾기 | Sobel → 닫힘 → minAreaRect → floodFill → SVM (5단계) | **객체 검출 CNN** (YOLO 같은 1단계 검출기) 하나 |
| 번호판 펴기 | minAreaRect 각도로 회전 (⚠️ 각도 규칙 함정) | 네 꼭짓점을 직접 예측 → **호모그래피**로 펴기 (📚 Chapter06 복습) |
| 글자 분리 | findContours + 규칙 (7개, 45~80, np.sort) | **생략.** 한 줄을 통째로 읽는 **CRNN + CTC** 계열은 글자 수를 미리 몰라도 됨 |
| 글자 인식 | 픽셀 1,600개로 k-NN | **CNN이 특징을 스스로 학습** ("ㄷ의 윗가로획" 같은 차이에 집중하도록) |
| 동전 | Otsu + 윤곽선 + 색상 히스토그램 + 반지름 표 | 검출이나 인스턴스 분할로 동전마다 바로 종류를 분류 |

## 3-2. 핵심 차이: 누가 특징과 숫자를 정하나

```
이 챕터:  사람이 설계  →  "Sobel로 세로 획을 찾자", "면적 3000~12000", "K = 10"   (숫자 수십 개)
딥러닝:   데이터에서 학습  →  필터와 기준을 수백만 개 가중치로 스스로 찾음
```

> 🍕 비유:
> - **규칙 기반**은 레시피를 정확히 따르는 요리예요. 재료가 같으면 늘 같은 맛이고 **왜 그런 맛인지 설명**도 쉬워요. 대신 재료가 바뀌면(카메라, 번호판 형식) 레시피를 새로 써야 해요.
> - **딥러닝**은 수만 번 맛을 보며 감을 익힌 요리사예요. 재료가 조금 바뀌어도 적응해요. 대신 **맛볼 재료(라벨 붙은 데이터)가 많이 필요**하고, 왜 그 맛을 냈는지 설명하기 어려워요.

| | 규칙 + 고전 ML | 딥러닝 |
|---|---|---|
| 필요한 데이터 | 적음 (이 챕터: 140장 + 글자표 2장) | 많음 (보통 수천~수만 장 + 라벨) |
| 계산 자원 | CPU로 충분 | 학습에는 보통 GPU |
| 설명 가능성 | 높음 (중간값을 하나하나 찍어볼 수 있음) | 낮음 |
| 환경 변화에 대한 강건성 | 낮음 (마법 숫자) | 데이터가 다양하면 높음 |

## 3-3. 그래도 이 챕터의 기법이 계속 쓰이는 곳

- **전처리와 후처리:** 딥러닝이 찾은 네 꼭짓점으로 펴기(호모그래피), 결과를 형식 규칙(정규식 `^\d{2,3}[가-힣]\d{4}$`)으로 검사하기
- **라벨링 보조:** 규칙으로 후보를 뽑아 주면 사람이 확인만 하면 돼요
- **저전력 임베디드나 실시간 처리**에서 가벼운 1차 필터로
- **딥러닝 결과의 상식 검사(sanity check):** 동전 반지름이 물리적으로 말이 되나? 번호판 비율이 2~6.5인가?

# PART 5. 🚗 AVM 업무로 가져갈 교훈

1. **위치 인자 함정은 다른 함수에도 있어요.** 탑뷰를 만들 때 쓰는 `warpPerspective`도 4번째 자리가 dst입니다. 🔢 실측해 보니 `cv2.warpPerspective(img, H, (w,h), cv2.INTER_NEAREST)`의 결과가 **기본값(선형) 결과와 완전히 같았어요.** 보간 방법은 항상 **`flags=`로 이름 붙여** 넘기세요.

2. **OpenCV 버전이 바뀌면 각도 규칙도 바뀔 수 있어요.** L6의 180° 뒤집힘은 4.5부터 바뀐 `minAreaRect` 각도 규칙 때문이었죠. 라이브러리를 올릴 때는 **회귀 테스트**(같은 입력에 같은 출력이 나오는지)가 필요해요. 캘리브레이션이나 fisheye 함수도 마찬가지입니다.

3. **픽셀 상수 대신 물리 단위로 쓰세요.** 동전 표가 "약 3.9 px/mm"에 묶여 있던 것처럼, 탑뷰에는 보통 **mm/px 배율**이 정해져 있어요. 기준을 mm로 적어 두고 배율만 바꾸면, 해상도가 바뀌어도 상수 하나만 고치면 돼요. 길이는 배율만큼, **면적은 배율의 제곱만큼** 바뀐다는 점(졸업 문제 Q2)도 기억하세요.

4. **중간값을 숫자로 찍어 보세요.** 이 챕터에서 찾은 버그(Otsu 기준값 무시, 180° 뒤집힘, dst 자리 인자, 끝 한 줄 잘림, 동점 처리)는 **전부 중간 상태를 출력해서** 발견했어요.

5. **단계별로 성공률을 따로 재세요.** 직렬 파이프라인은 확률이 곱해지니까(2-1), "최종 정답률"만 보면 어디를 고쳐야 할지 몰라요. 이번에도 A→B 개선이 "SVM 거부 34 → 3"이라는 단계별 숫자 덕분에 바로 보였습니다.

6. **튜닝 데이터와 시험 데이터를 분리하세요.** K = 1을 15대로 고른 것처럼, 시험 데이터로 정한 설정은 점수를 부풀려요.

7. **"모르겠다"를 출력할 수 있게 만드세요.** 주차 보조처럼 안전과 관련된 기능에서는 틀린 답을 자신 있게 내는 것보다 **"확신 없음"을 알리는 게** 훨씬 안전해요. SVM의 |d|, k-NN의 최근접 거리와 득표 차이가 그 재료가 됩니다.

### 졸업 문제 정답

**Q1.**
```
0.95 × 0.95 × 0.98 × 0.97⁷  =  0.9025 × 0.98 × 0.808  ≈  0.715   →  약 71.5%
```
글자 단계(0.97⁷ = **0.808**)가 가장 작은 곱셈 인자라서 **글자 인식부터** 고치는 게 효과가 가장 커요. 0.97이 0.99가 되면 그 인자만 0.932로 올라가요.

**Q2.** 길이가 2배가 되면 **면적은 2² = 4배**예요. 그래서 면적 조건은 **12,000~48,000**이 돼야 합니다. **비율**은 가로와 세로가 똑같이 2배가 되니 **2~6.5 그대로**예요. (같은 이유로 `getStructuringElement` 5×13 같은 커널 크기도 길이라서 약 2배로 키워야 해요.)

**Q3.** 4번째 위치 인자는 **dst**라서 `INTER_NEAREST`는 무시되고 **기본값인 선형 보간(INTER_LINEAR)**이 쓰입니다(실측으로 기본값 결과와 똑같음을 확인했어요). 고치려면 `cv2.warpPerspective(img, H, (w, h), flags=cv2.INTER_NEAREST)`처럼 이름을 붙여 넘기세요.
