# 실험: 어안 → 톱뷰 모아레

> **질문**: 어안 렌즈 때문에 톱뷰에서 바로 옆 화소인데도 원본에서 읽는 위치가 크게 바뀐다. 그래서 생기는 모아레를 제품에서는 어떻게 줄이나?
>
> 그 답(밉맵·비등방·슈퍼샘플링·ISP 튜닝·균일 프리블러의 한계)을 **같은 입력, 같은 LUT** 위에서 숫자와 그림으로 확인하는 실험이다.
> 로드맵 P3(바닥 탑뷰 + 모아레, 직접 구현 과제)의 미리보기이고, P3 에서 직접 구현한 결과를 비교할 기준 답안이기도 하다.

## 1. 결과 한눈에

기본 설정: 사이드 카메라(높이 0.95 m, 60° 하향, 190° 등거리 어안, 1280×960), 톱뷰 6 m × 6 m @ 1 cm/px.

| 방법 | 근거리 모아레↓ | 중거리 모아레↓ | 중거리 줄무늬 대비%↑ | 원거리 줄무늬 대비%↑ | 깜빡임↓ | ms (CPU) |
|---|---|---|---|---|---|---|
| 양선형 (지금 방식) | 4.1 | 0.5 | 63.6 | 86.0 | 1.6 | 4.8 |
| ISP 샤프닝 + 양선형 | 7.8 | 0.9 | 97.1 | 111.2 | 3.0 | 4.8 |
| 균일 블러 σ=1 | 0.8 | 0.1 | 31.8 | 61.1 | 0.2 | 1.9 |
| 균일 블러 σ=2.5 | 0.4 | 0.1 | 3.5 | 13.4 | 0.1 | 2.8 |
| 2× 슈퍼샘플링 | 1.7 | 0.3 | 62.8 | 84.8 | 0.8 | 1.9 |
| 피라미드 최근접 레벨 | 0.6 | 0.2 | 36.7 | 86.0 | 0.2 | 10.6 |
| 피라미드 trilinear | 0.7 | 0.1 | 38.2 | 86.0 | 0.2 | 16.7 |
| 비등방 (밉맵 + 긴 축 탭) | 1.2 | 0.3 | 63.6 | 86.0 | 0.5 | 79.8 |
| 정답 (바닥에서 직접 계산) | 0.1 | 0.0 | 100.0 | 100.0 | 0.0 | |

축소율 ρ: 톱뷰 면적의 52% 가 축소 구간 (ρ>1), 11% 가 2배 이상, 최대 4.0배 · 이방성 최대 8.4

모아레·깜빡임은 회색조 0~255 단위, 대비는 정답 대비 %. 지표의 정확한 뜻은 §3.4.

**세 줄 요약**
1. 균일 블러는 **하나의 σ 로 근거리(모아레)와 원거리(선명도)를 동시에 만족시키지 못한다.** σ=2.5 면 모아레는 0.4 로 줄지만 원거리 줄무늬가 13% 만 남는다.
2. 피라미드(밉맵)는 **위치마다 다른 필터**라서 근거리 모아레를 0.7 로 줄이면서 원거리는 86% 그대로 둔다. 다만 등방이라 중거리를 반경 방향까지 흐린다 (64% → 38%).
3. 비등방은 그 중거리를 64% 로 되찾는 대신 근거리 모아레가 조금 더 남는다 (0.7 → 1.2). 공짜는 없다.

## 3. 실험 구성

```
 수식으로 정의한 바닥 ──► 어안 카메라로 '찍기' ──► 어안 영상 ─┐
        │                (센서 박스 적분 + 렌즈 번짐)          │  같은 LUT, 읽는 방법만 8가지
        │                                                       ▼
        └──────────► 정답 톱뷰 (바닥에서 직접, 이상적 필터)    톱뷰 8장 ──► 지표·그림
```

### 3.1 장면과 카메라 — [moire/scene.py](moire/scene.py), [moire/camera.py](moire/camera.py)

| 무늬 | 크기 | 역할 |
|---|---|---|
| 체커보드 타일 + 줄눈 | 30 cm, 1.5 cm | 저주파. 어떤 방법이든 살아남아야 한다 |
| 미끄럼 방지 홈 (전체) | 주기 8 mm | 톱뷰 나이퀴스트(주기 2 cm)보다 촘촘 → **모아레의 원인** |
| 배수구 그레이팅 (근거리) | 주기 12 mm, 대비 큼 | 모아레가 가장 잘 보이는 곳 |
| 줄무늬 표시 (중거리) | 주기 10 cm, 반경 방향 | 표현 가능한 무늬 → 흐리면 손해. 비등방의 이득이 보이는 곳 |
| 줄무늬 표시 (원거리) | 주기 10 cm, 접선 방향 | 균일 블러의 손해가 보이는 곳 |

시뮬레이터 자체도 앨리어싱을 피하도록 만들었다. 먼 바닥에서는 센서 화소 하나가 몇 cm 를 덮는다. 이 화소를 몇 점으로만 찍으면 8 mm 홈이 '카메라 안에서' 거짓 무늬가 된다. 그래서 사인파 무늬는 찍기 전에 수식으로 흐린다(가우시안의 주파수 응답 `exp(-2π²σ²/P²)`). **샘플링 전에 거른다**는 이 실험의 원칙을 시뮬레이터에도 그대로 적용한 것이다.

### 3.2 LUT 와 발자국 — [moire/lut.py](moire/lut.py)

톱뷰 화소 → 지면 점 → 어안 좌표. 이 표(`map_x`, `map_y`)가 제품의 톱뷰 LUT 와 같은 것이다.
이웃한 출력 화소의 LUT 차분이 **"출력 한 칸 = 원본 몇 화소"**, 즉 축소율이다.

```python
step_x = np.hypot(np.gradient(map_x, axis=1), np.gradient(map_y, axis=1))   # 출력 오른쪽 한 칸 → 원본 이동량
step_y = np.hypot(np.gradient(map_x, axis=0), np.gradient(map_y, axis=0))   # 출력 아래쪽 한 칸 → 원본 이동량
rho = np.maximum(step_x, step_y)       # GPU 가 밉맵 레벨 log2(ρ) 를 고를 때 쓰는 값
```

2×2 야코비안의 특이값 `s_max`, `s_min` 은 발자국 타원의 긴 반지름·짧은 반지름이다. 그 비율이 이방성이다.
[01_scene.jpg](results/01_scene.jpg) 의 축소율 지도를 보면 차 바로 옆(0.4 m)이 3.8배 축소, 5 m 는 0.9배(확대)다. 이방성은 반대로 멀수록 커진다 (1.1 → 6.1).

### 3.3 비교하는 방법 — [moire/methods.py](moire/methods.py)

| 방법 | 하는 일 | 앞 답변의 어디에 해당하나 |
|---|---|---|
| 양선형 | `cv2.remap` 그대로. 이웃 4개만 읽는다 | 문제의 출발점 |
| ISP 샤프닝 + 양선형 | 원본에 언샤프 마스크 → 양선형 | §3-(5) ISP 튜닝: 샤프닝이 앨리어싱을 키운다 |
| 균일 블러 σ=1, 2.5 | 원본 전체에 같은 가우시안 → 양선형 | 처음 말했던 '고전적 방법' — 위치 불변 회선의 한계 |
| 2× 슈퍼샘플링 | 톱뷰를 2배로 그린 뒤 `INTER_AREA` | §3-(3) |
| 피라미드 최근접 레벨 | 화소마다 반올림한 레벨 하나에서 읽기 | §3-(1) — 레벨 경계 띠를 보여 주려고 |
| 피라미드 trilinear | 이웃 두 레벨을 lod 소수부로 섞기 | §3-(1) 밉맵 |
| 비등방 | 긴 축을 따라 N 탭, 탭마다 짧은 축에 맞는 레벨 | §3-(2) |

§3-(4) 오프라인 EWA 와 §3-(6) 시간축 필터는 구현하지 않았다.

### 3.4 지표 — [moire/metrics.py](moire/metrics.py)

- **모아레**: 미세 무늬가 있는 어안 영상과 없는 어안 영상을 **같은 방법으로** 톱뷰로 보내고, 두 결과의 차이를 잰다(RMS).
  - 미세 무늬는 톱뷰로 표현할 수 없으니 이상적인 값은 0 이다.
  - 두 영상은 타일 경계가 똑같아서, 방법이 경계를 얼마나 흐리든 그 영향은 상쇄된다. 처음에는 '정답과의 차이'로 쟀는데, 그러면 경계가 부드러워진 것까지 모아레로 세어서 trilinear 가 양선형보다 나쁘게 나왔다. 그래서 이 방식으로 바꿨다.
- **줄무늬 대비 %**: 10 cm 줄무늬의 표준편차를 정답과 비교한 것. 선명도 지표다. 100% 를 넘으면 정답보다 과장된 것이다(샤프닝).
- **깜빡임**: 1 cm/프레임으로 움직인 10프레임을 움직임 보정한 뒤, 화소마다 시간 방향 표준편차를 잰 것. 정답이 평평한 곳만 잰다. 정답은 0.0 이 나와야 하며, 이 값으로 보정이 정확한지 확인한다.

## 4. 결과 읽기

**① 양선형과 ISP 샤프닝** — [03_near.jpg](results/03_near.jpg)
그레이팅 위에 굵은 물결이, 타일 위에 가는 줄무늬가 보인다. 샤프닝을 켜면 모아레가 4.1 → 7.8, 깜빡임이 1.6 → 3.0 으로 두 배가 된다. 동시에 줄무늬 대비는 100% 를 넘는다. 샤프닝은 '선명해 보이게' 하는 대가로 앨리어싱을 키운다. 코드 한 줄 안 바꾸고 ISP 설정만으로 모아레를 줄일 수 있는 이유가 이것이다.

**② 균일 블러의 딜레마** — [04_mid_far.jpg](results/04_mid_far.jpg)
σ=1 은 근거리 모아레를 4.1 → 0.8 로 줄이지만 중거리 줄무늬가 64% → 32% 로 반토막 난다. σ=2.5 면 줄무늬가 거의 사라진다(3.5%, 13%). 근거리는 원본 4화소가 톱뷰 1화소로 줄어드는 곳이고, 중·원거리는 (반경 방향으로) 원본 1화소가 톱뷰 1~3화소로 늘어나는 곳이다. 같은 σ 가 근거리에선 '톱뷰 1화소 미만의 약한 블러'이고, 중거리에선 '톱뷰 몇 화소짜리 강한 블러'가 된다.

**③ 슈퍼샘플링 2×**
모아레가 4.1 → 1.7 로 절반 넘게 줄고 선명도는 거의 그대로다. 하지만 2배 촘촘히 읽는 것은 축소율 2배까지만 막는다. 근거리는 최대 4배라 잔무늬가 남는다.

**④ 피라미드 (밉맵)**
근거리 0.7, 원거리 86% (양선형과 같음). 축소 구간에서만 작은 레벨을 읽고 확대 구간(ρ<1)에서는 원본을 그대로 읽기 때문이다. **위치 불변 회선(피라미드 각 단계) 여러 벌 + 위치마다 고르기(remap)** 가 위치 가변 필터를 근사한다.
'최근접 레벨'은 숫자는 비슷하지만 [04_mid_far.jpg](results/04_mid_far.jpg) 중거리 줄무늬에 **곡선 띠**가 생긴다. lod 가 0.5(ρ ≈ 1.4)를 넘는 곳에서 반올림한 레벨이 0 → 1 로 갑자기 바뀌어서다. trilinear 가 두 레벨을 섞는 이유다.

**⑤ 등방 vs 비등방**
중거리는 이방성이 2.5~3.6 이다. 접선 방향으로는 1.3~1.9배 축소, 반경 방향으로는 확대다. 등방 밉맵은 큰 쪽(접선)에 맞춰 레벨을 고르니 반경 방향 줄무늬까지 흐린다(38%). 비등방은 접선 방향으로 탭 여러 개를 찍고 반경 방향은 원본 해상도로 읽어서 64% 를 지킨다.
대신 근거리 모아레가 0.7 → 1.2 로 조금 늘었다. trilinear 는 긴 축 기준으로 넉넉히(사실은 과하게) 흐려서 나이퀴스트 근처를 세게 누른다. 비등방은 덜 흐린 탭 2개로 나눠서 나이퀴스트 바로 위 성분이 조금 더 샌다. **선명도와 앨리어싱은 교환 관계**다. 제품에서 lod_bias 로 이 균형을 조절한다.

**⑥ 원거리의 한계**
모든 방법이 원거리·중거리에서 정답보다 흐리다(최대 86%, 64%). 카메라가 그 거리를 그만큼밖에 분해하지 못해서이고(확대 구간), 리샘플링 필터로는 고칠 수 없다. 모아레(축소 구간)와는 다른 문제다.

**⑦ 깜빡임** — [05_flicker.gif](results/05_flicker.gif)
양선형 1.6, trilinear 0.2 로 8배 차이다. GIF 에서 바닥은 오른쪽에서 왼쪽으로 흐른다. 두 가지를 눈여겨보자.

- 그레이팅의 물결은 바닥을 따라가지 않고 **제자리에 고정된 채** 그 위로 상자 테두리만 지나간다. 그레이팅은 가로 줄이라 차가 X 방향으로 움직여도 어안 영상 속 모습이 같다. 그러니 물결은 바닥의 무늬가 아니라 '샘플링 격자와 무늬의 간섭'이고, 카메라에 붙어 있다.
- 밝은 타일의 홈(X 방향 무늬)은 바닥과 함께 움직인다. 그래서 그 위의 잔무늬는 프레임마다 모양이 바뀌며 반짝인다.

정지 화면에서는 눈에 덜 띄던 잔무늬가 움직이면 '반짝임'이 된다. 주행 영상으로 평가해야 하는 이유다.

## 6. 한계

- 카메라 한 대, 평평한 바닥, 합성 무늬다. 노이즈·ISP·압축·실제 렌즈 왜곡은 없다.
- 센서 렌더는 화소당 4×4 점 박스 적분 + 사인파의 해석적 사전 블러로 근사했다. 아주 먼 바닥(톱뷰 범위 밖)은 평균 밝기로 바랜다.
- 피라미드는 `cv2.pyrDown`(5×5 가우시안)이다. GPU 밉맵은 보통 2×2 박스라 커널이 다르다.
- ms 는 CPU(numpy/OpenCV) 참고값이다. GPU 비용과 다르고, 비등방 80 ms 는 탭 × 레벨 remap 을 전부 돌리는 단순 구현 탓이다.
- GPU 의 `GL_TEXTURE_EXTERNAL_OES` 에서 밉맵을 못 쓰는 제약 같은 플랫폼 문제는 다루지 않는다. 제품 적용 설계는 [moire_sim/HANDOFF_topview_moire.md](../../moire_sim/HANDOFF_topview_moire.md) 참고.
